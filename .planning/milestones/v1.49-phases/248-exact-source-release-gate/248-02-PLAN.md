## Exact-head CI choice

GitHub documents that a pull_request run uses the synthetic merge commit for GITHUB_SHA, while a push run identifies the pushed commit. Add a push trigger for the single configured Release Please branch and have the privileged workflow_run consumer query that completed CI run by run ID, then compare its head SHA with the current PR head and the successful ci-gate job. This avoids accepting a green PR merge-commit check as proof of the PR head and closes branch-advance races with a final exact-head reread. Release Please creates or updates the branch with RELEASE_PLEASE_TOKEN so the push event starts CI; GitHub suppresses most follow-on workflow events created with GITHUB_TOKEN.

Sources: [pull_request and workflow_run event semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [GITHUB_TOKEN event suppression](https://docs.github.com/en/actions/concepts/security/github_token), [workflow_run security guidance](https://docs.github.com/en/actions/reference/security/secure-use).
</context>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Release candidate branch to CI | Candidate code is executed only in the normal read-only CI workflow. |
| workflow_run event to privileged merge job | Event metadata and API results are untrusted until repository, workflow, run, branch, and SHA are correlated. |
| Candidate content to merge decision | Changelog and ledger text are data; they are parsed but never executed. |
