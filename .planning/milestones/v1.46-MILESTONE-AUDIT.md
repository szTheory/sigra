## Findings

### W-1 — Duplicate `Email` label in the passkey-primary login variant, plus a broader duplicate-id cluster (HIGH — deferred)

**Requirements:** AUTHUI-02, AUTHUI-04, PROOF-03

Two distinct defects on the same page.

**(a) Duplicate visible label.** The PROOF-03 acceptance fix changed both magic-link forms
to `"Email for sign-in link"`, but those two occurrences are *mutually exclusive branches*.
In the `passkey_primary_enabled` branch the collision is unfixed: `login_html.ex:44` (the
primary passkey form) and `login_html.ex:111` (`password_form/1`, rendered at `:75` once
the disclosure expands) both read `dgettext("sigra", "Email")`. This is exactly the defect
class the owner rejected during PROOF-03 review, surviving one configuration flag away.

**(b) Duplicate DOM ids — broader, and pre-existing.** The initial write-up framed this as
a two-input passkey-vs-password id collision. That was too narrow. `@form` **and**
`@magic_link_form` are both built with `as: "user"` (`session_controller.ex:28-29`), so
*every* `f[:email]` on the page derives `id="user_email"` — four inputs in the passkey
branch (`:44`, `:68`, `:111`, and `enterprise_form/1` at `:136`). The else branch has the
same problem at lower count. This predates v1.46 and the milestone's work neither
introduced nor touched it.

Mitigating: `passkey_primary_enabled?` defaults to `false` (`core/auth.ex:831`) and the
acceptance smoke installs with `--no-passkeys` (`admin-acceptance-smoke.sh:125`), so the
composition has never been rendered in a browser.

**Deferred by owner decision on 2026-07-28** rather than fixed at close-out. Fixing (a)
alone takes the id cluster 4 → 3 — it closes the label collision but leaves a page-wide
"no duplicate ids" assertion still failing, and half-fixing invites a repeat of exactly the
partial-coverage mistake that produced this finding. A fully-verified implementation plan
for (a) exists at
`.planning/quick/260728-d9h-fix-passkey-primary-email-label-and-id/260728-d9h-PLAN.md`;
the finding is tracked at
`.planning/todos/pending/2026-07-28-w1-passkey-primary-duplicate-email-label-and-id.md`.

### W-2 — Example `sigra_auth.css` never received the v1.46 stylesheet (MEDIUM — deferred)

**Requirements:** AUTHUI-01, AUTHUI-03, AUTHUI-04, EXPR-01

`test/example/priv/static/assets/sigra_auth.css` is 12,281 B against the canonical
27,914 B, last touched by `d0a02f9f` (2026-06-08, pre-v1.46), with **zero** occurrences of
`.sigra-auth-flow`, `.sigra-auth-action--primary`, `.sigra-auth-disclosure`, or
`.sigra-auth-code-list`. The drift is silent because the example re-brands its own auth in
the `vt-*` lane, and the library's `/admin/branding` preview
(`branding_live.ex:96`) only uses `sigra-auth--preview` classes that exist in the stale copy.

Root cause is a gate asymmetry: `test/sigra/install/features/admin_test.exs:396` enforces
example≡template byte-parity for `sigra_admin.css`; no equivalent gate exists for
`sigra_auth.css`.

Deferred rather than fixed at close-out because refreshing the example copy would change
what `/admin/branding` renders, which risks drifting committed admin checkpoint baselines —
that needs the CI-native recapture lane, not a close-out edit.

### W-3 — Runtime coverage of generated auth is login-only (MEDIUM — deferred)

**Requirements:** AUTHUI-02, AUTHUI-03, AUTHUI-04, PROOF-01

`admin-generated.spec.ts:79` is the only browser test that renders a `sigra-auth-*`
surface, and it visits `/users/log_in` only. Registration, confirmation, reset,
reactivation, sudo, and invitation acceptance (AUTHUI-02), plus settings / MFA / backup
codes / passkeys / sessions (AUTHUI-03), are proven only by source-string assertions in
`test/sigra/install/auth_ui_contract_test.exs` plus `--warnings-as-errors` compile.

PROOF-01's literal "register/confirm" clause is satisfied programmatically, not through the
UI — the smoke seeds and confirms via `User.confirm_changeset()`
(`admin-acceptance-smoke.sh:180+`). The registration-template → generated-host-runtime link
is unproven.

This is the milestone's single largest proof gap and W-1 is the concrete evidence of its
cost: ~1,100 lines of template change verified almost entirely by string matching.

### W-5 — `export_auth_data/2` deny path is orphaned (LOW — deferred)

**Requirements:** SEC-01

data-export clause is satisfied in source but unreachable in a generated host;
`generated_impersonation_parity_test.exs:18` asserts only that the string appears.
