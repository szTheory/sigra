### Publish source objects before refs

When separately authorized, use `git push` to publish each unchanged frozen source commit to its individually allowlisted isolated branch. Git's receiving side accepts pushed objects and updates refs; GitHub's separate Create a reference endpoint takes a ref name and SHA and is not documented as transferring a missing object graph. The two readiness-pass 404s therefore remain a source-availability blocker; a ref-only call does not satisfy the publication plan. Verify each remote branch tip against the exact frozen SHA. `[CITED: https://git-scm.com/docs/git-receive-pack]` `[CITED: https://docs.github.com/en/rest/git/refs#create-a-reference]`

Before publication, inspect all workflow files and applicable push/observer triggers against the exact branch names and credential principal. GitHub documents that push events can run matching workflows and branch filters restrict which branches trigger them. Events caused by `GITHUB_TOKEN` generally do not create another workflow run, except for `workflow_dispatch` and `repository_dispatch`; a push made through another principal may behave differently. A `workflow_run` observer requires its workflow file on the default branch. Do not treat the CI workflow's own push filter or token type alone as a repository-wide trigger audit. `[CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push]` `[CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run]`

The checked-out `.github/workflows/ci.yml` declares `workflow_dispatch`, `schedule`, push branches `main` and `release-please--branches--main`, and pull request base `main` — verbatim trigger excerpt: `workflow_dispatch:`, `schedule:`, `push: branches: [main, release-please--branches--main]`, `pull_request: branches: [main]`. `[VERIFIED: .github/workflows/ci.yml:3-40]` This is local source evidence, not a live assertion about every workflow or remote observer.

### Dispatch a fixture through a registered workflow path

GitHub's dispatch documentation requires the workflow path to exist on the default branch. Dispatch can select another branch using `--ref`; the workflow concepts documentation says a run uses the workflow version present on the event's associated ref. Therefore a same-path fixture definition can be selected if the default-branch copy registers `workflow_dispatch` and the dispatch targets the fixture ref. Keep that fixture definition dispatch-only with a distinct workflow name, and capture actual workflow path/name, event, ref, SHA and run origin before treating startup as proved. The checked-out `ci.yml` contains a `workflow_dispatch` declaration, but this task made no account/API probe; live default-branch registration and selected-ref execution remain unobserved. `[CITED: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow]` `[CITED: https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows]`

### Look up production caches without restoring or saving

Use pinned `actions/cache/restore` with the production key, path, restore-key expression and `lookup-only: true`. The action documentation says lookup-only skips download but does not change save behavior; the restore-only action avoids the combined cache action's save lifecycle. Cache version depends on the path and compression tool, so a probe-only path/version cannot prove production availability. A lookup is not an actual restore or proof of useful warm contents. `[CITED: https://github.com/actions/cache]` `[CITED: https://github.com/actions/cache/blob/main/restore/README.md]` `[CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-version]`

Check future fresh-PR eligibility separately from the fixture probe. GitHub scopes cache access by key, cache version and branch; a default-branch cache can be consumed by other branches, while a pull-request-created cache is limited to reruns of that same PR. The exact keys, versions, accessible scopes and actual restores remain unproved for this project, including five app dependency caches. Do not infer availability or absence from the 17-entry inventory, local lexical hashing, a sibling branch or a lookup-only hit. `[CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache]`

### Pattern 1: Frozen source pair

**What:** Materialize one source containing all common correctness/environment repairs. Derive control from it and candidate from exactly the same tree plus the declared Phase 254 treatment patch. Record full source/tree/file digests, producer commit, workflow file digest, application source and treatment patch.  
**When to use:** Before hosted preparation. A different SHA is expected only where the declared treatment necessarily changes source; document separate application/workflow/workload identities.  
**Example:** Existing `ci-run-metrics.sh` source preflight/bundle interfaces and comparison tests are the local pattern. Add a deterministic dry-run that asserts common patch equality and treatment-only diff; do not run hosted actions in this gate. `[VERIFIED: scripts/ci/ci-run-metrics.sh:1-100]`

### Pattern 2: Producer-owned durable test evidence

**What:** Write each test suite's report to a persistent invocation directory, upload it with run/attempt identity, and validate report digest and producer metadata before comparing test identity/status.  
**When to use:** Every control and candidate full-workload family.  
**Current boundary:** `ci-mix-receivers.py` creates a `TemporaryDirectory` when `SIGRA_CI_RECEIVER_OUTPUT` is missing and calls `temporary.cleanup()` after each standalone leg (`scripts/ci/ci-mix-receivers.py:90-135`). Its native aggregate reads ordinary, scaffold and dep-off reports under the passed output (`:168-208`). `[VERIFIED: scripts/ci/ci-mix-receivers.py:90-208]` CI explicitly uploads two legacy ExUnit paths with `if-no-files-found: warn` (`.github/workflows/ci.yml:627-636`) and metadata names run/attempt and cache status (`:669-748`); this does not establish durable actual three-leg reports. `[VERIFIED: .github/workflows/ci.yml:627-748]`  
**Implementation guidance:** Add a persistent run/attempt-bound receiver output and upload/validate ordinary, scaffold, and dep-off reports; fail closed when expected files or test identities are missing. Compare identities, result statuses, seeds, actual skips/exclusions and setup-vs-product rows; never equate a suite count with equal work.

### Pattern 3: Compare only verified real PR families

**What:** Bind PR creation timestamp to the final successful applicable required check; bind each check to run, attempt, merge/source/head/base, workflow, and actual job. Calculate wait from original PR run `created_at`; retain retry delay and all attempt job costs.  
**When to use:** Acceptance families and offline replay.  
**Example:** Existing hosted verifier requires a unique PR with registered PR number/head/base and exact attempt jobs, then validates required check job binding and success (`scripts/ci/ci-hosted-gate-verify.py:1870-1944`). `[VERIFIED: scripts/ci/ci-hosted-gate-verify.py:1870-1944]` Its comparison-family origin is a useful start but needs narrowly scoped coverage for stale same-name checks, wrong merge/source, missing duration and partial-rerun de-duplication.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|

## Common Pitfalls

### Pitfall 1: Calling different-PR cache entries warm

**What goes wrong:** Preparation on one PR looks green, but the measured control/candidate PR restores no exact cache or only a broader fallback.  
**Why it happens:** GitHub PR caches are associated with `refs/pull/.../merge`; official docs say those caches can be restored only by reruns of that PR, not the base or sibling PRs. Existing workflow uses `pull_request` and cache keys have restore prefixes.  
**How to avoid:** Inspect every current workload owner/key and its actual reported `cache-hit`, restore key/scope, OS/runtime dimensions. Test the exact planned PR refs locally where possible; do not call a restore-prefix fallback an exact warm hit. Consider existing base-scope reusable caches only if safe and demonstrated.  
**Warning signs:** `cache-hit=false`, any fallback restore, different lock/tool/runtime/image identity, or only the prep PR has the cache.

### Pitfall 2: Treating native completion as complete test evidence

**What goes wrong:** A successful `mix ci` is accepted despite missing or ephemeral report files for one receiver.  
**Why it happens:** Standalone `ci-mix-receivers.py leg` defaults to a temporary directory and removes it; workflow uploads legacy timing paths and warns if absent.  
**How to avoid:** Persist all three reports under invocation output, upload with run/attempt binding, require files and complete test identity/status coverage, and compare actual test work between sides.  
**Warning signs:** Temporary output default; `if-no-files-found: warn`; a report that only covers ordinary plus dep-off guard, not scaffold.

### Pitfall 3: Equating workflow end or rerun start with required-result wait

**What goes wrong:** The wait excludes initial queue time or includes irrelevant trailing work.  
**Why it happens:** Full workflow has optional/trailing jobs; `run_started_at` for a rerun is not the original request origin. GitHub `pull_request` uses a merge ref, so a same-name check from an obsolete merge/source is not equivalent.  
**How to avoid:** Use original event run `created_at` to last successful completion of every frozen applicable required context, each bound to exact run/attempt/job and PR head/base/merge. Preserve attempted failures and retry delay.  
**Warning signs:** `updated_at`, whole workflow conclusion, run-attempt start, check name without SHA/job binding.

### Pitfall 4: Counting rerun jobs twice or losing their cost

**What goes wrong:** Partial rerun jobs are duplicated or failed/cancelled attempt cost disappears.  
**Why it happens:** Physical jobs persist across attempts but the API returns attempt-scoped job lists.  
**How to avoid:** Store raw job receipts by attempt; deduplicate unique physical job IDs for cost, preserve per-attempt outcomes and fail if a required duration is unknown. Use only one watcher per run and retain the original origin on the one allowed infra retry.  
**Warning signs:** Sum of job IDs has duplicates across attempt response, absent timestamp treated as zero, failures filtered out of cost.

### Pitfall 5: Treating proposed ceilings as authorization

**What goes wrong:** Planning writes become permission to consume hosted runs or publish evidence.  
**Why it happens:** Context contains precise proposed budgets (four preparation invocations; 40 primary families) but explicitly states collection is unauthorized.  
**How to avoid:** Finish local gates and scoped plan first. Preparation and primary measurement are separate future authorized actions. Stop at `insufficient_data` once 20 valid pairs are impossible; no replacements, extensions or budget renewal.
