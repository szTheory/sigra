## Checked platform facts

- Workflow GET returns identity/path/state. Disable uses PUT to `/repos/{owner}/{repo}/actions/workflows/{workflow_id}/disable`, yielding `disabled_manually`; enable uses PUT to the corresponding `/enable` endpoint, yielding `active`. Both mutation endpoints document Actions write permission for fine-grained tokens. Bind the actual permission capability in the future proposal without exposing or changing credentials. A successful response needs an independent GET read-back. [Workflow REST API](https://docs.github.com/en/rest/actions/workflows)
- Disabling prevents new triggers and leaves existing runs alive. An existing run cannot be rerun while disabled. No documented replay of skipped events is promised by re-enabling; never dispatch or rerun release work to compensate. [Disable/enable guide](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)
- Runs can be queued, in_progress, requested, waiting or pending; status/conclusion are different. Filtered run searches have a 1,000-result ceiling, so an incomplete/capped search cannot establish absence. Enumerate complete pages, retain Link/total/count and origin checks, and block on unknown states or unproved completeness. [Workflow-run REST API](https://docs.github.com/en/rest/actions/workflow-runs)
- Release-PR auto-merge and merge-queue state require explicit observations; GraphQL exposes AutoMergeRequest and MergeQueueEntry. A future fixed query may read those fields only, with complete cursor traversal, errors/permission failures blocking. HTTP POST for that fixed read query grants no GraphQL mutation permission. [Pull-request GraphQL reference](https://docs.github.com/en/graphql/reference/pulls)
- Custom environment patterns have their own paginated GET route. An environment response saying custom_branch_policies:true does not contain those patterns. [Deployment branch policies](https://docs.github.com/en/rest/deployments/branch-policies)

These are platform capabilities, not proof that this repository is quiet or restored. The 60-second snapshot age and the stable-scan rules below are proposed controller safeguards, not a GitHub transactional guarantee.

## Durable recovery and separate reserve

INSTALL-LEDGER carries per-target original/current state and origins, intent ID/method/route/payload digest, reserved/spent allowance, sent/acknowledged/unknown/read-back outcomes, timestamps and exact restore target. It also records proposal/source identities, pending installation intents, run/job/cache settlement inventory, original normal/restoration deadlines, counters and the next allowed action. Persist intent with fsync/atomic replacement and recoverable Git read-back before mutation. Retain dirty revisions using the standing write-ahead rule.

Every exception, interruption, signal or partial pause switches durably to recovery_required/restore_only before exiting. A continuation may reconcile pending outcomes, observe settlement and restore targets; it cannot push/open/merge/dispatch/seed or renew the normal scope. If a second disable fails, reconcile it and restore the first only after proving no installation consequence remains. If a disable/enable/merge/dispatch response is uncertain, read the real state first; never blindly retry that mutation. A proved unchanged state after an uncertain write still does not permit an automatic repeat under this once-only proposal.

BUDGET separates normal work, settlement/reconciliation and restoration-only resources. Normal work cannot spend the restoration reserve, including requests/GraphQL points/mutations and time. Before every normal mutation verify enough untouched reserve and time remain for the graph's maximum outstanding settlement path plus both independent read-backs/activity closeout. The normal deadline and restoration deadline are fixed before hosted consent; neither resets on resume, failed attempt, rate-limit delay or proposal repair. Queue/service uncertainty that prevents a finite safe bound blocks approval.

At normal timeout, stop new normal work and use only the reserved settlement/restoration continuation. Re-enable only after settlement, even when time has expired. If recovery deadline/quota/permissions or evidence availability prevents safe completion, retain both actual states and unknown intents, set recovery_blocked, keep prep/measurement blocked and escalate with the concrete missing run terminal record, workflow GET, API outcome or permission. Do not enable speculatively, silently extend time or spend beyond reserve. A separately approved recovery-only decision can supply additional recovery resources without reopening or resetting the spent normal allocation.

RESTORATION.json independently binds original captures, all disable/enable intents and read-backs, pause intervals per workflow, settlement evidence, final equality, final activity scan, all attempted/failed recovery costs and ledger/deadline identities. Success means exact state equality plus safe settlement and complete closeout, not always enabled. Recovery failure is retained as failure; an offline package/report may describe it without accepting preparation or measurement.
