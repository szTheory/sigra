## Pattern Assignments

### Bounded collector, comparison contract, and source preflight

**Analog:** `scripts/ci/ci-run-metrics.sh` (tracked)

This is a large shell driver with embedded Python. Keep changes localized to existing modes/helpers; do not fork collection logic. CLI defaults include `REQUEST_METHOD="GET"` and separate flags for collection, replay, evaluation, and comparison-plan validation (lines 64-100). The comparison evaluator already verifies source bundle identities, calls independent family-origin verification, checks browser coverage parity, derives physical-job costs, and computes median/nearest-rank p95 in the comparison path (around lines 2436-2660; use grep-targeted reads for exact sections because the file is large). New local preflight should follow existing fail-closed issue codes and digest-bound bundle interfaces. Hosted preparation, dispatch, measurement, and publication remain out of scope here.

**Test analog:** `scripts/ci/ci-run-metrics-attempt.test.py` (tracked). It builds synthetic raw bundle fixtures and exercises the real CLI/evaluator; retain this fixture-first shape for wrong source/merge, stale checks, missing duration, and rerun de-duplication.

### Persistent native receiver evidence

**Analog:** `scripts/ci/ci-mix-receivers.py` (tracked), `record_leg` (lines 94-136) and native aggregator (139-210).

`record_leg` takes the persistent output root from `SIGRA_CI_RECEIVER_OUTPUT`, writes per-leg timing and command records beneath `legs/<name>` and `commands/<name>`, and records seed/test metadata. Its standalone fallback creates and deletes a temporary directory (lines 95-100, 134-135), which explains why CI must pass a durable root. The native aggregator invokes `mix ci`, reads ordinary/scaffold/dep-off reports, and builds `sigra.ci-mix-receivers/v1` including leg records and exit status (lines 168-209). Extend this producer-owned schema/validation seam; require all expected leg records and identities rather than treating missing data as an empty report.

### CI producer artifact upload and metadata

**Analog:** `.github/workflows/ci.yml` (tracked), library job (lines 620-668).

The library step records the command under `$RUNNER_TEMP/ci-diagnostics/library`, then uploads a run/attempt-named timing artifact with `retention-days: 7`; the current legacy upload uses `if-no-files-found: warn` (627-636). The following diagnostic manifest includes source SHA, run ID, attempt, job/seam and explicit file roles (637-668). Extend this producer-bound manifest/upload pattern to the actual three native reports, fail on missing expected files, and preserve report digests and run/attempt identity. Avoid secrets and environment dumps.

### Independent origin verification

**Analog:** `scripts/ci/ci-hosted-gate-verify.py` (tracked), `verify_comparison_family_origin` (1836-1944).

Concrete patterns: confine bundle paths and reject symlinks (1841-1851); verify declared digests before parsing (1852-1860); bind registration to run/event/workflow/head (1872-1884); bind exactly one PR and its head/base repository identity (1888-1897); require attempt job receipts and job run/attempt/head consistency (1898-1916); bind required check names to unique actual jobs, exact SHA, GitHub Actions app, and successful conclusion (1925-1944). ### Offline replay and immutable historical separation

**Analog:** `scripts/ci/ci-comparison-replay.py` (tracked), imports/constants and `preflight_sources` (1-124).

The replay tool pins source commits and receipt identities (22-44), hashes inputs, rejects unsafe paths (46-67), resolves git objects and verifies source blob digests before replay (76-124). A new comparison replay must use its own contract/input identities and never alter Phase 255's pinned constants, historical inputs, or old terminal result. Reuse safe-path, hash, preflight, and deterministic input packaging ideas; route calculation through the already existing evaluator when possible.

### Browser identity and status comparability

**Analog:** `scripts/ci/ci-browser-records.mjs` (tracked), `compareProductCoverage` (206-249).

## Shared-cache amendment patterns — 2026-10-25 (D-24–D-29)

The preparation-amendment pattern above is historical: it forbids warming `main` and treats any missing main cache as a stop. D-24–D-29 supersede that recommendation for one workflow-only protected installation and a separate main-only seeder. Retain the earlier probe as history; it is not a substitute for cache creation or actual restore.

### Installation and common-base re-freeze

**Pattern:** One isolated workflow-only PR goes through the ordinary branch rules and all applicable required checks. Do not edit canonical CI/application bytes or branch rules. The merged commit becomes the new common base. Freeze it explicitly, then derive both control and candidate merge trees again against that same commit. Compare exact app/workflow identities and confirm the candidate still differs only by the approved speed-treatment patch. Keep old source heads and old merge records immutable; if unrelated main drift or a conflict appears, readiness is blocked pending a new decision.

**Why:** PR-source SHAs are fixed, but a main change alters the merge trees used by real PR runs. Fixed heads alone cannot demonstrate comparable treatment or required-check source identity.

### Dedicated guarded seeder

**Pattern:** A separate workflow file uses only `workflow_dispatch`, an explicit main-ref guard, fixed trusted source and owner allowlists, action pins, minimal read permissions and checkout with persisted credentials disabled. Source SHA, owners, cache keys/path settings and commands are fixed in reviewed workflow code, not arbitrary dispatch inputs. It checks out the fixed repaired control as the producer, maintains five app dependency owners only, and runs only the native setup/compilation work required for those outputs. No PR code or secrets enter the writer path. Do not use `pull_request_target` or add cache write permission to a low-trust PR workflow: GitHub documents cache-poisoning risk for write-capable low-trust jobs. [CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching]

**Code-to-research mapping:** the normal app cache convention is in `.github/actions/example-playwright-boot/action.yml` (`example_deps_cache`, pinned `actions/cache`, `test/example/deps`, `test/example/_build`, `working-directory: test/example`, `MIX_ENV: dev`). The five owner/port values are listed in the D-26 context text: `admin_behavior`, `admin_checkpoints`, `design_gallery`, `non_admin_smoke`, `demo_showcase`; ports 4001–4005. Preserve production ordering, runtime-derived key parts, and archive/compression settings, rather than making a probe-only key shape.

### Save receipts and actual restore distinction

**Pattern:** Treat each `actions/cache` save as a post-job operation. Persist a separate receipt per owner with source/tree, run/attempt/job, owner, key, version, ordered paths, default-branch ref/scope, action/archive settings, exact save outcome and terminal job result. Validate receipt digest/origin independently. A successful job, a lookup hit, or an action output indicating restore does not prove a usable saved archive or future restore. GitHub documents that cache version depends on path and compression metadata and that `pull_request` caches are scoped to the merge ref. [CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching] [CITED: https://github.com/actions/cache]

**Next consumer:** Only later approved full preparation can prove actual exact cache restores in fresh main-based PR families. Bind each restore to owner/key/version/scope and verify all real native reports and executed test identities. Keep compilation, DB preparation, `npm ci`, and browser OS dependency setup; cache hits are inputs, not substitutes for work or correctness.
