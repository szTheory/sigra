## Summary

The authenticated start/return authority boundary was reviewed together with its persistence, cookie transport, browser proof, and CI guard. Two continuation lifecycle paths remain unbounded: terminal database records are never reclaimed by the shipped runtime, and an authenticated client can grow its encrypted session cookie until browser cookie-size limits disrupt the flow.

## Narrative Findings (AI reviewer)

## Warnings

### WR-01: Expired and consumed continuations are never reclaimed by the runtime

**File:** `test/example/lib/example/accounts/crosswake_continuations.ex:62`
**Issue:** `cleanup_expired/2` is the only cleanup implementation, but no reviewed runtime path schedules or calls it. The start path at `crosswake_controller.ex:9` only issues more rows. Consequently every expired, denied, and allowed continuation retains its opaque session/subject binding and audit reference indefinitely unless an operator discovers and invokes this internal function manually. The bounded cleanup test proves the helper, not the required data-retention lifecycle.
**Fix:** Add a supervised, recurring host job (or invoke a bounded cleanup from an existing trusted maintenance job) and test that it calls `cleanup_expired/2` until the backlog is drained. For example, run batches from an Oban worker or scheduled process, with a fixed cap per execution and telemetry for failure/retry.

### WR-02: Start requests can overflow the encrypted cookie transport

**File:** `test/example/lib/example_web/controllers/crosswake_controller.ex:87`
**Issue:** Each successful `POST /crosswake/start` adds a new handle, verifier, and expiry entry to `:crosswake_pkce` (`Map.put(entries, handle, ...)`). Entries are pruned only on a later return or another start after expiry, and there is no cardinality cap or replacement policy. An authenticated user can issue many starts within the 300-second TTL, causing the signed/encrypted cookie to exceed browser size limits; the browser may reject the replacement cookie, making subsequent return/login behavior fail unpredictably. The current tests cover one entry only.
**Fix:** Bound the transport to a small fixed number of outstanding continuations (preferably one for this fixed flow). Before storing, delete prior entries or retain only the newest unexpired entry; add a controller test that repeatedly posts to `/crosswake/start` and asserts the serialized session remains bounded and only the intended continuation can complete.
