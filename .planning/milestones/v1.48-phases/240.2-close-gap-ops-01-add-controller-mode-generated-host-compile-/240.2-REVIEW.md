# Phase 240.2: Code Review Report

**Reviewed:** 2026-08-11T03:11:41Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The new fresh-host smoke leg and its source contracts correctly establish a separate controller-mode compilation lane. However, the supporting controller-mode implementation compiles while leaving generated account-security requests broken: the settings GET renders a non-existent inferred view, every MFA mutation endpoint is intentionally a no-op, and the registration controller drops the passkey-enrollment intent. The source-level contracts do not issue any controller-mode auth requests, so they cannot detect these failures.

## Critical Issues

### CR-01: Controller-mode MFA settings route raises at runtime

**File:** `/Users/jon/projects/sigra/priv/templates/sigra.install/core/settings_controller.ex:20`

**Issue:** `SettingsController` calls `render(conn, :mfa_settings, ...)`. Phoenix infers the view module from the controller name, so this resolves to `<WebModule>.SettingsHTML.mfa_settings/1`; the generated template instead defines `<WebModule>.MFASettingsHTML.mfa_settings/1`. A signed-in user requesting `GET /users/settings/mfa` therefore receives an undefined-template/view error, despite the fresh host compiling and booting.

**Fix:** Render through the actual generated view, for example:

```elixir
conn
|> put_view(<%= web_module %>.MFASettingsHTML)
|> render(:mfa_settings, mfa_enabled: status.enabled, ...)
```

Alternatively, rename the generated HTML module to `SettingsHTML` and keep its function name aligned with this controller.

### CR-02: All controller-mode MFA security actions are exposed but disabled

**File:** `/Users/jon/projects/sigra/priv/templates/sigra.install/core/settings_controller.ex:31-36`

**Issue:** The router emits endpoints for enrollment, confirmation, completion, disable, backup-code regeneration, and trusted-browser revocation, and `MFASettingsHTML` renders links/forms to them. Every action routes to `unavailable/1`, so users of a `--no-live` app cannot enroll in MFA, finish enrollment, disable it, regenerate recovery codes, or revoke trusted browsers. This is a functional and security-management regression masked by compile/boot-only smoke coverage.

**Fix:** Implement these actions with the same `Auth.mfa_enroll/1`, `Auth.mfa_confirm_enrollment/3`, `Auth.mfa_disable/3`, `Auth.mfa_regenerate_backup_codes/3`, and `Sigra.MFA.Trust.revoke_all/4` operations used by `mfa_settings_live.ex`, keeping enrollment state in a signed server-side session. If controller mode intentionally does not support MFA management, do not generate these routes/templates and replace account links with an explicit, accurate capability boundary.

### CR-03: Controller registration loses the requested passkey enrollment

**File:** `/Users/jon/projects/sigra/priv/templates/sigra.install/core/registration_controller.ex:14-17`

**Issue:** With passkeys enabled, `registration_html.ex` submits `user[enroll_passkey]`. The controller always generates `/users/confirm/#{token}` without `?enroll_passkey=1`. Consequently the passkey-aware `ConfirmationController.confirm/2` clause is never selected, so a user who chose “Add a passkey after creating your account” never receives the post-confirmation enrollment flow. `RegistrationLive` preserves this value when constructing its confirmation URL; this controller does not.

**Fix:** Derive the boolean from `user_params` and append the query parameter when true, matching `RegistrationLive`:

```elixir
enroll_passkey = Map.get(user_params, "enroll_passkey") in ["true", "on", "1", true]

confirmation_url_fun = fn token ->
  path = if enroll_passkey, do: ~p"/users/confirm/#{token}?enroll_passkey=1", else: ~p"/users/confirm/#{token}"
  url(conn, path)
end
```

## Warnings

### WR-01: Malformed registration POST crashes with a function-clause error

**File:** `/Users/jon/projects/sigra/priv/templates/sigra.install/core/registration_controller.ex:14`

**Issue:** `create/2` accepts only params containing a `"user"` map. A valid-CSRF malformed request such as `POST /users/register` without that key raises `FunctionClauseError` and produces a 500 response rather than redirecting or rendering a validation error.

**Fix:** Add a fallback `create(conn, _params)` clause that flashes a generic validation error and redirects/renders a fresh registration form.
