  <name>Task 1: Build and prove one shared branch/worktree mutation coordinator</name>
  <files>scripts/maintainers/repo-mutation-coordinator.sh, scripts/maintainers/repo-mutation-reference-transaction, scripts/maintainers/repo-mutation-coordinator.test.sh, scripts/maintainers/repo-mutation-coordinator.test.mjs</files>
  <behavior>
    - Main and linked worktrees resolve the same coordinator root using Git's common directory.
    - Coordinator acquisition and reference-transaction admission are serialized through a short atomic gate; an in-flight prepared ref transaction prevents coordinator acquisition, and a held coordinator rejects unrelated prepared branch/ref/HEAD transactions.
    - A coordinator owner token permits the owner's own Git operations; a process in a separate worktree without that token is rejected before its ref transaction commits.
    - Installation preserves/chains an existing executable reference-transaction hook and other executable hooks, or fails before changing config when safe chaining cannot be proven.
    - Verification checks the installed hook bytes/path and every registered worktree's effective hook path. Active/stale locks and abandoned transaction leases are reported and never removed automatically.
    - Fixtures demonstrate blocked `git branch`, `git update-ref`, checkout/worktree HEAD attachment from a linked worktree while the lock is held, and successful owner-authorized ref mutation; no sleeping or production repository access is used.
  </behavior>
  <precondition>All tests create temporary repositories and linked worktrees. They never install hooks or change Git config in the project checkout or remote.</precondition>
  <action>Create a sourceable Bash coordinator with `install`, `verify`, `run`, and `status` entry points. Store state under a dedicated directory in `git rev-parse --git-common-dir`; use atomic `mkdir` gate/lock/transaction-lease directories and an opaque per-owner token. During a non-coordinated Git transaction's `prepared` hook phase, atomically reject if a coordinator lock exists or register a lease until `committed`/`aborted`; coordinator acquisition takes the same gate, rejects any outstanding lease, writes its owner record, then releases the gate. During a coordinated operation, the hook accepts only the token recorded in the current lock. Fail closed on a missing owner record, stale lock/lease, hook mismatch, worktree-specific hook override, or conflicting existing hook configuration. Do not implement automatic stale-lock reclamation. Tests must use a real temporary main/linked-worktree pair and verify that `git worktree add` updates a hooked symbolic HEAD, that the second worktree cannot attach a branch while another process holds the lock, and that the owner can perform an expected ref transaction. Include a source inventory guard for repository-owned production branch/worktree ref mutators so a new uncoordinated entry point fails validation.</action>
  <verify>
    <automated>bash scripts/maintainers/repo-mutation-coordinator.test.sh && node --test --test-reporter=tap scripts/maintainers/repo-mutation-coordinator.test.mjs</automated>
    <fails_when>A linked worktree observes a different coordinator, a ref/HEAD mutation commits without the owner token during a held lock, a coordinator acquires across an in-flight transaction lease, a prior hook is silently lost, an uncoordinated production mutator passes the inventory guard, a test touches the project refs, or the command exits nonzero.</fails_when>
  </verify>
  <done>The shared coordinator and hook are installed/verified only through explicit operations, serialize ref transaction admission across linked worktrees, and have deterministic fixture coverage for ownership, contention, leases, chaining, and fail-closed recovery.</done>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Git ref transaction to common coordinator | Concurrent branch updates or symbolic HEAD attachments must not cross the local deletion window. |
| Linked worktree to shared repository state | Every worktree must resolve the same active hook, lock, gate, and transaction leases. |
| Hook installation to pre-existing hook policy | Installing coordination must preserve or safely chain existing hooks; uncertainty halts installation. |
| Snapshot candidate to local ref deletion | The exact full ref and expected OID remain guarded by the existing compare-and-delete. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-245-12-01 | Tampering | Local branch ref transaction | high | mitigate | Shared prepared-phase hook rejects uncoordinated transactions while the prune owner holds the common lock. |
| T-245-12-02 | Race condition | Worktree HEAD attachment | high | mitigate | Hook observes symbolic HEAD updates; lock admission and transaction leases share an atomic gate. |
| T-245-12-03 | Denial of service | Abandoned lock or transaction lease | medium | accept | Fail closed and require explicit operator reconciliation; never auto-delete stale coordinator state. |
| T-245-12-SC | Same-user deliberate hook bypass | Git config/command override | medium | accept | Verify effective hooks for all registered worktrees and document that a process deliberately overriding `core.hooksPath` is outside the cooperative coordinator contract. |
</threat_model>
