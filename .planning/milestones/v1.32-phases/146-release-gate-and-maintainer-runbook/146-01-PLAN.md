<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Maintainer dispatch -> GitHub Actions workflow inputs | Manual dispatch or recovery inputs can select the wrong ref or version unless validated. |
| Release Please outputs -> checked-out source tree | The workflow must prove the checked-out tag, manifest, and `mix.exs` version describe the same release. |
| GitHub Actions secrets -> workflow logs | `HEX_API_KEY` must stay in secret-backed env vars and never be echoed or transformed into artifact output. |
| Workflow logs -> release evidence | Release evidence is only trustworthy if the workflows run the canonical gates and keep stable job identities. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-146-01 | Tampering | `.github/workflows/release-please.yml` | mitigate | Verify `tag_name == v<version>`, verify `.release-please-manifest.json`, verify `@version`, and keep checkout pinned to `needs.release-please.outputs.tag_name`. |
| T-146-02 | Tampering | `.github/workflows/hex-publish.yml` | mitigate | Add `Validate manual release inputs` so only `v<release_version>` or a commit SHA is accepted, then verify manifest/version/source_ref before publish. |
| T-146-03 | Information Disclosure | `HEX_API_KEY` usage in publish jobs | mitigate | Keep `HEX_API_KEY` in step env only, do not echo it, and do not add artifact uploads containing environment dumps. |
| T-146-04 | Repudiation | `.github/workflows/ci.yml` release evidence | mitigate | Reuse the existing CI job ids via `workflow_dispatch` so gate evidence is tied to a stable workflow name and job surface instead of an ad hoc release-only copy. |
| T-146-05 | Repudiation | package inspection / dry-run evidence | mitigate | Add explicit `mix docs --warnings-as-errors`, `mix hex.build --unpack`, and Hex visibility steps so the workflow logs contain evidence for each release gate. |

## ASVS Notes

ASVS Level 1 applies. This plan directly addresses high-severity release-operation threats: wrong commit/tag publication, secret leakage/misuse, incomplete release evidence, and unvalidated manual workflow inputs.
</threat_model>
