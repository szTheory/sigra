<objective>
DX-05's second defect. `notify-failure-issue.sh` is the only loud consumer of a red `ci-gate` on
`main`, and on nightly `30331796188` it concluded `failure` — because `gh issue create --label` was
handed a label that did not exist. A notifier that dies on its own signal path is a dishonest gate by
another route: the red happened, and nobody saw it.

D-22 makes the script self-healing rather than soft-failing the label, per the filed todo's own
recommendation. Research adds one correction the todo did not have: GitHub's permissions reference
says `issues: write` covers both `GET /repos/{owner}/{repo}/labels` and `POST .../labels`, and both
callers already declare it — but community discussion #13565 has a contested 2022-to-2025 history on
exactly that question. That ambiguity is not resolvable without a live write, so the self-heal is
built fail-SOFT: if `gh label create` is denied, a warning is logged and the issue is opened anyway,
falling back to an unlabelled `gh issue create` as a last resort. The issue is the signal; the label
is only how the issue is found again.

The hard boundary PATTERNS surfaced and CONTEXT did not: the existing `gh` stub's fallthrough is
`echo … >&2; exit 1`, and the script under test runs `set -euo pipefail`. The instant the script
calls `gh label list`, cases A, B and C all break with `exit=1 create_count=0`. So the stub is
extended first, in Task 1, before the script learns the new call.

D-23 is honored by omission: nothing here opens, comments on, or probes a real issue.

Purpose: the `release-lane-rot` signal survives a missing label, and its own self-test proves it.
Output: a self-healing notifier and four new hermetic cases.
</objective>
