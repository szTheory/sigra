<objective>
Build the single shared loud-signal mechanism (D-07) and wire its two consumers (D-02 for HARD-01,
D-06.3 for HARD-02). Today a red `upgrade_smoke`/`ci-gate` on main has no loud consumer, and
release-please auto-publish stalls silently for ~30 minutes on a `gate-ci-green` timeout (proven real:
run #74 = failure, no alert — 222-RESEARCH.md Finding 4). This plan replaces both silent failure modes
with one idempotent "open-or-update a tracking Issue" script invoked from a push/schedule-gated reporter
job in ci.yml and a failure-aggregator job in release-please.yml.

Per 222-RESEARCH.md Finding 2: use the preinstalled `gh` CLI in one shared shell script (no new
SHA-pinned third-party action). ci.yml default permissions are `contents: read` (needs a job-level
`issues: write` override); release-please.yml already declares workflow-level `issues: write` (:22).
The notify jobs must NOT be added to `ci-gate.needs` and must NOT be required checks — a push-only
required context risks stranding PR merges under ruleset 14941512 (Pitfall 2). Copy the needs-free,
push/schedule-gated shape of `nightly_probe` (ci.yml:2181).

Purpose: make every release-lane failure loud and discoverable via one durable tracking Issue.
Output: the shared notify script + self-test; the two consumer jobs; workflow-assertion coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions job -> GitHub Issues API | The notify job runs with `issues: write` and `GITHUB_TOKEN`, writing issue titles/bodies |
| Workflow context (`github.*`) -> issue title/body | Branch/ref/actor/run strings are interpolated into the Issue body |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-222-02-01 | Elevation of Privilege | ci.yml notify job permissions | high | mitigate | `issues: write` is scoped to the `notify_release_lane_rot` job only; ci.yml workflow default stays `contents: read`. No workflow-wide write grant. release-please.yml's pre-existing workflow-level `issues: write` (:22) is unchanged (already-shipped surface) |
| T-222-02-02 | Tampering | untrusted `${{ github.* }}` in issue title/body | high | mitigate | GitHub context strings are passed to `gh` only via the step `env:` mapping and as `--body`/`--title` argument values — never interpolated into a `run:` shell expression — so a crafted branch/ref/actor cannot inject shell or `::workflow::` commands; BODY carries controlled run URL + SHA + surface |
| T-222-02-03 | Information Disclosure | GH_TOKEN / GITHUB_TOKEN in logs | medium | mitigate | The script never echoes the token; it is consumed only by `gh` via `GH_TOKEN` env, and GitHub masks the token in logs |
| T-222-02-04 | Denial of Service | issue spam on repeated failures | low | mitigate | Idempotent find-open-by-label -> comment-or-create keeps one durable tracking issue per label; occurrences append, no per-run new issue |
| T-222-02-SC | Tampering | package installs | low | accept | No npm/pip/hex/cargo installs — uses the preinstalled `gh` CLI (no new SHA-pinned third-party action per RESEARCH Finding 2) |
</threat_model>
