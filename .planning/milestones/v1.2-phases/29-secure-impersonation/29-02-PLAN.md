<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser POST/DELETE -> impersonation controller | Untrusted requests may attempt to bypass sudo, forge `return_to`, or hit the stop action from non-admin routes |
| `UserAuth` renew/clear cycle -> preserved admin token | Session fixation protection must remain intact while selected keys survive renewal |
| app-wide stop route -> impersonation restore helpers | The non-admin stop path must restore only from preserved impersonation state and never from route membership alone |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-05 | S | controller start/stop routes | mitigate | Per D-06, wire start behind `RequireSudo` and use explicit controller routes rather than LiveView events or hidden buttons. |
| T-29-06 | T | `return_to` handling | mitigate | Reuse the local-path validation pattern from `SudoController` so external redirects are rejected during start and stop. |
| T-29-07 | E | session renewal preservation | mitigate | Preserve only the explicit impersonation-restoration keys around `renew_session/1`; all other session data is cleared as before. |
| T-29-08 | D | timeout expiry in `UserAuth` | mitigate | Per D-18, centralize timeout-driven restoration in `UserAuth` helper paths and cover them in focused tests. |
| T-29-09 | E | app-wide stop route | mitigate | Keep the stop route outside admin-only scopes, but require preserved impersonation state in `UserAuth`/controller restore logic so impersonated users can end the session without reacquiring admin routing. |
</threat_model>
