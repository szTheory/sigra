# v1.2 "Admin Dashboard" — Earmarked Direction

This document captures the full user direction on the v1.2 milestone as
expressed during the v1.1 scoping conversation on 2026-04-11. It sits
dormant until v1.1 completes, at which point it is consumed by the next
`/gsd-new-milestone` invocation (copy content into `MILESTONE-CONTEXT.md`
at that time).

**Do not execute against this file directly.** This is a forward-looking
capture. When v1.2 starts, reconfirm with the user that the direction is
still accurate (some of it may have evolved during v1.1 research and
execution) before treating it as binding.

## Scope

v1.2 bundles three tightly-related feature areas:

1. **Admin UI for user management** (LiveView, mobile-first, light+dark)
2. **Admin impersonation** (first-class, security-sensitive)
3. **Expanded audit views** (per-user, per-org, rich filtering)

All three belong together because the admin UI is the primary surface for
impersonation and audit exploration; building them separately would
duplicate the user detail / session / audit viewer code three times.

## Goal

> Ship a beloved, default-on, opt-out admin user-management UI in
> LiveView: Django-admin-level delight, mobile-first, light+dark mode,
> org-aware from day 1 (on the v1.1 Organizations foundation), with
> first-class admin impersonation and rich audit exploration. Basic
> branding customization (logo, accent color, app name) — not a
> theming engine.

## Anchor 1: Admin User Management UI

### User direction (their own words)

> "Before we start building out a bunch of new stuff, I want to slot this
> in: if we didn't already build this out I think we should have a great
> user management UI here. We can do this in LiveView because it's just
> for admin use really. ... My vision of it is like how with Django people
> loved the admin UI — I'm not saying to copy Django at all, but my point
> is that we should have a great out-of-the-box, very full-featured
> experience for developers working with our library as they integrate it
> into their SaaS apps. Of course you can opt out of it but I think by
> default we should have this admin UI enabled unless you opt out. And for
> the admin UI itself it should be a great user experience and very
> idiomatic UI/UX, very user friendly, and addresses all the main pain
> points of other user admin UIs that might come out of the box with some
> of the other authentication libraries out there for other web frameworks.
> So I will want you to research this using subagents — research on the
> web — like what did other ones do right, what is their pain points and
> lessons learned and we'll want to incorporate that into ours.
>
> Also important that it works well on mobile so it should be responsive
> because that way people will be able to manage users from their phones.
> Also important that whatever UI we build out is very UI/UX user friendly,
> great conventions. I guess it should have basic 'branding' customization
> too but nothing crazy because this will be more of an internal tool.
> And it should also work well in light and dark mode so that people
> don't get blinded on their phones at night while using it. And it should
> accomplish the happy path use cases very very well — intuitive — but
> also work well with main error / boundary cases too.
>
> Think deeply on this. Obviously it will be a lot more research and stuff
> to hone it in, but I do want you to slot this in for future development —
> doesn't necessarily have to be RIGHT NOW but as part of this milestone,
> and I want you to earmark all of the right context so that when we pick
> it up (now or later) all my thoughts and direction on that is captured
> so that we're set up for success."

### Non-negotiables

1. **LiveView-based.** Admin-only, not public-facing.
2. **Default ON, opt-out via `--no-admin`.** Reuses the conditional
   template pattern introduced in v1.1 for Organizations.
3. **Mobile-responsive.** Genuinely usable from a phone, not just
   "doesn't crash at 375px". Manage-from-phone is a target use case.
4. **Light + dark mode.** Follows system preference by default, user
   override. Explicit user direction: "so people don't get blinded on
   their phones at night."
5. **Idiomatic Phoenix/LiveView.** No custom design-system buildouts that
   fight Phoenix 1.8 core_components / scopes patterns.
6. **Happy path is delightful, error paths are handled.** Common admin UI
   failures (bulk action half-succeeds, unique constraint race,
   optimistic lock, pagination off-by-one) must surface clearly without
   hiding root cause.
7. **Basic branding customization.** Logo, accent color, app name via
   config struct. NOT a full theming engine — internal tool only.
8. **Security model.** Mount is gated behind host-app `is_admin?/1`
   callback. No default "first user is admin" magic. All destructive
   admin actions require sudo re-auth (leans on Phase 4 work).
9. **Org-aware from day 1.** Built on v1.1 `current_scope.active_organization`.
   Platform admins see cross-org; org admins see their org only.

### Functional scope (first cut)

**User list / search / filter:**
- Table view with column config, sort, search (email, id, name)
- Filter by: confirmed / unconfirmed, MFA enabled / disabled,
  locked / unlocked, provider (OAuth vs password vs passkey),
  deleted / active, registration date range, organization membership
- Bulk actions (with confirm + audit trail): lock, unlock,
  force-logout-all, require-password-reset, soft-delete
- CSV export (respects filters)

**User detail — tabbed:**
- **Profile** — core fields (email, name, created, updated, last-seen,
  locale, tz)
- **Sessions** — all active sessions (device, IP, location, last-active),
  revoke individual or all
- **Security** — MFA status, backup codes regen, enforced-MFA toggle,
  password age, last password change, lockout state, **passkeys list
  with rename/revoke (new in v1.2)**
- **Identities** — connected OAuth providers, unlink with last-method guard
- **API keys** — list PATs with scopes/expiry, revoke
- **Audit log** — per-user audit rows with filtering
- **Organizations** — org memberships, roles, join/leave history
- **Danger zone** — soft-delete, hard-delete, anonymize, reactivate,
  trigger password reset, send magic link on behalf of user,
  **impersonate (new in v1.2)**

**Organization list / detail:**
- List all orgs (platform admin) or own orgs (org admin)
- Org detail: member list, invite management, settings, audit log,
  danger zone (delete org)

**Global dashboard:**
- Signups over time (simple sparkline — not a BI tool)
- Active sessions count
- Failed login / lockout counts (from audit log)
- Recent security events (suspicious logins, MFA enrollments, new
  passkeys, impersonation sessions)

**Branding customization (basic):**
- Logo upload (or URL)
- Accent color (single value, CSS variable)
- App name display
- Configured via host-app config struct, not runtime UI

### Explicitly NOT in v1.2 scope

- Full analytics / BI dashboards — use a real tool
- Role / permission management (authorization is out of Sigra's scope
  already)
- Arbitrary content management (user management, not CMS)
- Custom form builder / field extensions (simple callback-based
  extension point for extra columns is OK)
- Multi-org hierarchy / nested org admin

### UX principles to encode

- **Everything reachable in 2 taps on mobile.** Primary actions (lock,
  reset password, force logout) must not be buried.
- **Destructive actions require explicit confirm + sudo.** Soft-delete
  is default; hard-delete requires typed-confirmation.
- **Optimistic UI where safe, pessimistic UI where risky.** Never claim
  a user is locked when the DB write failed.
- **No dead ends on errors.** Every error screen offers a recovery path.
- **Keyboard-friendly on desktop, touch-friendly on mobile.** Same UI,
  different affordances.
- **Empty states are teaching moments.** First-time load has quickstart
  copy, not just "no users".
- **Respect Phoenix 1.8 scopes.** Admin's `current_scope` clearly
  differs from user scope; mis-scoped actions are impossible by
  construction.

## Anchor 2: Admin Impersonation

### User direction (their own words)

> "Also BTW I forgot — we'll need impersonation if we didn't already add
> that. So yeah, think deeply on this and slot this in for development.
> ... Impersonation (and impersonation and also audit stuff should be
> built into the admin UI). Consider other offerings for the impersonation
> stuff — and audit logging — like from other authentication libs in
> other languages/frameworks. What they did right and what they did wrong,
> pain points and lessons learned. Scan using subagents, research using
> subagents to get all the context that will help you make informed
> decisions about planning out the scope / space for this."

### Security model (non-negotiable)

1. **Strictly admin-only.** Gated by host-app `is_admin?/1` callback.
2. **New session with distinct marker.** Creates a new session record
   with `impersonating_from: admin_id` on the session (or a parallel
   `impersonation_sessions` table — decide in discuss-phase).
3. **Scope extension.** `current_scope.impersonating_from: admin_id`
   field added to `%Scope{}` (v1.1 already extended it for orgs).
4. **Always-visible banner.** Non-dismissable UI banner shows "You are
   impersonating alice@example.com — [End session]". Rendered in layout,
   not in individual templates, so it cannot be missed.
5. **Time-limited.** Shorter absolute timeout than a normal session
   (default 30 min, configurable). Idle timeout also shorter.
6. **Non-nestable.** Admin impersonating user cannot initiate another
   impersonation. Attempt returns explicit error.
7. **Locked-down actions.** While impersonating:
   - Cannot change password of impersonated user
   - Cannot enable/disable MFA on impersonated user
   - Cannot create/revoke API keys as the user
   - Cannot add/remove passkeys on the user
   - Cannot delete the user's account
   - These are enforced at the plug/context layer, not just UI
8. **Dual-actor audit trail.** Every audit row generated during
   impersonation carries BOTH `actor_id` (the real admin) and an
   `effective_user_id` field (the impersonated user). Audit queries can
   surface either view. Audit row `action` gets a `:impersonated`
   suffix or metadata flag.
9. **Org-scoped for org admins.** Platform-admin can impersonate any
   user. Org-admin can only impersonate users within their org. Scope
   is enforced at the impersonation-initiate plug.
10. **Revocable at any time.** End-session button always available.
    Admin's original session is unaffected — they return to it
    immediately.

### Scope

**New library modules:**
- `Sigra.Impersonation` — start/end impersonation, scope checks
- `Sigra.Plug.ForbidDuringImpersonation` — denies sensitive ops
- `Sigra.Plug.ImpersonationBanner` — assigns banner data to conn

**Audit integration:**
- Audit schema gains `effective_user_id` field (nullable — null for
  non-impersonation rows)
- Migration: add column, backfill null
- `Sigra.Audit.query/1` gains `:effective_user_id` and
  `:impersonation_only` filters

**Admin UI integration:**
- "Impersonate" button on user detail Danger Zone (gated, sudo-required,
  typed-confirmation)
- Impersonation session list in admin dashboard
- Per-user audit view shows impersonation sessions as distinct rows

### NOT in v1.2 scope

- Pre-approval workflow (impersonation-needs-second-admin-approval) —
  defer to v1.3 if demand surfaces
- Impersonation reason capture (required text field explaining why) —
  consider for v1.3
- Time-windowed impersonation (approved for next N minutes only) — defer
- Read-only impersonation mode (cannot write anything) — defer; current
  model is write-allowed-except-security

## Anchor 3: Expanded Audit Views

### User direction

> "And audit stuff should be built into the admin UI."

Audit infrastructure already exists (v1.0 Phase 9, mature query API).
v1.2 adds the **views** that expose it to the admin operator.

### Scope

- **Per-user audit log** — all actions by or on a specific user, with
  filtering, date range, action filter, CSV export
- **Per-organization audit log** — all actions within an org (leans on
  `:organization_id` metadata filter added in v1.1)
- **Global audit log** — platform admin only, all actions
- **Impersonation audit view** — all impersonation sessions, who
  impersonated whom, when, what actions were taken during the session
- **Security event feed** — pre-filtered view: failed logins, lockouts,
  suspicious logins, password changes, MFA changes, new passkeys,
  impersonation
- **Search + filter** — by action, outcome, date range, actor, target,
  organization, effective user
- **CSV export** — respects current filters, background job via Oban for
  large exports

### Integration with v1.0 audit infra

- Reuses `Sigra.Audit.query/1` composable query DSL
- Reuses `Sigra.Audit.list/2` cursor pagination (default 50, max 500)
- Adds `:effective_user_id` filter (new from impersonation)
- Adds `:impersonation_only` filter (new)
- Already has `:organization_id` filter (added in v1.1)

### NOT in v1.2 scope

- SIEM integration / log forwarding — document the pattern but don't
  ship an adapter
- Real-time audit log streaming via LiveView subscription — defer
- Audit log retention / archival policies — host app concern
- Audit row immutability enforcement beyond what PG already provides

## Research assignments for v1.2

When v1.2 `/gsd-new-milestone` runs, the research phase MUST be enabled.
Four parallel researchers:

### STACK.md researcher
- Phoenix 1.8 `core_components.ex` dark mode primitives — do they ship
  any, or do we bring our own tokens?
- daisyUI vs Tailwind `dark:` class patterns for dark mode — which fits
  Phoenix 1.8 defaults?
- Any new Elixir libraries for admin UI scaffolding (LiveDashboard
  adjacent?) that shifted since v1.0 research
- CSV export libraries for Elixir — any changes?

### FEATURES.md researcher — deep web research

**Beloved admin UIs — what they do right, what users complain about:**

- **Django admin** — category-defining "beloved by developers" admin. Why
  is it loved? What do people say it still gets wrong in 2026? Mobile?
  Bulk actions? Custom views?
- **Rails ecosystem:**
  - ActiveAdmin — classic, extensive, users complain about learning curve
  - Administrate — Thoughtbot's modern take, what's praised/missed
  - Avo — modern paid alternative
  - Rails + Trestle, RailsAdmin, Motor Admin — compare
- **PHP ecosystem:**
  - **Filament (Laravel)** — widely admired for UX. Deep dive: form
    builders, table builders, widgets, mobile responsive, dark mode,
    notifications. What makes it loved?
  - Laravel Nova (paid) — what's the commercial benchmark?
  - Backpack for Laravel — community-driven alternative
- **SaaS admin tools:**
  - Retool — what do they do for mobile? Row actions? Bulk actions?
  - Forest Admin — what auto-generates well vs poorly?
- **Phoenix / Elixir native:**
  - **Phoenix LiveDashboard** — native Phoenix precedent for admin-style
    LiveView. Tone, patterns, dark mode, mobile. Must-read for v1.2.
  - **Kaffy** — generic Phoenix admin; what's lacking for auth-specific
    admin?
  - **Torch** — Phoenix admin generator; compare approach
- **Auth-specific dashboards (CRITICAL):**
  - **Clerk** — user management UI; benchmark for modern auth admin
  - **Auth0** — mature enterprise dashboard; lessons learned
  - **WorkOS** — enterprise-focused, widely studied
  - **Supabase Studio** — user management tab specifically. Dark mode,
    responsive, open source — closest comparator in pattern
- **Top 5 recurring complaints across all of these** — prioritize
  avoiding these in our own implementation

**Impersonation — study real implementations:**
- **Laravel Nova impersonation** — default UX, security model
- **Rails `pretender` gem** — approach, security model
- **Rails `devise-masquerade`** — approach, security model
- **Django `django-hijack`** — approach, security model
- **Clerk impersonation** — the modern SaaS bar
- **Auth0 impersonation** — enterprise bar, lessons on deprecation
  (Auth0 removed/changed impersonation — learn why)
- **Known CVEs in impersonation features** — there are several worth
  studying; most are around forgetting to audit, session confusion, or
  failing to lock down sensitive ops during the impersonated session

**Audit view UX — how to present audit data without overwhelming:**
- Datadog Security Events UX
- Linear activity feed patterns
- GitHub audit log (for organizations)
- Auth0 logs UI
- What's the right density? Color coding? Grouping?
- How do pros handle "100k events over last week" queries without
  crashing the browser?

### ARCHITECTURE.md researcher — integration into Sigra

- Admin mount path — default `/admin`, host-configurable
- Admin LiveView layout vs host app layout — isolation or shared?
- How does `current_scope.impersonating_from` propagate through every
  layer (plug, LiveView mount, audit helper, template rendering)?
- Banner rendering — root layout assign, LiveView hook, or flash?
- Branding config struct shape — compile-time or runtime?
- Where does the admin UI live re: the lib+generator hybrid? Likely:
  layout + LiveView modules in the library so they auto-upgrade; only
  the admin router mount + `is_admin?/1` callback module get generated
  into the host app. Confirm during discuss-phase.
- Mobile breakpoint strategy — Tailwind defaults or custom?
- Dark mode storage — `localStorage`, cookie, or user preference column?

### PITFALLS.md researcher — failures and CVEs

**Admin UI pitfalls:**
- "First user is admin" default magic (anti-pattern, document why we
  don't do it)
- Privilege escalation via admin panel
- CSRF on destructive actions
- Mass action UIs without dry-run / preview
- Audit log tampering from the admin panel itself
- XSS via user-controlled display names rendered in admin tables

**Impersonation pitfalls (critical):**
- Forgotten audit rows (most common)
- Session confusion leading to admin actions attributed to target user
- Ability to escalate impersonated user's privileges while impersonating
- Leaving sensitive ops unlocked (password change, MFA change)
- Impersonation banner dismissable / hideable
- Nested impersonation enabled by accident
- Impersonation not time-limited
- Cross-org leakage (org admin impersonates user from different org)
- Known CVEs in impersonation features — last 5 years

**Dark mode pitfalls:**
- FOUC (flash of unstyled content) on first load
- User preference not persisting
- Inconsistent contrast on destructive buttons
- Accessibility regressions in dark mode

## Open questions for v1.2 discuss-phase

0. **Packaging: single package vs `sigra_admin` separate package in a monorepo?** User flagged 2026-04-11: "we might want to do a monorepo with a sigra_admin package or something separately." Explore during v1.2 kickoff. Tradeoffs:
   - **Single package (`sigra` bundles admin UI behind `--no-admin` flag):** Simpler DX — one dep, one version. Matches v1.1 conditional-template pattern. Users who don't want admin UI pay nothing at runtime because the LiveViews are only loaded when mounted; library code is inert. Downside: non-admin users still download admin template files (~KBs) and the library dep graph includes any admin-specific deps (none currently identified).
   - **Separate `sigra_admin` package (monorepo with `sigra` + `sigra_admin` + `sigra_orgs`?):** Clean dep boundary — apps that don't need admin never pull it. Matches how e.g. `oban` ships `oban_web` separately. Admin-specific deps (potential: heavier JS libs for charts, CSV streaming, rich filters) live isolated. Downside: release coordination across packages, version skew risk, two hex.pm releases per change that touches both, docs split across two projects.
   - **Recommendation pending research:** lean toward single package with conditional templates unless v1.2 admin UI grows admin-only runtime deps worth isolating. Monorepo question is orthogonal to package boundary — a monorepo can ship a single `sigra` package. Revisit after v1.2 research pass surfaces the admin UI's actual dep footprint.

1. **Admin mount path** — default `/admin`? Configurable? Per-org?
2. **Admin layout** — separate from host layout, or shared? Separate is
   cleaner for dark mode but duplicates layout code.
3. **`is_admin?/1` callback location** — host app module (generated) or
   library behaviour?
4. **"First admin" bootstrap** — document the iex one-liner, or
   generate a `mix sigra.promote_admin` task?
5. **Hybrid question (admin UI templates in lib vs generator)** —
   likely answer: layout + LiveView modules in the library so they
   auto-upgrade; only router mount + `is_admin?/1` module in host app.
   Confirm during discuss-phase.
6. **Dark mode implementation** — daisyUI theme switching, Tailwind
   `dark:` classes, or custom CSS variables? Depends on what Phoenix
   1.8 core_components ships.
7. **Branding config shape** — compile-time config struct, runtime
   DB-stored settings, or both?
8. **Impersonation session storage** — reuse `sessions` table with a
   marker column, or separate `impersonation_sessions` table?
9. **Impersonation duration default** — 30 min? 1 hour? Configurable
   but need a sensible default.
10. **Audit view pagination strategy** — cursor (current) is fine for
    default, but CSV export needs different handling.

## Estimated phase count

v1.2 is roughly **6-8 phases** (bigger than v1.1 because it's all UI +
integration work):

- Admin UI scaffold (router mount, layout, is_admin? callback, base
  LiveView, dark mode toggle, branding config)
- Admin user list + search + filter + bulk actions
- Admin user detail tabs (profile, sessions, security, identities,
  API keys, orgs) — reading + basic actions
- Admin user detail danger zone + destructive actions (sudo-gated)
- Admin organization list/detail/member management
- Admin impersonation (start, banner, locked-down ops, audit dual-actor)
- Admin audit views (per-user, per-org, global, security feed, CSV export)
- Admin UI polish (mobile responsive pass, dark mode pass, empty states,
  error paths)
