## Phases

### v1.21 — active (Phases **91–96**)

**Coverage:** 7 requirements → 6 phases. Numbering continues from **v1.20** (last phase **90**); `--reset-phase-numbers` not used.

**Dependency shape:** three legs that may run in parallel and converge at milestone close:

- **Leg 1 — B2B trust** (Phases **91**, **92**, **93**). Phase **92** (RBAC seams) lands the `Sigra.Authz` behaviour and `:role` scope-struct field that the M2M path in Phase **93** consumes for `actor_type` discrimination, so **93 depends on 92**. **91 (org MFA enforcement)** is independent of 92/93.
- **Leg 2 — Production hardening** (Phases **94**, **95**). Both are independent of Leg 1 and of each other; **94 (Postgres-only declaration)** narrows the migration surface that **95 (`mix sigra.doctor`)** enumerates, so 95 reads cleaner if 94 lands first, but the legs do not block each other.
- **Leg 3 — OAuth + API polish** (Phase **96**). Independent of Legs 1 and 2. Bundles **HARD-03** (OAuth refresh dispatch) and **API-01** (rate-limit headers) because both touch the dual-mode auth plug + OAuth callback area.

No phase blocks the milestone close on a separate launch / monitoring leg — v1.20 already shipped that.

## Phase Details

### Phase 91: Org-level MFA enforcement (B2B-01)

**Goal:** B2B customers can require MFA for every member of an organization with a single admin toggle, with non-MFA members blocked at the request boundary until enrollment, and the policy change recorded as an atomic audit row co-fated with the schema write. After this phase, an org admin's "all members must MFA" policy is enforced consistently across session, API, and LiveView surfaces without host code changes.

**Depends on:** Nothing (parallel-ready with Phases 92–96).

**Requirements:** B2B-01.

**Success criteria** (what must be TRUE):

1. An org admin opening the generated host's `OrganizationSettingsLive` page sees an "Require MFA for all members" toggle gated to the admin role; flipping it persists `enforce_mfa_for_members: true` on the `Organization` row and emits exactly one `organization.mfa_policy_change` audit row whose `inserted_at` is in the same `Repo.transaction/1` boundary as the org write (no orphan audit rows on rollback under fault injection).
2. An existing member of that org who does not have `mfa_enabled: true` issuing a request to any route plugged with `Sigra.Plug.RequireOrgMfa` is redirected to the MFA enrollment page and cannot reach the protected route until enrolled; an org member who is MFA-enrolled passes through unchanged; a member of a non-enforced org is unaffected.
3. A maintainer running `mix phx.new` + `mix sigra.install` on a fresh host (with the `--organizations` feature on) finds the `enforce_mfa_for_members` migration generated, the LiveView toggle wired into `OrganizationSettingsLive`, and `Sigra.Plug.RequireOrgMfa` enumerated in the generated auth pipeline so no host code edit is needed to opt in.
4. A reviewer running the `test/example/test/example_web/integration/` suite sees a generator-host integration test that flips the toggle as an admin, then issues a request as a non-MFA member from the same browser session and asserts the enrollment redirect; the same test asserts the audit row exists.
5. `91-VERIFICATION.md` records the merge gate outcome — full library suite green, generator-host integration green, golden-diff for the new template stable — and notes that no new `log_safe/3` debt was introduced (the new audit row uses `Sigra.Audit.log_multi_safe/3` per `AUDIT-ATOMICITY-DEFAULTS.md`).

**Plans:** 7/7 plans complete

### Phase 92: RBAC seams (B2B-02)

**Goal:** Hosts can implement opinionated role-based access control on top of Sigra's organizations without reverse-engineering scope structs or forking the library, while Sigra itself ships zero opinionated roles. After this phase, the path from "I want owner / admin / member" to working enforcement is one schema field plus one `Sigra.Authz` impl plus a documented recipe — and the library remains role-agnostic.

**Depends on:** Nothing (parallel-ready with Phases 91, 93–96). Phase 93 depends on 92 for the `:role` and `actor_type` scope-struct fields.

**Requirements:** B2B-02.

**Success criteria** (what must be TRUE):

1. A maintainer running `mix phx.new` + `mix sigra.install` on a fresh host finds: a nullable `role :string` column on the generated `organization_memberships` table; a generated `MyApp.Authz` module implementing the `Sigra.Authz` behaviour with a no-op `can?/3` returning `true` for everything; the `Sigra.Authz` module path wired into the host config so callers can swap implementations without library changes.
2. A developer reading `current_scope` inside a LiveView, controller, or worker context sees a populated `:role` field whenever the scope is org-active and the membership row carries a role; the field is `nil` (not absent, not crashing) when the membership has no role or the scope is not org-active.
3. A developer following `guides/recipes/role-based-access-control.md` end-to-end can implement a three-role model (owner / admin / member) with deny-by-default semantics by editing only their own `Authz` module and migration — no library code changes, no Sigra dep upgrade required, no fork. The recipe compiles clean against `mix docs --warnings-as-errors`.
4. A reviewer running `test/sigra/install/golden_diff_test.exs` against the extended `Authz` template sees stable golden output; running the new `test/sigra/authz_test.exs` exercises the behaviour contract (callback shape + scope-struct propagation) without depending on any specific role taxonomy.
5. `92-VERIFICATION.md` records the merge gate outcome and explicitly attests that the library ships no opinionated roles (no `:owner`, `:admin`, `:member` constants in `lib/sigra/`); the recipe is the only place those names appear, and only as illustrative.

**Plans:** 4 plans.

Plans:
- [x] `92-01-PLAN.md` — De-opinionate the library RBAC seams and add the `Sigra.Authz` behaviour.
- [x] `92-02-PLAN.md` — Emit host-owned authz/default scope contracts and nullable membership-role generator output.
- [x] `92-03-PLAN.md` — Propagate `current_scope.role` only through shared org-enrichment seams with parity coverage.
- [x] `92-04-PLAN.md` — Add the RBAC recipe and close golden/docs/authz verification gates.

### Phase 93: M2M / service-account tokens (B2B-03)

**Goal:** Org admins can mint org-scoped service-account tokens that authenticate API calls via the `client_credentials` grant on Sigra's existing JWT path, with the resulting requests cleanly distinguishable from user-tied tokens in `current_scope` and audit rows. After this phase, hosts no longer need to mint user-tied PATs / JWTs for internal APIs / scheduled jobs / third-party integrations, and revoking a service account is a single admin action that breaks the class of tokens cleanly.

**Depends on:** Phase 92 (consumes the `actor_type`-aware scope-struct extension; the `Sigra.Authz` behaviour must already be in place so service-account requests can be `can?/3`-checked the same way user requests are).

**Requirements:** B2B-03.

**Success criteria** (what must be TRUE):

1. An org admin opening the generated service-accounts admin LiveView can: create a new service account with a name + scope list, see the token displayed exactly once at creation (never readable again), see the service account in the org's list view with status / created-by / last-used columns, and revoke a service account such that `revoked_at` is set and the token immediately stops authenticating.
2. An external caller issuing `POST /oauth/token` with `grant_type=client_credentials` + valid client credentials receives a JWT bound to the service account; calling a protected API endpoint with `Authorization: Bearer <jwt>` succeeds, and `current_scope.actor_type` reads `:service_account` (not `:user`) inside the controller / LiveView. The same JWT after revocation produces a 401 with `api.token_verify.failure` audit row whose actor type is `:service_account`.
3. A reviewer querying audit rows for a service-account-issued request sees `service_account.create` / `service_account.revoke` rows for lifecycle events and `api.token_verify` rows extended with the actor-type discriminator; every audit row uses `Sigra.Audit.log_multi_safe/3` (no `log_safe/3` debt added).
4. A maintainer running the `test/example/test/example_web/integration/` suite sees a generated-host E2E that issues a service-account token, calls a protected endpoint successfully, revokes the service account, and asserts the next call fails — including the audit-row assertions on both halves.
5. `93-VERIFICATION.md` records: full library suite + generator-host E2E green, golden-diff stable for the new template set, JWT path test coverage exercises both `:user` and `:service_account` actor types, and the dual-mode auth plug remains the single entry point (no parallel auth pipeline introduced).

**Plans:** 6/6 plans complete

- [x] `93-02-PLAN.md` — Lock JWT, FetchBearer, membership, and org-MFA service-account parity on the existing dual-mode auth path.
- [x] `93-03-PLAN.md` — Enforce generator gating and add direct `/oauth/token` controller coverage for the generated/example token surface.

### Phase 94: Postgres-only declaration (HARD-01)

After this phase, the install task refuses non-Postgres adapters with a clear remediation message, and the conditional `if adapter == :mysql` / `:sqlite` branches that were placeholders are removed.

**Depends on:** Nothing (parallel-ready with Phases 91–93, 95, 96).

**Requirements:** HARD-01.

**Success criteria** (what must be TRUE):

1. A developer running `mix sigra.install` against a host whose `Repo` adapter is `Ecto.Adapters.MyXQL` or `Ecto.Adapters.SQLite3` is rejected at generator pre-flight with a single-paragraph error naming the adapter found, naming PostgreSQL as the only supported adapter, and pointing at the relevant docs section — no template files written, no migration emitted.
2. A maintainer running `rg "if .*adapter.* == .*:mysql" priv/templates/ lib/mix/tasks/sigra.install.ex lib/sigra/install/` and the `:sqlite` equivalent finds zero hits; the conditional branches that were emitting placeholder DDL are gone, and the templates compile cleanly against the Postgres-only path.
3. A reader opening `mix.exs` (`description:`), `README.md`, `.planning/PROJECT.md` Constraints section, and `guides/introduction/getting-started.md` finds consistent language naming PostgreSQL as the supported adapter; `CHANGELOG.md` `[Unreleased]` carries the trace bullet calling out the removal explicitly so adopters reading release notes know this is a documented narrowing, not a regression.
4. A reviewer running the new regression test (`test/sigra/install/postgres_only_test.exs` or equivalent) sees the install task refused against a fake `MyXQL` adapter config and accepted against `Postgres`; the `install_smoke` CI job remains green against Postgres.
5. `94-VERIFICATION.md` records the merge gate outcome including: zero remaining adapter-conditional branches in templates, the trace bullet committed to `CHANGELOG.md` `[Unreleased]`, and the explicit MySQL / SQLite Out-of-Scope row in `REQUIREMENTS.md` matches the language now in PROJECT.md / README.

### Phase 95: Optional-dep boot-validation + `mix sigra.doctor` (HARD-02)

**Goal:** Optional dependencies (Oban for async email, Bcrypt for legacy hash migration, EQRCode for TOTP QR rendering) fail loudly and actionably when absent at the moment Sigra needs them, instead of compiling to silent `nil` and producing dead workers in production. After this phase, an adopter running `mix sigra.doctor` gets a per-feature dep matrix with remediation hints, and a missing optional dep at first use raises a tagged error that names both the feature and the dep — not a `FunctionClauseError` or `UndefinedFunctionError`.

**Depends on:** Nothing (parallel-ready with Phases 91–94, 96).

**Requirements:** HARD-02.

**Success criteria** (what must be TRUE):

1. A developer running `mix sigra.doctor` against a generated host sees a table with one row per optional feature (`:async_email`, `:bcrypt_migration`, `:totp_qr`, plus any others surfaced from `Sigra.OptionalDeps`); each row reads OK or MISSING with the dep name and a one-line remediation hint (e.g. `add {:oban, "~> 2.21"} to mix.exs`); the task exits 0 if all required features are OK, non-zero otherwise.
2. A developer running a host without `:oban` and triggering a password-reset email sees a clear, actionable error at the call site (e.g. `Sigra.OptionalDeps.MissingDependencyError: feature :async_email requires {:oban, "~> 2.21"} but it is not loaded`) instead of silent nil; the same applies for Bcrypt-on-bcrypt-hash-login and EQRCode-on-TOTP-enroll.
3. A reader of the generated host's compile output sees a compile-time warning (not silent) when the install flag set implies a required dep is missing — e.g. `--api` without `:joken` warns at compile, not at first request.
4. A reviewer running the optional-dep CI matrix sees three jobs (Oban-absent / Bcrypt-absent / EQRCode-absent) each toggling that dep off via `mix.exs` and asserting the raise-on-missing path fires with the expected error tag — none silently passes by skipping the relevant code.
5. `95-VERIFICATION.md` records the merge gate outcome plus the `MAINTAINING.md` "Diagnosing first-run issues" row pointing at `mix sigra.doctor`; `lib/sigra/optional_deps.ex` is the single source of truth for the feature → dep mapping (verified via grep — no scattered `Code.ensure_loaded?` guards left in workers).

**Plans:** 1/4 plans executed

### Phase 96: OAuth refresh + rate-limit headers (HARD-03 + API-01)

**Goal:** Two narrow, paired API-surface gaps close together because they sit on the same dual-mode auth plug + OAuth callback area: OAuth token refresh works for the four non-Google providers Sigra ships strategies for (GitHub, Apple, Facebook, Generic), and API responses on rate-limited paths carry the standard `X-RateLimit-*` + `Retry-After` headers so clients can backoff correctly. After this phase, hosts using GitHub / Apple / Facebook / Generic OAuth do not silently drop refresh tokens, and API consumers on rate-limited routes get the metadata they need to behave.

**Depends on:** Nothing (parallel-ready with Phases 91–95).

**Requirements:** HARD-03, API-01.

**Success criteria** (what must be TRUE):

1. A developer running `mix test test/sigra/oauth/refresh_test.exs` on Postgres sees per-provider passing tests (GitHub / Apple / Facebook / Generic) using Assent's test mode + recorded fixture cassettes; each test exercises a valid refresh, a refresh-token rotation when the provider returns a new one, and the appropriate failure mode (e.g. revoked refresh) — no live provider calls in CI.
2. A maintainer running `rg "not yet implemented" lib/sigra/oauth.ex lib/sigra/oauth/` finds zero hits; the warning at the previous `lib/sigra/oauth.ex:174` site is replaced by per-provider dispatch, and `Sigra.OAuth.refresh_token/2` returns a typed result for each of GitHub / Apple / Facebook / Generic. Each successful refresh writes one `oauth.token_refreshed` audit row co-fated with the stored-token rotation under `Sigra.Audit.log_multi_safe/3` (no orphan audit rows on rollback).
3. An API client issuing a request to a rate-limited route (e.g. `/api/auth/login`) and being rate-limited receives a 429 response carrying `X-RateLimit-Limit`, `X-RateLimit-Remaining: 0`, `X-RateLimit-Reset` (epoch seconds), and `Retry-After` (RFC 7231 seconds-or-HTTP-date); a successful request below the limit carries the same headers minus `Retry-After`, with `Remaining` reflecting the post-decrement value from Hammer's state.
4. A reviewer running the new `test/sigra/plug/rate_limit_headers_test.exs` plug-unit suite plus the e2e against the example app's rate-limited endpoint sees both the under-limit and over-limit shapes asserted; the plug is wired into the dual-mode auth pipeline in `priv/templates/sigra.install/core/auth_plug_pipeline.ex` so generated hosts get headers without manual config.
5. `96-VERIFICATION.md` records the merge gate outcome including: per-provider OAuth refresh tests green on Postgres, the dropped warning verified by grep, the audit-atomicity check confirms `oauth.token_refreshed` uses `Multi + log_multi_safe`, and the rate-limit-headers e2e against the example app proves the headers reach the wire.
