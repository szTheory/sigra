## Problem

`doc/llms.txt` is a tracked, committed documentation index. Its content is fully derived —
regenerated byte-for-byte by `mix docs` — from `mix.exs`'s `@version` and the set of public
modules carrying `@moduledoc`. It drifts out of sync with the source tree along two
independent, already-measured axes (`237-RESEARCH.md` §B.2b, re-confirmed by plan `237-01`'s
regeneration this phase):

**Drift shape 1 — version header.** The file's first line hardcodes the release version
(`# Sigra vX.Y.Z - Table of Contents`). Every `mix.exs` `@version` bump — which happens on
every release, including the routine patch cut Phase 242 performs for `1.5.1` — leaves this
line stale until someone manually re-runs `mix docs` and commits the result.

**Drift shape 2 — missing module rows.** The index is a flat list of one row per public
module with a `@moduledoc`. Adding a new public module (as PR #238 did for
`Sigra.Branding.Contrast`, which this phase's plan `237-01` found the committed index missing
entirely) leaves the index incomplete until the same manual regenerate-and-commit step runs.

**Why this matters.** SC-1 of this phase (`237-CONTEXT.md` D-05) requires a fresh `git clone`
to report a clean `git status`. That is true **only as long as nobody runs `mix docs`** — and
running `mix docs` is exactly what a maintainer does when touching documentation, and exactly
what this phase's own gate (Task 3, `MIX_ENV=test mix ci` plus a documentation build) checks
at every future HEAD. This phase (via plan `237-01`, D-05) regenerated and committed
`doc/llms.txt` at `v1.5.0` to make the clean-tree property true **at this HEAD**. That fix is
deliberately temporary: the moment `mix.exs`'s `@version` next changes — Phase 242 cuts
`1.5.1` — or the moment a new public module ships, the identical condition this phase just
fixed recreates itself. There is no committed mechanism that catches this before it ships.

## Solution

The durable fix is a **build-then-compare drift check**: in CI (or as a release-lane step),
run `mix docs`, then assert `git diff --exit-code -- doc/llms.txt` is clean. If it is not, the
committed index is stale relative to the code that is about to ship, and the check should
fail loudly rather than let the drift land silently — the same "found-while-cleaning becomes
a todo, never an in-phase fix" boundary this phase's other findings observe.

This belongs with the **release-lane phase that cuts the next patch version** — Phase 242
(`Hex Retire + Docs Revert + Pinned-Install ADR + Cut 1.5.1`, per the v1.48 phase map in
`.planning/STATE.md`), since that is the first point in the roadmap where `mix.exs`'s
`@version` changes again and the drift shape would otherwise silently recreate itself on the
very release this phase's own D-05 fix was meant to protect.

This todo records the observation and the recommended mechanism; it does not build the check
itself — that is out of this phase's scope per its own phase-boundary fence (`237-CONTEXT.md`,
"Phase-boundary fences (do not drift into these)": "A `doc/llms.txt` staleness drift check →
todo, lands with Phase 242's release lane").
