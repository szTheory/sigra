## Findings

### Blockers

**1. [task_completeness] The source proof must cover and persist both exact comparison arms and the selected prerequisite repairs before the PR #368 update.**

- **Plan:** `256-02`, Task 1.
- **Evidence:** The action at lines 82–84 says to check the selected prerequisite repairs and both measured source closures. The only environment-check command at line 89 passes the candidate ref. The production checker accepts one `--source` SHA and reads only the action, workflow, and helper blobs; it checks the helper hash, helper calls, callers, and runner pin, but not the unnamed prerequisite repairs or the candidate/control treatment. Its result is printed to stdout, and the command does not save it to the planned `.planning/execution/256/SOURCE-CHECK.json`. The predecessor `SOURCE-CHECK-RECHECK-01.json` covers earlier commits, not the new Phase 256 candidate.
- **Why this blocks execution:** The approved comparison depends on a frozen common-repair set and a separate candidate treatment. Without a current, reviewable check for both source roles and the exact repairs, execution cannot establish that it is publishing and measuring the authorized comparison.
- **Specific correction:** Name the selected repair files/identities in the scope, then run checks against the exact Phase 256 candidate and control commits and persist both results plus the symmetric/common-versus-candidate diff proof in `SOURCE-CHECK.json` before authorizing the PR update.

**2. [scope_sanity] Each plan must stay below the 15-file blocker threshold.**

- **Plan:** `256-02`.
- **Evidence:** Its `files_modified` list has 16 paths (lines 7–23), above the plan-checker contract's 15+ blocker threshold. It also combines source freezing, proposal/authority creation, one-shot hosted preparation, independent verification, and terminal diagnostics.
- **Specific correction:** Split the offline source/proposal work from the one-shot preparation into dependency-ordered plans, or otherwise reduce the actual files and work owned by this plan while preserving the single authorization and one-shot boundary.

### Warnings

**1. [scope_sanity] Plan 03 exceeds the 10-file warning threshold.**

- **Plan:** `256-03`.
- **Evidence:** Its `files_modified` list has 11 paths (lines 7–18), spanning proposal authorization, collection, observation, replay, and report artifacts.
- **Specific correction:** Consider separating terminal replay/report packaging from collection so each plan has a smaller file and task surface.

**2. [scope_sanity] The phase's calibrated estimates total about 77% of the 100,000-token budget.**

- **Plans:** `256-01`, `256-02`, `256-03`.
- **Evidence:** Calibrated estimates are 28,772 + 25,176 + 23,018 = 76,966 tokens. Each plan is individually below budget and the estimate confidence is high (six calibration samples), but the phase total is above the approximately 70% warning threshold.
- **Specific correction:** Reduce or narrow the work that must share an execution context, especially the large source/authority and measurement plans, while retaining the authorized scope.

**3. [key_links_planned] The replay package's staged path and digest are not checked by an automated step.**

- **Plan:** `256-03`, Task 3.
- **Evidence:** The package command writes `.planning/execution/256-input-package.tar.gz` (line 139), while replay consumes `.planning/execution/256/replay/input-package.tar.gz` (line 141). The action at line 130 asks to copy and verify the SHA-256 read-back, but no `<automated>` command verifies that copy before replay. The package helper constructs `INPUTS.json` inside the tar archive; it does not create the listed worktree path `.planning/execution/256/replay/INPUTS.json`.
- **Specific correction:** Add a deterministic staging/read-back check that proves the durable package bytes equal the validated temporary package, and either create the listed `replay/INPUTS.json` artifact or remove it from the declared outputs if the embedded manifest is the intended artifact.
