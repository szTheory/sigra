<objective>
Build the cheap pre-clock gate that would have caught the 253-97 defect before the window opened: an offline dry-run of the full canary scenario sequence against a local fake GitHub. Use it to fix, RED-first, the two driver defects that need a second invocation or a failure to show (repeated preflight, unrecorded halt) and the two timing assumptions it exposes. Zero GitHub requests.

Today's harness cannot do this. ci-hosted-transport.py routes only Git object routes (and production-kind collectors) to a hermetic local origin. Every other canary route (rate_limit, rules, check runs, workflow, dispatch, runs, jobs, artifacts, downloads, cancel) requires a live allocation. So no test ever ran ci-gate-canary.sh past --publish-only.

Defects fixed here (found while planning R8 from the code; none observed live, because 253-97 stopped first):
- repeated preflight: the preflight block runs on every invocation, so full-pass plus --remaining-scenarios issues about ten preflight-category requests against a frozen maximum of 8, and hydrate_effective_checks requires exactly one check_runs transaction;
- fail-open halt marking: api_get returns the transport's nonzero status instead of calling fail, so set -e exits without marking the evidence halted (the committed R7 evidence has no status and no diagnostics);
- discovery race: the script lists runs immediately after a dispatch with a single charged listing;
- first poll: watch_run polls immediately, so the first poll per run is wasted against the 18-poll category.

What the gate covers: the frozen driver's route mapping and control flow, transport validation and per-category accounting, ledger/receipt/evidence shapes, approval and allocation binding (synthetic stand-ins in the clone), ref names and dispatch inputs from the freeze, and that the real verifier accepts the shapes the script writes. What it does not cover: real GitHub latency and eventual consistency beyond the modeled delays, the real presence of check runs on the decided commit, real authentication and rate limits, real fixture-workflow runtimes and artifact contents (modeled from 253-LOAD-RECOVERY-CANARY-WORKFLOW.yml and the verifier's rules), and anything after the canary (the PR families have their own hermetic suite in ci-pr-proof.test.sh).

Purpose: 253-102 runs it against the R8 freeze identity; 253-104 runs it as a pre-clock gate before Jon's approval.
</objective>
