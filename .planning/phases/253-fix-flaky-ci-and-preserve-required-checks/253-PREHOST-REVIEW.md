## Critical Issues

### CR-01: Registration evidence verification trusts self-reported claims

**Classification:** BLOCKER  
**Priority:** P1 — false acceptance evidence  
**Location:** `scripts/ci/ci-registration-repro.sh:46-58`  
**Category:** Evidence integrity / gate correctness  
**Exploit/failure:** A caller can pass a JSON file with the expected schema and truthy values for the six `controls.*` fields, and `--verify-controls` exits 0 without checking a test result, trace, report hash, source identity, or run record. `--verify-acceptance` likewise accepts any three projects with allowed `originalOutcome` strings; for example, it accepts `status: "not_reproduced"` with three failed projects and no reports. A fabricated or incomplete evidence file can therefore be presented as passing the registration controls or acceptance verifier. The adjacent test at `scripts/ci/ci-registration-repro.test.sh:26-29` invokes each mode only with `--help`, so it never tests those claims.
**Reachability:** Local operator or automation that invokes the verifier on an evidence file.  
**Impact:** A required CI readiness or reproduction control could be marked satisfied without having run.  
**Fix:** Make verifier modes validate evidence generated by the runner: require and hash-check the expected native report, trace and logs; bind their paths and hashes to the frozen source and project; verify actual statuses and run counts; require all projects to have passed before accepting `not_reproduced`; and add negative fixtures that invoke both verifier modes with forged booleans, missing artifacts, failed results, and mismatched identities.
