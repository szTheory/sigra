**The roadmap's SC-4 wording — "documentation attribute ranges in `lib/` are clean starting with
the audit module" — is stale, and D-01 is what this plan is graded against.** The measured surface
is 348 token occurrences across 259 sites in 71 files, of which only 4 are dead planning-directory
references. The other ~344 are benign phase mentions in prose and belong to the later ratchet
phase, which the roadmap already defines as a monotonic-decrease mechanism where zero is explicitly
not the target. Plan 237-06 records the measured baseline so that ratchet has a number to start
from. Attempting 71 files here would produce low-care prose edits across a shipped auth library's
public documentation.

**CONTEXT.md abbreviates the golden-fixture mix task's path.** The tracked path is
`lib/mix/tasks/sigra.fixture.rebless_golden.ex`; both D-01 line references point into that file.
The abbreviation is a shorthand, not a second file.

**The check is a phase artifact, not repository tooling (D-04).** It lives in the phase directory,
is not picked up by any workflow glob, and is deliberately NOT a durable guard — the durable
ratchet belongs to the later phase. It is committed so the RED/GREEN demonstration is reproducible
rather than a claim in a summary.

**Every scope fence in this plan is taken against `origin/main`, never a revisionless `git diff`.**
A revisionless diff reports unstaged changes only, so the moment a task commits, the fence passes on
empty output and stops meaning anything. That is the same class of defect as a guard on a literal
that occurs zero times.

**The check tolerates deleted lines that carry a bookkeeping token, by design.** A line that both
names a bookkeeping token and mentions a class word is precisely the rewrite case; the check's job
is to catch deletions of lines that carry ONLY the class word. That tolerance is why the second
fixture exists: it pins the tolerated case so a later reader can see the boundary was chosen, not
stumbled into.

Write `237-security-comment-diff-check.sh` in the phase directory. It takes one argument: a path to
a unified-diff file, or a `-` meaning read the diff from standard input. It reports, and exits
non-zero on, any REMOVED line that mentions the rationale class but carries no bookkeeping token.

The pipeline is given in RESEARCH §F.4 and should be followed rather than reinvented: select removed
lines, discard the diff's own file-header lines, keep those matching the case-insensitive word-class
alternation `security|CSRF|enumeration|timing|scope|impersonation`, then discard any line that also
carries a bookkeeping token (a decision id, a success-criterion id, a phase mention, or a
planning-directory path) — because those are the rewrite cases, which are reviewed rather than
blocked. Any line surviving all four filters is printed with a clear failure banner and forces a
non-zero exit. Zero surviving lines exits zero and prints, on its own line and in exactly this
machine-readable grammar, how many removed lines it examined:

    examined_removed_lines=<N>

Downstream verification asserts that N is non-zero, so a pass that examined nothing is mechanically
impossible rather than merely discouraged.

Guard the script against the failure mode it exists to prevent: make it exit non-zero if the input
is empty or unreadable, so "no findings" can never be produced by "no input". Implement that guard
for BOTH input modes — read stdin fully into a variable or temp file first and reject it when empty,
not just when a file argument is zero-length. The real run in Task 3 uses stdin, so a guard that
only inspects a file argument leaves the evidence-producing path unprotected, and empty stdin is
exactly what a mis-quoted or mis-ranged `git diff` produces.

Then commit TWO fixture diffs under the phase's `fixtures/` directory and demonstrate both
directions:

form — and not only on an empty file argument. That is the channel the real evidence run uses.
