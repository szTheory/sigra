<objective>
Make six local-only stashes durable on `origin`, retire five stale worktree admin records, and only
then empty the local stash list — with the drop gated behind an explicit decision checkpoint.

Purpose: REPO-03. Stashes are ordinary commit objects that exist nowhere but this machine. Once the
local list is emptied they are reachable only through the reflog, and this milestone forbids the
garbage-collection commands that would otherwise finish them off. The whole value of this plan is
the ORDER: preserve, prove preserved, then drop.

Output: a committed snapshot of all twelve SHAs, six archive refs on `origin`, one worktree entry,
and an empty stash list.
</objective>

<planner_decisions_closed_here>
**The archive ref namespace is a free choice, and it is fixed here as `refs/stash-archive/<date>/stash-N`.**
No existing convention was found on `origin` — the only safety-ish refs there today are three
ordinary branches. Fixing the namespace in the plan rather than leaving it to execution is what
makes the `git ls-remote` count assertion writable in advance.

**Two safety refs named by the roadmap's later branch-prune phase are NOT on `origin` today.** That
is recorded as a note for Phase 245 and is explicitly out of scope here — this plan creates only
the six stash archive refs.

**The archive table is the machine-readable contract; everything else in the snapshot file is for
humans.** `git worktree list --porcelain` emits bare 40-hex SHAs into the same file, so any check
that harvests 40-hex strings from the document at large cannot distinguish a stash SHA from a
worktree HEAD — measured on this repository: 6 such porcelain lines, 5 of them resolvable non-stash
SHAs, which is enough to clear an `at least 6` count with five stashes destroyed. Hence the fixed
`ARCHIVE-ROW|` grammar, an exact-6 comparison, and no `at least` anywhere in this plan.

**This plan's remote queries are ref-scoped, not diff-scoped, so the moving-tip problem does not
apply to them.** They ask the remote for one named ref at a time and compare a recorded SHA; a
sibling phase merging to the default branch cannot perturb that. The `merge-base` discipline used by
the diff-based fences elsewhere in this phase is therefore not needed here.

**The remote assertion is primary; the local one is recorded but near-tautological.** With garbage
collection prohibited, `git cat-file -e` on a dropped stash still succeeds via the reflog. What
REPO-03 actually claims is that the commits are refs on `origin` pointing at the recorded SHAs, so
that is what is asserted SHA-for-SHA, before and after the drop.

**This plan runs LAST among the working plans (wave 4).** Its assertions are about global mutable
state — `git worktree list` holding exactly one entry, and the stash list — which any concurrent
worktree-based dispatch would make unsatisfiable. Sequencing it after the file-editing plans costs
nothing and removes the race.

**Resolvability is asserted twice, and the second time is what counts.** Checking `git cat-file -e`
before the drop proves only that a local object exists. The assertion that matters runs AFTER the
stash list is emptied.
</planner_decisions_closed_here>

As each ref is pushed, append a machine-parseable row to the snapshot file under a heading

    ARCHIVE-ROW|<stash index 0-5>|<40-hex commit SHA>|<full ref path pushed>

Every field is mandatory and is validated against a strict grammar before any comparison runs:
index is a single digit 0-5, SHA is exactly 40 lowercase hex characters, ref begins with

not a row that happens to match — `git ls-remote` on a ref that does not exist exits 0 with EMPTY
output, so an empty recorded SHA compared against an empty remote answer scores as a match and six
such rows make total failure indistinguishable from total success. The grammar assertion and an
explicit non-empty test on the remote's answer are what close that hole; neither may be dropped.

Six rows, one per stash. This table — not free prose, and not the raw porcelain dumps elsewhere in
the same file — is the machine-readable contract Task 3 reads. It matters because
`git worktree list --porcelain` also emits bare 40-hex SHAs into this same file, so a check that
harvests every 40-hex string in the document cannot tell a stash SHA from a worktree HEAD.

Then confirm the push landed by querying the remote, not by trusting the push output, and confirm it
SHA-for-SHA: for each row, the SHA the remote reports for that exact ref must equal the SHA in the
row. "Six refs exist" is a weaker claim than REPO-03 makes — six refs could exist while pointing
somewhere else entirely. Include a positive control in the same evidence — a remote query returning
a known non-empty result — so the match is not a claim about a query that never ran.

Do NOT drop or clear any stash in this task. Do NOT delete any branch. Do NOT run any
garbage-collection, reflog-expiry or prune-now command.
