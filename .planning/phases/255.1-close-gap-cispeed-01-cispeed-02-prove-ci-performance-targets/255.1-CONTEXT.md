## Implementation Decisions

### Reference and honest claim
- **D-01:** Adopt the user-approved repaired-control amendment. Construct control and candidate from one common repaired source, retaining the selected Phase 254 speed optimizations only in the candidate. Publish the exact common patches and treatment diff, source/producer/workflow identities and file digests before collection. Historical source remains recoverable; never relabel the repaired control as the unchanged historical baseline.
- **D-02:** Apply necessary connection-handoff reliability fixes, actual ordinary/scaffold/dependency-off test execution, equivalent diagnostics, registry/package transport and runner checks symmetrically. Include their real timing cost. The complete candidate must contain current Phase 255 behavior; the earlier successful candidate run does not establish final-source performance. Demonstrating a Socket race does not prove which event initiated the original hosted failure.
- **D-03:** Keep CISPEED-01/02 open until this new comparison passes. A later pass closes the amended requirements with an explicit reference to this amendment; it does not rewrite the original comparison or automatically complete Phase 254 verification. The exact-original-source route is not logically impossible, but has no demonstrated successful full execution and is not the selected default.

### Feasibility before measured work
- **D-04:** First run deterministic local checks for clean source materialization, common versus treatment patches, producer/workflow/application origin, trigger/merge-tree feasibility, actual test identities, expected exclusions/skips and cache keys. No hosted measurement should be planned around an assumed runnable source or unavailable input. Record `ready` or `blocked` with the specific missing prerequisite.
- **D-05:** Close the hosted library-report retention gap before measuring: supply persistent receiver output and upload/validate actual ordinary, scaffold and dependency-off reports, seeds and executed test identities on both sides. `ci-mix-receivers.py` currently defaults to a temporary directory it deletes, while CI uploads legacy timing paths. A green alias or test count alone does not prove equal useful work. Compare browser case/project identities and statuses too; distinguish setup rows from product cases. Counts such as 108 browser rows are historical observations, not an immutable replacement for current identity-based checks.
- **D-06:** Prove cache preparation for the actual PR event/ref scheme. PR-created caches generally cannot warm sibling PRs. Record exact versus fallback restores, matched keys/scope and the six workload owners' actual conditions. Preserve runtime/environment/port compiled-cache isolation, `npm ci` and browser OS dependencies. Match actual runner image/OS/architecture per owner within each pair; a runner label does not pin the historical image build.

### Proposed finite scope; execution authority remains separate
- **D-07:** Planning should use an upper bound of four full-workload preparatory invocations, two per side, within two hours, with no automatic preparation retry/replenishment. The first prepares and the second checks warm readiness. This is a proposal, not permission to spend runs. If all-warm fresh PRs cannot be achieved within it, stop and record the precise cache/trigger constraint before acceptance. Do not silently add per-PR warmups.
- **D-08:** Plan a separate new allocation of 20 matched successful pairs / 40 primary real-PR families in one 48-hour window, all warm. Freeze identities, family registrations, a seeded balanced order (10 control-first, 10 candidate-first), cache/image rules, maximum pair gap, timeout/request limits and window-start rule before the first measured family. Nearby sequential executions within each pair are the default. Do not update a PR during its family or let superseding cancellation manufacture replacement observations.
- **D-09:** Propose at most one independently diagnosed infrastructure retry total across the new comparison, retained inside its original family with the original wait origin and both attempts' cost. Product-test failures receive no acceptance retry. No replacement families, window extension, outlier deletion or automatic budget renewal. Stop with `insufficient_data` once 20 valid successful pairs are impossible. Development/parser/fixture repairs use scoped maintenance and meaningful local tests, not numbered successor repair plans.
- **D-10:** Reuse existing bounded acquisition/origin verification. Freeze per-stage request and mutation ceilings in the execution plan; retain the existing ceiling of 600 HTTP requests per acquisition pass / 60 minutes, counting retrieval, retries and watcher requests. Check REST core before a watch; stop at <=250 and honor 403/429 reset/retry time. One watcher per run, 60-second interval, one structured terminal summary, failed logs only for a failed conclusion. No live preparation, CI dispatch, evidence publication or measurement is authorized by this context.

### What gets timed and calculated
- **D-11:** Use real `pull_request` families for contributor waiting time: run `created_at` through the last successful completion of every applicable required check, bound to source/run/attempt/job. Record head/base/merge/application/workflow identities and branch-rule provenance. Whole-workflow completion includes unrelated trailing jobs; rerun `run_started_at` can omit queue delay. Neither substitutes for the required-result endpoint. Keep retry delay inside the family wait.
- **D-12:** Keep the three thresholds: ordinary candidate median <=0.8 times control median; nearest-rank candidate p95 <=control p95 (19th sorted observation at n=20); and non-increasing actual runner seconds per comparable PR. Sum unique physical jobs across all attempts, including failed/cancelled work and post-check execution, without double counting partial reruns. With equal family counts, summed cost compares per-PR mean cost; disclose preparation cost separately. Unknown durations or unbound checks invalidate a result rather than becoming zero.
- **D-13:** Twenty valid pairs satisfying every threshold means pass; twenty with a numerical miss means miss; fewer valid pairs or missing comparability means insufficient data. Preserve all observed outcomes and costs. Pair ratios/deltas and order effects are diagnostics, not replacement estimators. The empirical p95 describes this sample; it is not a guarantee about future slow PRs.
- **D-14:** Retain raw permitted inputs, origins, identities, calculation version and offline replay for this new experiment. Keep Phase 255's pinned historical replay unchanged. Add narrow checks for stale same-name checks, wrong merge/source, cache fallback, missing duration, first-attempt failure followed by success and partial-rerun job deduplication before depending on collection.

### Contributor experience and security
- **D-15:** Preserve `MIX_ENV=test mix ci`, all actual test receivers, the five isolated browser owners, one worker, zero browser retries, role/stable selectors and LiveView readiness without sleeps. Retain required names and failure/cancellation/missing/unexpected-skip controls. Keep registration and authorization behavior under test; authenticated shortcuts cannot replace it.
- **D-16:** Reuse small existing Python/shell/Node helpers and native Mix/Ecto tasks. No new dependency, benchmark service, orchestration framework or image migration is justified. Use read-only measurement job credentials, separate orchestration authority and safe source-bound artifact handling. Never upload auth storage, tokens, environment dumps or raw auth-bearing traces; never execute untrusted PR code with privileged credentials.

### Agent's Discretion
Choose helper structure, targeted regression cases, source materialization, balanced scheduling seed and exact finite pair-gap/request limits during planning. Verify that existing keys can actually serve the proposed warm-cache design. If execution feasibility fails, record the blocker and smallest corrective step; do not redefine the baseline, weaken coverage, change thresholds or spend additional allowances silently.

### Folded Todos
None. Existing database-isolation and gate/manifest concerns are inputs to current invariants, not authority for a new migration. Keyword-only todo matches remain outside scope and unchanged.
