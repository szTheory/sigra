**When to use:** Before hosted preparation. A different SHA is expected only where the declared treatment necessarily changes source; document separate application/workflow/workload identities.  
**Example:** Existing `ci-run-metrics.sh` source preflight/bundle interfaces and comparison tests are the local pattern. Add a deterministic dry-run that asserts common patch equality and treatment-only diff; do not run hosted actions in this gate. `[VERIFIED: scripts/ci/ci-run-metrics.sh:1-100]`

### Pattern 2: Producer-owned durable test evidence

**What:** Write each test suite's report to a persistent invocation directory, upload it with run/attempt identity, and validate report digest and producer metadata before comparing test identity/status.  
**When to use:** Every control and candidate full-workload family.  
**Current boundary:** `ci-mix-receivers.py` creates a `TemporaryDirectory` when `SIGRA_CI_RECEIVER_OUTPUT` is missing and calls `temporary.cleanup()` after each standalone leg (`scripts/ci/ci-mix-receivers.py:90-135`). **Implementation guidance:** Add a persistent run/attempt-bound receiver output and upload/validate ordinary, scaffold, and dep-off reports; fail closed when expected files or test identities are missing. ### Pattern 3: Compare only verified real PR families

**What:** Bind PR creation timestamp to the final successful applicable required check; bind each check to run, attempt, merge/source/head/base, workflow, and actual job. Calculate wait from original PR run `created_at`; retain retry delay and all attempt job costs.  
**When to use:** Acceptance families and offline replay.  
**Example:** Existing hosted verifier requires a unique PR with registered PR number/head/base and exact attempt jobs, then validates required check job binding and success (`scripts/ci/ci-hosted-gate-verify.py:1870-1944`). `[VERIFIED: scripts/ci/ci-hosted-gate-verify.py:1870-1944]` Its comparison-family origin is a useful start but needs narrowly scoped coverage for stale same-name checks, wrong merge/source, missing duration and partial-rerun de-duplication.

## Common Pitfalls

### Pitfall 1: Calling different-PR cache entries warm

**What goes wrong:** Preparation on one PR looks green, but the measured control/candidate PR restores no exact cache or only a broader fallback.  
**Why it happens:** GitHub PR caches are associated with `refs/pull/.../merge`; official docs say those caches can be restored only by reruns of that PR, not the base or sibling PRs. Existing workflow uses `pull_request` and cache keys have restore prefixes.  
**How to avoid:** Inspect every current workload owner/key and its actual reported `cache-hit`, restore key/scope, OS/runtime dimensions. Test the exact planned PR refs locally where possible; do not call a restore-prefix fallback an exact warm hit. Consider existing base-scope reusable caches only if safe and demonstrated.  
**Warning signs:** `cache-hit=false`, any fallback restore, different lock/tool/runtime/image identity, or only the prep PR has the cache.

### Pitfall 2: Treating native completion as complete test evidence

**What goes wrong:** A successful `mix ci` is accepted despite missing or ephemeral report files for one receiver.  
**Why it happens:** Standalone `ci-mix-receivers.py leg` defaults to a temporary directory and removes it; workflow uploads legacy timing paths and warns if absent.  
**How to avoid:** Persist all three reports under invocation output, upload with run/attempt binding, require files and complete test identity/status coverage, and compare actual test work between sides.  
**Warning signs:** Temporary output default; `if-no-files-found: warn`; a report that only covers ordinary plus dep-off guard, not scaffold.

### Pitfall 3: Equating workflow end or rerun start with required-result wait

**What goes wrong:** The wait excludes initial queue time or includes irrelevant trailing work.  
**Why it happens:** Full workflow has optional/trailing jobs; `run_started_at` for a rerun is not the original request origin. GitHub `pull_request` uses a merge ref, so a same-name check from an obsolete merge/source is not equivalent.  
**How to avoid:** Use original event run `created_at` to last successful completion of every frozen applicable required context, each bound to exact run/attempt/job and PR head/base/merge. Preserve attempted failures and retry delay.  
**Warning signs:** `updated_at`, whole workflow conclusion, run-attempt start, check name without SHA/job binding.

### Pitfall 4: Counting rerun jobs twice or losing their cost

**What goes wrong:** Partial rerun jobs are duplicated or failed/cancelled attempt cost disappears.  
**Why it happens:** Physical jobs persist across attempts but the API returns attempt-scoped job lists.  
**How to avoid:** Store raw job receipts by attempt; deduplicate unique physical job IDs for cost, preserve per-attempt outcomes and fail if a required duration is unknown. Use only one watcher per run and retain the original origin on the one allowed infra retry.  
**Warning signs:** Sum of job IDs has duplicates across attempt response, absent timestamp treated as zero, failures filtered out of cost.

### Pitfall 5: Treating proposed ceilings as authorization

**What goes wrong:** Planning writes become permission to consume hosted runs or publish evidence.  
**Why it happens:** Context contains precise proposed budgets (four preparation invocations; 40 primary families) but explicitly states collection is unauthorized.  
**How to avoid:** Finish local gates and scoped plan first. Preparation and primary measurement are separate future authorized actions. Stop at `insufficient_data` once 20 valid pairs are impossible; no replacements, extensions or budget renewal.

## Security Domain

Use read-only measurement credentials for acquisition; keep any orchestration authority separate. PR code is untrusted: do not use privileged credentials in its execution context, do not upload auth state, tokens, environment dumps or raw auth-bearing traces, and verify producer run/attempt/digest before accepting artifacts. GitHub documentation warns that base caches may be readable by PR workflows and specifically describes cache poisoning risks for low-trust triggers; do not put credentials in cache paths. `[CITED: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching]` `[CITED: https://docs.github.com/en/actions/reference/security/secure-use]`

| Threat | Mitigation |
|---|---|
| PR artifact claims its own origin | Verify API producer run/attempt/head and artifact digest via `ci-hosted-gate-verify.py`. |
| Cache poisoning or sensitive cache disclosure | Keep untrusted code from privileged cache writes; cache no secret or auth material; retain safe scope. |
| Wrong/stale required check accepted | Require exact source, run/attempt and job binding for every frozen check context. |
| Untrusted PR code sees orchestration credentials | Separate collection credentials and code execution; use read-only collection authority. |
