# Phase 246.2: Close gaps: APP-04 and APP-05 — generated refresh and revocation surfaces - Context

**Gathered:** 2026-08-16 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the v1.49 audit gaps by making the already-generated app-session refresh and owner-constrained one/all revocation facades reachable through secure generated-host routes and controllers. This phase completes the generated HTTP delivery contract for APP-04 and APP-05; it does not add new session lifecycle semantics, device listing, a new management UI, or any PWA, native, Crosswake, Electron, or admin capability.

</domain>

<decisions>
## Implementation Decisions

### Refresh HTTP boundary
- **D-01:** Expose refresh as a public JSON `POST` beside the existing generated `/api/app-login` routes. Accept only a `refresh_token` request field and delegate directly to `Auth.AppSessions.refresh/1`.
- **D-02:** Refresh must not require browser authentication, an access token, or `FetchAppSession`. An expired access credential must not prevent a client from presenting its refresh credential, and refresh credentials must never be accepted as ordinary request authentication.

### Refresh responses and abuse controls
- **D-03:** Successful refresh returns the same bounded credential shape as hosted/direct exchange: `access_token`, `refresh_token`, `family_id`, and `expires_in`. Replacement credentials are returned only after the library transaction commits.
- **D-04:** Malformed transport receives a bounded request error. Invalid, expired, reused, and internal lifecycle failures collapse to a bounded unauthenticated refresh failure rather than revealing credential state. Keep refresh on a generated rate-limited public credential pipeline.

### User-owned revocation
- **D-05:** Generate JSON consumers for revoking one app-session family and all of the current user's app-session families. Derive the owner exclusively from `conn.assigns.current_scope.user`; request data may identify a family but never an owning user.
- **D-06:** Protect both revocation mutations with the established browser, authenticated-Scope, recent-authentication, and CSRF boundary used by sensitive generated self-service operations.
- **D-07:** This closure exposes the existing one/all mutations only. Do not add device/session listing, a new management page, admin/operator controls, or new library lifecycle APIs.

### Deterministic closure evidence
- **D-08:** Extend generated source contracts and a disposable fresh-host HTTP proof to cover routed refresh rotation, consumed-refresh replay family revocation, one-family owner isolation, all-family revocation, and denial on the next access authentication.
- **D-09:** Proof remains automation-first: use real generated routes and PostgreSQL state, deterministic barriers where concurrency matters, no sleeps or human UAT, and no raw credential values in retained diagnostics or receipts.

### the agent's Discretion
- Exact route names beneath the locked `/api/app-login` refresh boundary and authenticated `/users` revocation boundary.
- Exact controller/module factoring, HTTP status codes, and bounded JSON error identifiers, provided all failure classes and secrecy rules above hold.
- Whether refresh reuses the existing `:app_login_public` limiter or receives a dedicated generated limiter, provided it is bounded and deterministically tested.
- The narrowest extension of the existing generated-host proof harness that produces truthful current-HEAD evidence.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Auth.AppSessions.refresh/1`, `revoke_family/2`, and `revoke_all/1` already provide the thin generated facade; this phase needs consumers rather than new lifecycle logic.
- `Sigra.AppSession` already owns locked refresh classification, every-use rotation, reuse-family revocation, and owner-constrained one/all revocation.
- `AppLoginController` already implements strict body-field extraction and bounded JSON responses for public app credential ceremonies.
- Generated PAT management provides the closest browser-authenticated/recent-authenticated/CSRF mutation pattern.

### Established Patterns
- Security-critical state transitions stay in the library while generated controllers and routes remain thin host-owned delivery code.
- Public credential endpoints are rate-limited and return bounded JSON failures; sensitive browser mutations derive the actor from current Scope.
- Generated-host claims require real routed compile/runtime evidence; template-string assertions are supporting evidence only.

### Integration Points
- Add refresh routing and controller handling to the existing app-login generated templates.
- Add authenticated one/all revocation routes and controller actions without creating a device-listing dependency.
- Extend installer source tests and the Phase 246 disposable-host proof to exercise the new routes through committed PostgreSQL state.

</code_context>

<specifics>
## Specific Ideas

- Treat refresh as credential exchange, not as access-token-authenticated API traffic.
- Preserve the same success credential vocabulary across hosted exchange, direct login, and refresh so generated clients do not need ceremony-specific parsing.
- Keep revocation deliberately mutation-only in this closure; a device inventory would be a separate capability rather than an accidental prerequisite.

</specifics>

<deferred>
## Deferred Ideas

- Device/session listing and a user-facing device-management page are separate capabilities and are not required to close the audited one/all revocation reachability gap.
- PWA/offline behavior, native clients, Crosswake proof, and Electron contract work remain Phases 247–249.
- Admin/operator app-session management remains outside the v1.49 scope.
