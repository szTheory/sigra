## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Refresh HTTP boundary
- **D-01:** Expose refresh as a public JSON `POST` beside the existing generated `/api/app-login` routes. Accept only a `refresh_token` request field and delegate directly to `Auth.AppSessions.refresh/1`.
- **D-02:** Refresh must not require browser authentication, an access token, or `FetchAppSession`. An expired access credential must not prevent a client from presenting its refresh credential, and refresh credentials must never be accepted as ordinary request authentication.

#### Refresh responses and abuse controls
- **D-03:** Successful refresh returns the same bounded credential shape as hosted/direct exchange: `access_token`, `refresh_token`, `family_id`, and `expires_in`. Replacement credentials are returned only after the library transaction commits.
- **D-04:** Malformed transport receives a bounded request error. Invalid, expired, reused, and internal lifecycle failures collapse to a bounded unauthenticated refresh failure rather than revealing credential state. Keep refresh on a generated rate-limited public credential pipeline.

#### User-owned revocation
- **D-05:** Generate JSON consumers for revoking one app-session family and all of the current user's app-session families. Derive the owner exclusively from `conn.assigns.current_scope.user`; request data may identify a family but never an owning user.
- **D-06:** Protect both revocation mutations with the established browser, authenticated-Scope, recent-authentication, and CSRF boundary used by sensitive generated self-service operations.
- **D-07:** This closure exposes the existing one/all mutations only. Do not add device/session listing, a new management page, admin/operator controls, or new library lifecycle APIs.

#### Deterministic closure evidence
- **D-08:** Extend generated source contracts and a disposable fresh-host HTTP proof to cover routed refresh rotation, consumed-refresh replay family revocation, one-family owner isolation, all-family revocation, and denial on the next access authentication.
- **D-09:** Proof remains automation-first: use real generated routes and PostgreSQL state, deterministic barriers where concurrency matters, no sleeps or human UAT, and no raw credential values in retained diagnostics or receipts.

### the agent's Discretion
- Exact route names beneath the locked `/api/app-login` refresh boundary and authenticated `/users` revocation boundary.
- Exact controller/module factoring, HTTP status codes, and bounded JSON error identifiers, provided all failure classes and secrecy rules above hold.
- Whether refresh reuses the existing `:app_login_public` limiter or receives a dedicated generated limiter, provided it is bounded and deterministically tested.
- The narrowest extension of the existing generated-host proof harness that produces truthful current-HEAD evidence.

### Deferred Ideas (OUT OF SCOPE)
- Device/session listing and a user-facing device-management page are separate capabilities and are not required to close the audited one/all revocation reachability gap.
- PWA/offline behavior, native clients, Crosswake proof, and Electron contract work remain Phases 247–249.
- Admin/operator app-session management remains outside the v1.49 scope.

## Summary

The audited gap is delivery, not lifecycle semantics. `Sigra.AppSession` already implements digest-only issuance, atomic refresh rotation, consumed-refresh family revocation, owner-constrained one-family revocation, all-family revocation, audit co-fate, and subsequent-access denial. The generated `Auth.AppSessions` facade already exposes `refresh/1`, `revoke_family/2`, and `revoke_all/1`, but the generated router and controller expose neither consumer. [VERIFIED: `lib/sigra/app_session.ex`; `priv/templates/sigra.install/app_sessions/auth_app_sessions.ex`; `.planning/v1.49-v1.49-MILESTONE-AUDIT.md`]

Plan two narrowly connected delivery changes: first, add a public, rate-limited JSON refresh action to `AppLoginController` beneath `/api/app-login`, strictly accepting only `refresh_token`; second, add JSON one-family/all-family revocation actions beneath `/users` behind `[:browser, :require_authenticated, :require_sudo]`. Both revocation actions must use `conn.assigns.current_scope.user` exclusively, while Phoenix’s browser pipeline supplies the established CSRF boundary. [VERIFIED: `priv/templates/sigra.install/app_sessions/router_injection.ex`; `priv/templates/sigra.install/app_sessions/app_login_controller.ex`; `lib/sigra/install/features/core.ex`]

**Primary recommendation:** Extend the existing app-login controller/router and the existing disposable generated-host proof; do not create a new lifecycle service, client UI, package, or authentication pipeline.

## Architecture Patterns

### System Architecture Diagram

```text
refresh client JSON POST {refresh_token}
  -> generated /api/app-login refresh route
  -> :api + :app_login_public rate limiter
  -> AppLoginController strict one-field extraction
  -> Auth.AppSessions.refresh/1
  -> Sigra.AppSession locked PostgreSQL transaction
     -> rotated credentials (after commit) -> bounded JSON credential response
     -> invalid/expired/reused/internal -> one bounded unauthenticated JSON failure

browser user POST (CSRF-protected) {family_id?}
  -> generated /users revocation route

  -> Auth.AppSessions.revoke_family/2 | revoke_all/1

  -> next access request -> FetchAppSession -> revoked family denied
```

### Pattern 1: Strict public credential exchange
**What:** Match only `%{"refresh_token" => token}`; require exactly the singleton key list and a binary value; invoke `AppSessions.refresh/1`; return its success map directly only on `{:ok, credentials}`.

**When to use:** The public `/api/app-login` refresh endpoint only.

**Example:**
```elixir
# Source: existing generated exchange action, adapted under locked D-01–D-04
def refresh(conn, %{"refresh_token" => token} = params) do
  with ["refresh_token"] <- Map.keys(params),
       true <- is_binary(token),
       {:ok, credentials} <- AppSessions.refresh(token) do
    json(conn, credentials)
  else
    _ -> json(conn |> put_status(:unauthorized), %{error: "invalid_refresh"})
  end
end
def refresh(conn, _params), do: json(conn |> put_status(:bad_request), %{error: "invalid_request"})
```
The exact bounded error labels/statuses are discretionary, but malformed transport must stay distinguishable only as a request error and lifecycle classes must collapse. [VERIFIED: CONTEXT.md; existing `exchange/2` pattern]

### Pattern 2: Owner-derived sensitive browser mutation
**What:** Read `owner = conn.assigns.current_scope.user`; permit only an opaque family identifier from params; call `AppSessions.revoke_family(owner, family_id)` or `revoke_all(owner)`; never read an owner/user ID from request input.

**When to use:** The two generated `/users` revocation mutations only.

**Example:**
```elixir
# Source: APITokenController ownership pattern and Auth.AppSessions facade
def revoke_family(conn, %{"family_id" => family_id}) do
  owner = conn.assigns.current_scope.user

  case AppSessions.revoke_family(owner, family_id) do
    {:ok, _family} -> json(conn, %{ok: true})
    {:error, :not_found} -> json(conn |> put_status(:not_found), %{error: "not_found"})
    _ -> json(conn |> put_status(:unprocessable_entity), %{error: "revocation_failed"})
  end
end
```
The router, not controller ad-hoc checks, supplies browser authentication, recent-authentication, and CSRF protection. [VERIFIED: `APITokenController`; `core.ex`; CONTEXT.md]

### Anti-Patterns to Avoid

- **Refreshing through `FetchAppSession` or a Bearer access token:** violates D-02 and fails clients whose access credential expired. [VERIFIED: CONTEXT.md]
- **Adding refresh tokens to normal request authentication:** `FetchAppSession` only extracts a Bearer access credential and must remain access-only. [VERIFIED: `fetch_app_session.ex`; CONTEXT.md]
- **Passing `user_id` or owner data from body/path into revocation:** creates an ownership-selection vulnerability; use Scope’s user. [VERIFIED: CONTEXT.md; `app_session.ex`]
- **Reimplementing lifecycle behavior in controller code:** duplicates locked transaction/audit semantics and risks returning raw replacements before commit. [VERIFIED: `app_session.ex`; CONTEXT.md]
- **Adding listing/UI/admin work:** explicitly deferred and not needed for mutation reachability. [VERIFIED: CONTEXT.md]
- **Retaining raw access/refresh credentials in proof diagnostics or receipts:** D-09 forbids it; use response classifications and source hashes. [VERIFIED: CONTEXT.md; runtime harness]

## Common Pitfalls

### Pitfall 1: Treating refresh as an authenticated API call
**What goes wrong:** A client with expired access cannot refresh, or refresh credentials become accepted as ordinary Bearer authentication.
**Why it happens:** Access and refresh are both opaque strings, but their authority differs.
**How to avoid:** Put refresh on public `:api` + rate-limited pipeline only; do not add `FetchAppSession` or browser auth.
**Warning signs:** Route has `:api_authenticated`, `FetchAppSession`, or authorization-header requirements. [VERIFIED: CONTEXT.md; `fetch_app_session.ex`]

### Pitfall 2: Leaking refresh lifecycle state
**What goes wrong:** Invalid, expired, consumed/reused, and infrastructure-failure inputs get distinct external responses.
**Why it happens:** The library exposes precise internal atoms needed for audit/lifecycle behavior.
**How to avoid:** Controller collapses every lifecycle error to one bounded unauthenticated failure; only malformed transport gets a bounded request error.
**Warning signs:** JSON emits `token_expired`, `reuse_detected`, or internal exception details. [VERIFIED: CONTEXT.md; `app_session.ex`]

### Pitfall 3: Losing CSRF/recent-auth protection on JSON mutations
**What goes wrong:** Revocation endpoints are placed beneath an API/public pipeline because they return JSON.
**Why it happens:** Response format is confused with actor/authentication model.
**How to avoid:** JSON response is compatible with `/users` browser pipeline; route both mutations through browser, authenticated Scope, and sudo.
**Warning signs:** Route lacks `:browser`, `:require_authenticated`, or `:require_sudo`. [VERIFIED: CONTEXT.md; `core.ex`]

### Pitfall 4: Proof that calls facade/library directly
**What goes wrong:** Tests pass although generated hosts have no route, controller, injection, or usable CSRF boundary—the exact audit failure.
**Why it happens:** Unit tests are easier than fresh-host routing.
**How to avoid:** Extend existing installer source contracts and the disposable host script; dispatch real HTTP after `mix sigra.install`, migrate, compile, and start.
**Warning signs:** Test invokes `AppSessions.refresh/1` without a generated-host HTTP request. [VERIFIED: milestone audit; runtime harness]
