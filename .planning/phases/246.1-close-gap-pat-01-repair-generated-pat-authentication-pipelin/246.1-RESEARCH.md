## User Constraints (from CONTEXT.md)

### Locked Decisions

### Generated Router Configuration
- **D-01:** The generated `--api` router must pass both required `Sigra.Plug.FetchAPIToken` options: a host runtime configuration function and the host `Scope` module.
- **D-02:** The emitted PAT plug configuration must follow the adjacent generated JWT runtime-configuration pattern rather than capturing a compile-time configuration value.

### Explicit PAT Boundary
- **D-03:** Preserve the Phase 243/244 explicit PAT contract: `FetchAPIToken` remains the generated verifier, accepts only a Bearer PAT, reloads the live user into the host's normal Scope, and stores bounded credential facts in `conn.private[:sigra_auth]`.
- **D-04:** Do not replace the explicit PAT pipeline with `FetchBearer`, token-shape autodetection, or browser-session fallback.

### Fresh-Host Regression Proof
- **D-05:** Extend the existing disposable Phase 244 API-host harness to prove the generated router and `:api_authenticated` pipeline initialize successfully.
- **D-06:** The fresh-host proof must send a real PAT-authenticated request through the emitted router pipeline and assert the resulting normal Scope and bounded PAT credential metadata. A direct `FetchAPIToken.call/2` invocation or router source-string assertion alone is insufficient.
- **D-07:** Keep the proof deterministic and automation-first: generate a disposable host, install twice, migrate, compile, boot or dispatch through the real endpoint, and fail on initialization or authentication regressions without sleeps or human UAT.

### Requirement Reverification Scope
- **D-08:** Re-establish PAT-01 and only the PAT consumer portion of API-01. Preserve existing PAT management, JWT, app-session, and login-ceremony behavior unless a narrowly necessary compatibility adjustment is discovered while repairing the generated pipeline.
- **D-09:** Closure evidence must explicitly reconcile the milestone audit's `FetchAPIToken.init([])` disconfirmation; prior Phase 244 verification is not sufficient evidence for this gap.

- The planner may choose the smallest focused source-contract assertions that complement the runtime proof, but source-text checks cannot substitute for runtime initialization and authentication.

## Summary

This is a narrow generator integration repair. `Sigra.Plug.FetchAPIToken.init/1` fails fast with `Keyword.fetch!` for `:config` and `:scope_module`, but `Sigra.Install.Features.Core.api_injections/3` currently emits `plug Sigra.Plug.FetchAPIToken` with no options. The milestone audit reproduced that exact `FetchAPIToken.init([])` failure and marks PAT-01 unsatisfied and the PAT-consumer portion of API-01 partial. [VERIFIED: codebase inspection — `lib/sigra/plug/fetch_api_token.ex`, `lib/sigra/install/features/core.ex`, `.planning/v1.49-v1.49-MILESTONE-AUDIT.md`]

The production fix belongs only in the generated PAT pipeline: mirror the adjacent JWT emission, using `config: &#{context_module}.sigra_config/0` and `scope_module: #{context_module}.Scope`. This preserves request-time host configuration resolution and leaves `FetchAPIToken` as the explicit Bearer-PAT verifier. The plug already verifies the PAT, reloads the user through the configured repository, builds the normal host Scope, and writes bounded credential facts; it needs no redesign. [VERIFIED: codebase inspection — `lib/sigra/install/features/core.ex`, `lib/sigra/plug/fetch_api_token.ex`, `lib/sigra/plug/credential_auth.ex`]

The decisive regression is not a direct plug call. Phoenix router pipelines run only after a route is found, so the disposable host must contain a temporary routed probe that uses `[:api, :api_authenticated]`, then send an actual endpoint request carrying a newly created PAT. The handler must expose only test-safe evidence sufficient to assert the normal Scope user ID and bounded `:sigra_auth` fields; use an existing innocuous handler or inject a minimal test-only route/controller into the generated host. [CITED: https://hexdocs.pm/phoenix/Phoenix.Router.html] [CITED: https://hexdocs.pm/phoenix/Phoenix.ConnTest.html]

**Primary recommendation:** Make one source-contract correction in `Core.api_injections/3`, then extend the existing serial Phase 244 disposable-host lane with a real routed PAT probe that proves initialization, Scope projection, and bounded credential metadata after install-twice/migrate/compile.

### Anti-Patterns to Avoid

- **Direct plug-only smoke:** It proves plug behavior but not generated option emission, pipeline compile/init, route attachment, or endpoint dispatch. [VERIFIED: milestone audit and context — `.planning/v1.49-v1.49-MILESTONE-AUDIT.md`, `246.1-CONTEXT.md`]
- **Source-string-only closure:** A string assertion can coexist with malformed or non-initializing generated code; retain only as a focused complement to runtime proof. [VERIFIED: `246.1-CONTEXT.md`]
- **New permanent public API probe endpoint:** The required handler is evidence-only; avoid expanding the shipped API surface to test a generator connection. [VERIFIED: phase boundary — `246.1-CONTEXT.md`]
- **Changing PAT lifecycle, JWT, session, or login code:** Those contracts are explicitly closed or deferred. [VERIFIED: `246.1-CONTEXT.md`]

## Common Pitfalls

### Pitfall 1: Proving only the library plug

**What goes wrong:** The current direct `FetchAPIToken.call/2` smoke can pass while `FetchAPIToken.init([])` in generated router compilation raises `KeyError`. [VERIFIED: milestone audit and codebase inspection — `.planning/v1.49-v1.49-MILESTONE-AUDIT.md`, `test/sigra/planning/phase_244_generated_auth_runtime_proof_test.exs`]

**How to avoid:** Add a real route attached to `:api_authenticated`, compile the generated host after two installations, and make an endpoint request before asserting Scope/metadata.

### Pitfall 2: Testing an unmatched path

**What goes wrong:** Router pipelines are not invoked when no route matches, producing a false positive if the probe path is absent. [CITED: https://hexdocs.pm/phoenix/Phoenix.Router.html]

**How to avoid:** Assert `Phoenix.Router.route_info/4` or make the successful endpoint response impossible unless the handler ran; dispatch the exact registered probe path.

### Pitfall 3: Capturing host config at generation/compile time

**What goes wrong:** A generated struct can bind stale or unavailable application configuration and contradicts the locked runtime configuration decision.

**How to avoid:** Emit `config: &#{context_module}.sigra_config/0`, mirroring the JWT pipeline exactly. [VERIFIED: `246.1-CONTEXT.md`, `lib/sigra/install/features/core.ex`]

### Pitfall 4: Leaking raw PATs in proof output

**What goes wrong:** A convenience probe might serialize authorization headers, raw tokens, or unbounded request content.

**How to avoid:** Create the token in setup, send it only as the request header, and return/assert only the bounded `:sigra_auth` facts already defined by `CredentialAuth`. [VERIFIED: `243-CONTEXT.md`, `lib/sigra/plug/credential_auth.ex`]

### Pitfall 5: Treating unavailable Postgres as a skipped proof

**What goes wrong:** The existing harness requires a real database; silently skipping removes the only end-to-end evidence for PAT-01.

**How to avoid:** Retain `require_postgres!/0` and fail with its bounded preflight diagnostic. The current local configured test database at `127.0.0.1:53988` was unreachable during research, so execution needs `tmp/db.env`/test database startup first. [VERIFIED: current focused test command and `test/sigra/planning/phase_244_generated_auth_runtime_proof_test.exs`]
