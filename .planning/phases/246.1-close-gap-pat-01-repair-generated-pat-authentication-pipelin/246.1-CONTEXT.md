# Phase 246.1: Close gap: PAT-01 — repair generated PAT authentication pipeline - Context

**Gathered:** 2026-08-16 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Repair the generated `--api` personal-access-token authentication pipeline disconfirmed by the v1.49 milestone audit. The phase restores initialization and real request authentication through the emitted `:api_authenticated` pipeline, adds deterministic fresh-host regression proof, and re-establishes PAT-01 plus the PAT consumer portion of API-01. It does not reopen PAT management, advanced JWT, opaque app-session, hosted/direct login, or other first-party-client contracts.

</domain>

<decisions>
## Implementation Decisions

### Generated Router Configuration
- **D-01:** The generated `--api` router must pass both required `Sigra.Plug.FetchAPIToken` options: a host runtime configuration function and the host `Scope` module.
- **D-02:** The emitted PAT plug configuration must follow the adjacent generated JWT runtime-configuration pattern rather than capturing a compile-time configuration value.

### Explicit PAT Boundary
- **D-03:** Preserve the Phase 243/244 explicit PAT contract: `FetchAPIToken` remains the generated verifier, accepts only a Bearer PAT, reloads the live user into the host's normal Scope, and stores bounded credential facts in `conn.private[:sigra_auth]`.
- **D-04:** Do not replace the explicit PAT pipeline with `FetchBearer`, token-shape autodetection, or browser-session fallback.

### Fresh-Host Regression Proof
- **D-05:** Extend the existing disposable Phase 244 API-host harness to prove the generated router and `:api_authenticated` pipeline initialize successfully.
- **D-06:** The fresh-host proof must send a real PAT-authenticated request through the emitted router pipeline and assert the resulting normal Scope and bounded PAT credential metadata. A direct `FetchAPIToken.call/2` invocation or router source-string assertion alone is insufficient.
- **D-07:** Keep the proof deterministic and automation-first: generate a disposable host, install twice, migrate, compile, boot or dispatch through the real endpoint, and fail on initialization or authentication regressions without sleeps or human UAT.

### Requirement Reverification Scope
- **D-08:** Re-establish PAT-01 and only the PAT consumer portion of API-01. Preserve existing PAT management, JWT, app-session, and login-ceremony behavior unless a narrowly necessary compatibility adjustment is discovered while repairing the generated pipeline.
- **D-09:** Closure evidence must explicitly reconcile the milestone audit's `FetchAPIToken.init([])` disconfirmation; prior Phase 244 verification is not sufficient evidence for this gap.

### the agent's Discretion
- Exact test endpoint, generated-host handler, helper names, and internal test factoring may follow existing Sigra conventions, provided the test traverses the real emitted router pipeline and proves the locked authentication boundary above.
- The planner may choose the smallest focused source-contract assertions that complement the runtime proof, but source-text checks cannot substitute for runtime initialization and authentication.

</decisions>

## Existing Code Insights

### Reusable Assets
- `Sigra.Plug.FetchAPIToken` already implements Bearer extraction, PAT verification, live-user reload, normal Scope projection, and bounded `:sigra_auth` metadata; the library plug does not need redesign.
- The generated `FetchJWT` pipeline in `Sigra.Install.Features.Core` already demonstrates the required runtime config-function and Scope-module option shape.
- `Sigra.Planning.Phase244GeneratedAuthRuntimeProofTest` already provides disposable host generation, repeated installation, migration, compilation, PAT creation, and focused generated-host test execution.

### Established Patterns
- Security-critical verification remains library-owned; the generator emits host-owned router configuration with explicit dependency injection.
- Generated-host truth requires real fresh-host runtime evidence. Direct plug tests and source-string assertions are supporting checks, not end-to-end proof.
- Authentication success projects the current live user into the host's normal Scope while credential facts remain bounded and separate in `conn.private[:sigra_auth]`.

### Integration Points
- `Sigra.Install.Features.Core.api_injections/3` emits the broken `:api_authenticated` pipeline and is the narrow production repair seam.
- `Sigra.Plug.FetchAPIToken.init/1` is the fail-fast boundary that currently raises because generated options are absent.
- `test/sigra/planning/phase_244_generated_auth_runtime_proof_test.exs` is the primary regression-evidence seam for generated router initialization and real PAT-authenticated dispatch.

</code_context>
