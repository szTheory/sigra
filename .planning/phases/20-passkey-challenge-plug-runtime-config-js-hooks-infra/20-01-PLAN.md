`issue/4` should mirror the OAuth request-side session pattern: generate the ceremony challenge with `Registration.new_challenge/2` or `Authentication.new_challenge/2`, sign `%{"c" => challenge_b64}` with `Sigra.Token.generate(secret_key_base, "sigra-passkey-challenge", payload, max_age: 60)`, and store only `%{"token" => signed_token}` in the matching Plug session slot.

`verify/5` should mirror the OAuth callback-side single-use flow: fetch the matching session slot only, verify the signed token with `max_age: 60`, rebuild the exact `Wax.Challenge` from the signed payload and current config, invoke the callback with that `Wax.Challenge`, and `delete_session/2` only when the callback returns `{:ok, result}`.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Plug session | Untrusted browser input crosses into the session-backed challenge verification edge |
| Plug edge → passkey primitives | The Plug adapter must hand only a server-authoritative `Wax.Challenge` into Phase 19 verification modules |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-01 | S | `Sigra.Plug.PasskeyChallenge.verify/5` | mitigate | Verify only the signed session token with purpose `sigra-passkey-challenge`; never trust browser-supplied challenge authority |
| T-20-02 | T | Plug session slot storage | mitigate | Keep ceremony-specific slots and single-use delete-on-success semantics to block replay and cross-ceremony tampering |
| T-20-03 | R | challenge consumption path | mitigate | Preserve the slot on callback error so failures are auditable/reproducible instead of silently replacing challenge state |
| T-20-04 | D | session-backed challenge issuance | accept | 60-second TTL intentionally bounds replay window; broader ceremony flood defense lands in Plan 20-02 per PK-10 |
</threat_model>
