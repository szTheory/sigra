## Info

### IN-01: `audit_migration_timestamp` clamps to `:59` and can collide with the primary migration

**File:** `lib/mix/tasks/sigra.install.ex:607-620`
**Issue:** `api_token_timestamp` and `audit_migration_timestamp` use `min(ss + 1, 59)` / `min(ss + 2, 59)`. When the current `ss` is 58 or 59, both offsets clamp to `59`, so the main migration timestamp, api_token timestamp, and audit timestamp can all equal the same second, defeating the intended ordering. Probability is low (~3% window) but the fix is trivial.
**Fix:** Use `rem(ss + n, 60)` and carry into minutes, or simply add one to the base minute when `ss + n > 59`. Alternatively, generate all three timestamps from a single base time and increment with modular arithmetic.

### IN-02: `pad/1` uses binary construction that breaks for values > 9

**File:** `lib/mix/tasks/sigra.install.ex:722-723`
**Issue:** `defp pad(i) when i < 10, do: <<?0, ?0 + i>>` is a micro-optimization that produces the correct two-byte result, but the adjacent `defp pad(i), do: to_string(i)` is only correct for values ≤ 99. Months (1-12), days (1-31), hours (0-23), minutes/seconds (0-59) are all in range so this is currently safe, but the asymmetric implementation is a readability wart and a footgun if the helper is ever reused for 3-digit values.
**Fix:** Replace both clauses with `defp pad(i), do: String.pad_leading(to_string(i), 2, "0")`.

### IN-03: `reset_user_password/2` legacy clause bypasses `Sigra.Auth` security telemetry

**File:** `priv/templates/sigra.install/auth.ex:427-436`
**Issue:** The legacy `reset_user_password(%User{}, attrs)` clause runs its own `Ecto.Multi` rather than delegating to `Sigra.Auth.reset_password/4`, so it misses audit log entries (`auth.password_reset_complete`), telemetry events (`[:sigra, :reset, :completed]`), and HMAC signature rewind that the signed-token path provides. The reset_password_controller template (line 61) still calls this legacy clause with a user struct.
**Fix:** Either route the controller through the signed-token clause (requires passing the token, not the user), or document that the legacy clause is for tests only and route controller flows through the signed-token path. At minimum, add a `@doc false` marker and a comment pointing at the signed-token replacement.

### IN-04: Drift-guard test relies on runtime `File.cwd!` which may differ under umbrella/nested test runs

**File:** `test/sigra/templates/installer_drift_test.exs:229-230`
**Issue:** `Path.expand(@fixture.template, File.cwd!())` resolves paths relative to the current working directory. If the test is invoked from an umbrella app or a different working directory (e.g., `mix test` run from a subdir), the fixture paths will not resolve. Other template tests in this PR use `Path.expand("../../../priv/templates/...", __DIR__)` which is directory-independent and more robust.
**Fix:** Switch to `Path.expand(@fixture.template, Path.expand("../../..", __DIR__))` or similar `__DIR__`-anchored resolution for parity with the other template tests.

### IN-05: `confirm_user_by_code` missing `:secret_key_base` is not required by library but template passes it

**File:** `priv/templates/sigra.install/auth.ex:316-323`
**Issue:** The template passes `secret_key_base:` to `Sigra.Auth.verify_confirmation_code/3`, but the library function does not read that key (verified against `lib/sigra/auth.ex:712-803`). Harmless today, but creates an implicit coupling — if a reader looks at the template first, they may assume the secret is used in code verification.
**Fix:** Remove the `secret_key_base:` line from this call site; it is noise. Keep it only where actually consumed (link verification, reset tokens).

### IN-06: `handle_event("validate", ...)` auto-submit path in `confirmation_live.ex` uses `send(self(), ...)` race

**File:** `priv/templates/sigra.install/confirmation_live.ex:122-130`
**Issue:** On each keystroke, if `code` is exactly 6 digits, a `{:auto_confirm, code}` message is sent to `self()`. If the user types a 7th character quickly, the pending message is still in the mailbox and fires with a stale 6-digit prefix once the handler runs. The rate limiter will catch the extra attempt, but it wastes an attempt against the `:max_code_attempts` counter (default 5).
**Fix:** Guard against repeat sends by tracking an `auto_submit_pending?` assign, or handle the auto-submit directly inside `handle_event("validate", ...)` rather than dispatching via the mailbox. Alternatively, debounce with a 200-300 ms timer.
