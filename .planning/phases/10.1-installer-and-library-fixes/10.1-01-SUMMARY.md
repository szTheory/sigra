# Phase 10.1 Plan 01: Fix Plain-Map Insert in request_password_reset & request_magic_link — Summary

One-liner: Closed AR-10-01/AR-10-02 by making `Sigra.Auth.request_password_reset/3` and `Sigra.Auth.request_magic_link/3` build proper `%UserToken{}` structs via `struct!(user_token_schema, attrs)` with a struct-matching stub-repo regression test that kills the latent DoS bug.

## What Was Built

Two latent denial-of-service bugs were sitting in `lib/sigra/auth.ex`:

1. `request_password_reset/3` built a plain `%{token: ..., context: "reset_password", ...}` map and passed it to `repo.insert!/1`, which raises `Protocol.UndefinedError` for `Ecto.Queryable` at runtime.
2. `request_magic_link/3` had the identical shape-of-bug with `context: "magic_link"`.

The existing `Sigra.AuthTest` unit tests matched `insert!/1` with plain-map patterns (`fn %{token: _, context: "magic_link", ...}`), which is why the bug slipped through in the Phase 2 + Phase 3 test passes: the mock itself happily accepted the bad payload.

### Fix

Both functions now:

1. `Keyword.fetch!(opts, :user_token_schema)` at the top of the function body (raises `KeyError` if omitted).
2. Build the row via `struct!(user_token_schema, %{...})` — the same pattern already in use at `lib/sigra/auth.ex:549` and `:556` for the confirmation-email writes.
3. Document the new required `:user_token_schema` option in the `@doc` Options block.

### Regression test

`test/sigra/auth_plain_map_regression_test.exs` provides a `StubRepo` whose `insert!/1` function head only matches `%_{}` structs. A plain-map regression therefore blows up with `FunctionClauseError`, which is the same kind of hard failure `Ecto.Adapters.SQL.Sandbox` would produce. The test asserts:

- `request_password_reset/3` inserts a `%TestUserToken{}` with the right `context`/`sent_to`/`user_id`/`token` fields and returns `{:ok, {encoded_token, url}}`.
- `request_magic_link/3` does the equivalent with `context: "magic_link"`.
- Both functions raise `KeyError` when `:user_token_schema` is missing from opts.

4 tests, 4 passing (was RED with 4 `FunctionClauseError`s before the fix).

## Deviations from Plan

### Architectural deviation: StubRepo instead of Ecto.Adapters.SQL.Sandbox

**Found during:** Task 1, read-first step.
**Issue:** The plan's behavior section asked for a "live Sandbox Repo" test (`Ecto.Adapters.SQL.Sandbox.start_owner!/2`). But the sigra library test suite (`test/sigra/*`) has **no configured Ecto.Repo**: `test/test_helper.exs` only starts ExUnit and defines Mox mocks; there is no migration, no Repo module, no database URL, no Postgres dependency for the library tests. Only `test/example/` (the end-to-end example app) has a live Repo, and pulling that infra into the core library tests would (a) add Postgres as a hard dev-test dep for every library contributor and (b) dramatically expand the plan scope.
**Fix:** Used an in-process `StubRepo` module whose `insert!/1` function head only matches `%_{} = struct`. A plain-map insert raises `FunctionClauseError` — which is the same kind of hard-fail as `Protocol.UndefinedError` from the real repo, and carries the same regression guarantee (any regression to a plain map turns the test red). The test also asserts the captured row is a `%TestUserToken{}` struct, verifying the `struct!(user_token_schema, ...)` path end-to-end.
**Rationale:** The plan's intent was "a regression test that fails if either call site reverts to a plain-map insert". The StubRepo meets that exactly, and the plan's `<read_first>` step even hinted this might be needed: "If no shared case exists, set up Sandbox inline OR" — with "or" implying flexibility.
**Files modified:** `test/sigra/auth_plain_map_regression_test.exs`
**Commit:** `f9f36ad`

### [Rule 1 — Bug] Tightened Sigra.AuthTest matchers from plain-map to struct

**Found during:** Task 2, updating call sites.
**Issue:** `test/sigra/auth_test.exs` already had tests for both call sites, but its `insert!/1` matchers used plain-map shape (`fn %{token: _, context: "magic_link", ...}`). Those matchers are the root cause of why the original plain-map bug shipped undetected. Leaving them in place would let a future regression pass the old tests while only the new regression file catches it — a footgun.
**Fix:** Updated both `describe "request_magic_link/3"` (3 tests) and `describe "request_password_reset/3"` (3 tests) to pass `:user_token_schema: TestUserToken` in opts and to assert the `insert!/1` argument is a `%TestUserToken{}` struct.
**Files modified:** `test/sigra/auth_test.exs`
**Commit:** `10c7cf9`

### Scope boundary notes (NOT fixed here)

Two items discovered during the `rg` sweep that are explicitly out of scope for this plan:

1. **`priv/templates/sigra.install/auth.ex:124` and `:335`** — the generated Accounts context template calls `Sigra.Auth.request_magic_link(Repo, email, user_schema: ..., url_fun: ...)` and `Sigra.Auth.request_password_reset(Repo, email, user_schema: ..., secret_key_base: ..., url_fun: ...)` **without passing `:user_token_schema`**. After this plan's fix, host applications generated from the current template will crash with `KeyError` on every password-reset or magic-link request. The plan explicitly says this belongs to plan 10.1-02 (installer backport). Noted here for that plan's execution agent: both template caller sites must be updated to pass `user_token_schema: UserToken` in the opts keyword list.

2. **`test/sigra/audit/cursor_portability_test.exs:31`** — unrelated pre-existing failure in audit cursor pagination, net improvement vs. the phase 10 baseline of 3 failures (now 1). Not touched.
