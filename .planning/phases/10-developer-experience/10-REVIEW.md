# Phase 10: Code Review Report

**Reviewed:** 2026-04-09
**Depth:** standard
**Files Reviewed:** 10 (library + installer templates + CI + mix.exs)
**Status:** issues_found

## Summary

Phase 10 adds the `cookie_domain` config surface, an email helper pair
(`normalize_email/1`, `valid_email?/1`), audit test helpers
(`audit_event_fixture/1`, `assert_audit_event/2`), scenario fixtures in the
installer template, an ExDoc guides surface, and a CI workflow. The bulk of
the diff is additive and well-documented.

Two critical findings are reported. The first is a **new regression**
introduced by this phase: the installer template for `UserAuth` now calls
`Mix.env()` at runtime from `remember_me_options/0`, which raises
`UndefinedFunctionError` inside a Mix release where `:mix` is not a runtime
dependency. The same bug is present in the already-generated example app.
The second is the **pre-existing deferred issue** flagged in the config
(`Sigra.Auth.request_password_reset/3` inserting a plain map via
`repo.insert!/1`); it is recorded here for traceability.

Warnings cover doc drift (`guides/flows/mfa.md` references
`Sigra.MFA.verify_backup_code` and `Sigra.MFA.enrolled?` — neither exists;
the real functions are `verify_backup` and `enabled?`), a subtle boolean
bug in `assert_audit_event` where `Map.get(...) || Map.get(...)` will
collapse a `false`/`nil` metadata value, the deprecated-shim for
`Sigra.MFA.Trust.cookie_opts/0` leaving the old example-app/test path
silently ignoring `cookie_domain`, and a defaults-surprise in the
`oauth_enabled?/1` doctest where the function returns `true` on a
config with no `:oauth` key set.

## Critical Issues

### CR-01: `Mix.env()` called at runtime in generated `UserAuth` (release crash)

**File:** `priv/templates/sigra.install/user_auth.ex:32`
**Also affected:** `test/example/lib/example_web/user_auth.ex:33`
**Issue:** `remember_me_options/0` was changed from a compile-time module
attribute to a runtime function so that `cookie_domain` can be resolved
dynamically. The body calls `Mix.env() == :prod`. `Mix` is NOT loaded in a
production Elixir release (Mix is a build-time tool; `mix release` excludes
the `:mix` application from the release by design). The first login that
triggers `maybe_write_remember_me_cookie/3` in a release will raise
`UndefinedFunctionError` on `Mix.env/0`, breaking remember-me for every
deployed app generated by `sigra.install` after this phase ships.

This is a regression — the original compile-time attribute (`secure: Mix.env() == :prod`)
was safe because it resolved at build time.

The sibling check at `lib/sigra/application.ex:30` uses
`if function_exported?(Mix, :env, 0), do: Mix.env(), else: :prod`, which
IS safe. The installer template should use the same guard, or better, not
depend on `Mix.env()` at all at runtime.

**Fix:** Resolve the `:secure` flag at compile time (it does not need to
vary per-request) and add it to the static attribute. `cookie_domain` can
remain runtime-resolved:

```elixir
@remember_me_static_options [
  sign: true,
  max_age: @max_age,
  same_site: "Lax",
  http_only: true,
  secure: Mix.env() == :prod
]

defp remember_me_options do
  config = <%= context_module %>.sigra_config()

  case config.cookie_domain do
    nil -> @remember_me_static_options
    domain when is_binary(domain) -> Keyword.put(@remember_me_static_options, :domain, domain)
  end
end
```

Alternatively, drive `:secure` off `config.endpoint_url_scheme == "https"`
or a new `cookie_secure?` config field if you need runtime flexibility,
but do NOT reference `Mix.env/0` from code that runs inside a release.

Apply the same fix to `test/example/lib/example_web/user_auth.ex`.

### CR-02: `Sigra.Auth.request_password_reset/3` inserts a plain map (deferred, pre-existing)

**File:** `lib/sigra/auth.ex:828-835`
**Issue:** (Flagged in review config under `scope_notes` as a known deferred
issue — recorded here for traceability.) The function builds a plain map
named `token_struct` and then calls `repo.insert!(token_struct)`. Ecto's
`Repo.insert!/1` requires an `%Ecto.Changeset{}` or a struct implementing
`Ecto.Schema`. Passing a plain `%{}` raises `Protocol.UndefinedError` at
the first call — password reset is fundamentally broken when this path is
hit. No Phase 10 smoke test exercises it (DX-04 covers registration, login,
logout, MFA, OAuth, API tokens, and the getting-started flow, but password
reset is covered only by the `password_reset_test.exs` smoke file which
appears to test other paths).

**Fix:** Build a proper `%UserToken{}` struct:

```elixir
token_struct = %UserToken{
  token: hashed_token,
  context: "reset_password",
  sent_to: user.email,
  user_id: user.id
}

repo.insert!(token_struct)
```

Ensure `alias MyApp.Accounts.UserToken` or equivalent is available, or use
the schema module resolved from `config.token_schema`. Add a smoke test
that actually drives `request_password_reset` through a live repo so this
does not regress again.

### WR-02: `assert_audit_event` metadata lookup collapses `false`/`nil` values

**File:** `lib/sigra/testing.ex:1178-1181`
**Issue:** The helper tries to support metadata stored with either atom or
string keys by doing:

```elixir
actual =
  Map.get(event.metadata || %{}, to_string(k)) ||
    Map.get(event.metadata || %{}, k)
```

Because `||` short-circuits on any falsy value, an event with
`metadata: %{"deleted" => false}` or `metadata: %{"note" => nil}` will
cause the first `Map.get` to return `false`/`nil`, fall through to the
second `Map.get`, and silently pick up whatever the atom-key lookup
returns (typically `nil`). The comparison against the expected value
will then mis-diagnose the real content of the field — either asserting
against the wrong value or passing when it should fail.

**Fix:** Use `Map.has_key?/2`-based branching, or `Map.fetch/2`:

```elixir
metadata = event.metadata || %{}

actual =
  cond do
    Map.has_key?(metadata, to_string(k)) -> Map.get(metadata, to_string(k))
    Map.has_key?(metadata, k) -> Map.get(metadata, k)
    true -> nil
  end
```

Add a regression test where expected metadata value is `false`.

### WR-03: `Sigra.MFA.Trust.cookie_opts/0` deprecated but still callable — callers silently miss `cookie_domain`

**File:** `lib/sigra/mfa/trust.ex:37-39`
**Issue:** The `cookie_opts/0` arity-0 version is marked `@deprecated` and
`@doc deprecated:` but still exists and returns the domain-unaware
options. Any code in a host app written against the old signature (e.g.,
apps upgrading from 0.6-0.9) will compile with a deprecation warning but
silently continue to drop cookies without the configured domain, reopening
exactly the subdomain-auth bug this phase fixes. The risk window is the
entire upgrade period.

Note that `mfa_challenge_controller.ex` in the installer templates HAS
been updated to `cookie_opts(config)`, so new apps are fine. The concern
is existing host apps using the old template (arity-0 form).

**Fix:** Either

1. **Preferred:** Delete `cookie_opts/0` outright in a major bump and
   force a compile error on upgrade. Document the break in CHANGELOG.
2. **Or:** Make `cookie_opts/0` raise at runtime with a clear message:

```elixir
def cookie_opts do
  raise """
  Sigra.MFA.Trust.cookie_opts/0 was removed to guarantee cookie_domain is \
  honored. Call cookie_opts/1 with your %Sigra.Config{}. See \
  CHANGELOG for migration notes.
  """
end
```

3. **Minimum:** If retention is required, log a `Logger.warning` on every
   call so the issue is visible in staging before prod.

Current behaviour (silent deprecation + wrong cookies) is the worst of
all options for a security-sensitive path.

### WR-04: `Sigra.Config.oauth_enabled?/1` defaults to `true` with no providers — misleading doctest

**File:** `lib/sigra/config.ex:1360-1362` (implementation); `1349-1352` (doctest)
**Issue:** The new doctest added this phase asserts:

```
iex> config = Sigra.Config.new!(repo: Fake.Repo, user_schema: Fake.User)
iex> Sigra.Config.oauth_enabled?(config)
true
```

Because `oauth: []` is the default and
`Keyword.get(oauth, :enabled, true)` returns `true` for an empty list,
every base config claims OAuth is "enabled" despite having zero providers.
Callers checking `oauth_enabled?/1` before rendering a "Sign in with
Google" button will now render an empty buttons row in apps that never
configured any provider. The previous behaviour was the same, but the
doctest now explicitly promises this as a stable contract.

**Fix:** Either redefine the semantics to `enabled? and providers != []`:

```elixir
def oauth_enabled?(%__MODULE__{oauth: oauth}) do
  Keyword.get(oauth, :enabled, true) and Keyword.get(oauth, :providers, []) != []
end
```

Update the doctest accordingly:

```
iex> config = Sigra.Config.new!(repo: Fake.Repo, user_schema: Fake.User)
iex> Sigra.Config.oauth_enabled?(config)
false
```

Or rename to `oauth_permitted?/1` and add a separate
`oauth_configured?/1` for "has at least one provider". Either way, do
not leave the current contract documented as-is.

### IN-01: `application.ex` uses `Mix.env/0` via a `function_exported?` guard — correct pattern, worth documenting

**File:** `lib/sigra/application.ex:30`
**Issue:** The new `maybe_warn_missing_cookie_domain/0` defensively guards
`Mix.env()` with `function_exported?(Mix, :env, 0)`. This is the correct
release-safe pattern and contrasts with CR-01's regression in
`user_auth.ex`. Consider extracting this to a small helper such as
`Sigra.Env.current/0` so the pattern is reused consistently across
library code and generated templates.

**Fix:** Add to `lib/sigra/env.ex`:

```elixir
defmodule Sigra.Env do
  @moduledoc false
  def current do
    if function_exported?(Mix, :env, 0), do: Mix.env(), else: :prod
  end
end
```

Call `Sigra.Env.current()` from `application.ex` and the installer
template. Covers CR-01 at the same time.

### IN-02: `test_load_filters` regex excludes `test/example/` cleanly

**File:** `mix.exs:15`
**Issue:** `test_load_filters: [~r"^test/(?!example/)"]` relies on a
negative lookahead. It works today but is non-obvious for a future
contributor, and `test_load_filters` is a relatively new Mix option
(Elixir 1.15+). Your root `mix.exs` already declares `elixir: "~> 1.18"`
so compatibility is fine, but consider a short comment explaining what
gets in/out of the filter (it already has one — good; just consider
adding a concrete example: "matches `test/sigra/foo_test.exs`, excludes
`test/example/test/example_web/foo_test.exs`").

**Fix:** Extend the existing comment block:

```elixir
# Matches: test/sigra/** , test/support/**
# Excludes: test/example/**
test_load_filters: [~r"^test/(?!example/)"],
```

**Issue:** `erlef/setup-beam@v1` is pinned to the major tag, not a

### IN-04: `scenario/2` in installer template silently raises on unknown atoms

**File:** `priv/templates/sigra.install/auth_fixtures.ex:270-275`
**Issue:** The docstring says "Raises FunctionClauseError on any other
value, including string scenario names." The intent is clear and the
test file `test/sigra/auth_fixtures_scenario_test.exs` asserts this
behaviour. However, `FunctionClauseError` is a generic message that will
not help a test author debug a typo like `scenario(:autheticated)` —
they will get "no function clause matching in MyApp.AccountsFixtures.scenario/2"
with no hint of the valid set.

**Fix:** Add a catch-all clause that raises `ArgumentError` listing
valid atoms:

```elixir
def scenario(other, _attrs) do
  raise ArgumentError,
        "unknown scenario #{inspect(other)}. Valid scenarios: " <>
        ":anonymous, :authenticated, :mfa_pending, :mfa_complete, " <>
        ":sudo, :locked, :unconfirmed"
end
```

Update the test to assert against `ArgumentError` with a matching
message.

### IN-05: `normalize_email/1` does not strip interior whitespace

**File:** `lib/sigra/auth.ex:49-52`
**Issue:** `String.trim/1 |> String.downcase/1` handles leading/trailing
whitespace and case but leaves interior whitespace intact:

```
iex> Sigra.Auth.normalize_email("Alice @example.com")
"alice @example.com"
```

Such a value will then fail `valid_email?/1` (the regex rejects whitespace
in the local part) but will still be persisted if a caller skips
validation and writes directly to the citext column. Not a bug per se —
just that the "normalize" contract is narrower than a reader might
assume.

**Fix:** Either

1. Document explicitly in the moduledoc that only surrounding whitespace
   is stripped, or
2. Strip all whitespace with `String.replace(email, ~r/\s+/, "")` before
   downcasing (riskier — may surprise users with "middle dot" emails).

Document-only fix is lower risk.
