# Phase 8 -- UI Design Contract

> Visual and interaction contract for account lifecycle generated templates. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Phoenix/Elixir -- shadcn not applicable) |
| Preset | not applicable |
| Component library | Phoenix Core Components (`.header`, `.button`, `.input`, `.form`, `.link`, `.icon`) |
| Icon library | Heroicons via `hero-*` class prefix |
| Font (web) | Tailwind default (system font stack via `font-sans`) |
| Font (email) | `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif` (inline `@font_family`) |

**Source:** Established in phases 1-7. All existing templates use Phoenix Core Components with Tailwind CSS utilities.

---

## Spacing Scale

Declared values use Tailwind's default spacing scale (multiples of 4px):

| Token | Tailwind Class | Value | Usage |
|-------|---------------|-------|-------|
| xs | `gap-1`, `p-1` | 4px | Icon gaps, inline badge padding |
| sm | `gap-2`, `p-2` | 8px | Badge padding, compact element spacing |
| md | `p-4`, `gap-4` | 16px | Card padding, form element spacing |
| lg | `mt-6`, `gap-6` | 24px | Section gaps within settings page |
| xl | `mt-8`, `gap-8` | 32px | Top margin below header (`.header` to first section) |
| 2xl | `py-12` | 48px | Not used in this phase |
| 3xl | `py-16` | 64px | Not used in this phase |

**Email spacing:** Inline styles using `margin: 0 0 12px 0` (12px paragraph gap), `margin: 24px 0` (24px section gap), `padding: 24px 16px` (card padding). Matches existing email template pattern.

Exceptions: none

**Source:** Verified from existing templates -- `session_live.ex` uses `mt-8 space-y-4`, `mfa_settings_live.ex` uses `p-4`, `login_live.ex` uses `my-6`.

### Settings Page Layout (D-55, D-61)

| Component | Pattern | Width | Notes |

| Danger section | Same card + `border-l-4 border-red-500` or `border-red-300` | Full width | Deletion section only |

### Email Section (D-59)

| State | Display | Interaction |
|-------|---------|-------------|
| No pending change | Current email as read-only `<p>` + "Change email" form below | Form: new email input + submit button. Submit triggers sudo. |
| Pending change | "Changing to: new@example.com (awaiting confirmation)" banner + "Cancel change" button | Cancel button sends `phx-click="cancel_email_change"` |
| After confirmation | Flash success message, email updated | Redirect or page refresh |

### Password Section (D-45, D-60)

| State | Display | Interaction |
|-------|---------|-------------|
| Has password | "Change password" form: current password + new password + confirm | Submit validates current, updates, invalidates sessions |
| OAuth-only (no password) | "Set a password" form: new password + confirm only | Submit triggers sudo (OAuth re-auth), then sets password |
| Force change banner | Yellow banner: "You must change your password to continue" | Banner at top of section when `must_change_password` is true |

### Deletion Section (D-30, D-57)

| State | Display | Interaction |
|-------|---------|-------------|
| Normal | Danger zone card with warning text + "Delete account" button (red) | Button opens confirmation modal. Modal triggers sudo. |
| Scheduled | "Account scheduled for deletion on [date]" + "Cancel deletion" button | Cancel requires re-auth. Shows cooldown if within 24h. |
| Confirmation modal | Modal with warning text, re-type action phrase, confirm button | `data-confirm` or LiveView modal component |

### Reactivation Page (D-15)

| State | Display | Interaction |
|-------|---------|-------------|
| Login during grace period | "Your account is scheduled for deletion on [date]. Want to cancel?" + "Cancel deletion" button + "Continue with deletion" link | Cancel requires re-auth. Continue logs them out. |

## Interaction Patterns

### Sudo Gate Flow

All sensitive operations follow the established Phase 4 sudo pattern:

1. User submits form (email change, account deletion)
2. If sudo window expired, redirect to `/users/sudo?return_to=/users/settings`
3. User re-authenticates (password or OAuth re-auth for OAuth-only users)
4. Redirect back to `/users/settings` with sudo window refreshed
5. User re-submits the form (form state should be preserved via session or URL params)

**Source:** `Sigra.Plug.RequireSudo` (Phase 4 D-20 to D-23)

### RequirePasswordChange Redirect

1. User with `must_change_password: true` hits any protected route
2. `RequirePasswordChange` plug redirects to `/users/settings#password`
3. After successful password change, flag cleared, user continues to original destination
4. Pattern identical to `RequireSudo` plug

### Settings Page Navigation (D-61)

- Single URL: `/users/settings`
- Anchor links: `#email`, `#password`, `#delete`
- Email confirmation route: `/users/settings/confirm-email/:token`
- Cancel email change: inline `phx-click` event (no separate route)
- Cancel deletion: inline `phx-click` event (no separate route)

### Deletion Confirmation Modal

1. User clicks "Delete my account" button
2. Modal appears with warning text and confirmation
3. Modal submit triggers sudo check
4. After sudo, deletion is scheduled
5. Page updates to show scheduled state with cancel option

## Accessibility Requirements

| Requirement | Implementation |
|-------------|---------------|
| Form labels | All inputs use `<.input>` component with `label` attribute |
| Error announcements | Changeset errors render via Phoenix Core Components (built-in `aria-describedby`) |
| Focus management | Autofocus on first input in active section; focus trap in deletion modal |
| Color contrast | All text/background combinations meet WCAG 2.1 AA (4.5:1 for normal text) |
| Destructive confirmations | `data-confirm` or modal -- never single-click destructive action |
| Status indicators | Badges use text + color (not color alone) for pending/scheduled states |
| Anchor navigation | Settings sections use `id` attributes matching anchor fragments |
