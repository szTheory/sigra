<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser hook -> MFA LiveView | Hook errors and success payloads are untrusted UI events. |
| MFA LiveView -> SessionController | Success handoff crosses from recoverable UI state to controller-owned session update. |
| MFA pending session -> full session | MFA challenge completion changes authentication state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-03-01 | Elevation of Privilege | MFA passkey success | mitigate | LiveView never calls `Auth.authenticate_passkey/2` directly; success posts to `/users/mfa/passkey`, where Plan 01 verifies the server-stored challenge and clears `:mfa_pending`. |
| T-21-03-02 | Spoofing | challenge prompt | mitigate | `begin_passkey_authentication` uses explicit user CTA and server-provided options; no auto-trigger on mount. |
| T-21-03-03 | Tampering | hook payload | mitigate | Error payload fields only select a recovery bucket; they are not displayed and do not change session state. |
| T-21-03-04 | Information Disclosure | error rendering | mitigate | Raw `AbortError`, `NotAllowedError`, and `WebAuthnError` are excluded from HEEx. |
| T-21-03-05 | Denial of Service | stuck ceremony | mitigate | Aborted/error handlers reset `passkey_status` to `:idle` and keep retry/fallback actions visible. |
| T-21-03-06 | Repudiation | MFA auth completion | mitigate | Actual authentication goes through `Auth.authenticate_passkey/2`, preserving library audit behavior from Phase 19. |
</threat_model>
