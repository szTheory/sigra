<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Login HTML -> SessionController | Untrusted identifier and passkey response post into auth completion. |
| Registration flow -> confirmation controller | User-selected signup enrollment intent crosses from LiveView params into email confirmation URL and session redirect state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-04-01 | Spoofing | passkey-primary login | mitigate | Keep identifier-first email field and POST to `/users/log_in/passkey`; Plan 01 verifies assertion against the requested user and server challenge before session creation. |
| T-21-04-02 | Tampering | signup enrollment redirect | mitigate | `ConfirmationController.confirm/2` writes `:user_return_to` server-side only after successful confirmation and routes through `/users/sudo?return_to=/users/settings/mfa#passkeys`. |
| T-21-04-03 | Information Disclosure | unknown email/passkey failure | mitigate | Login template preserves magic-link fallback and Plan 01 completion uses enumeration-safe generic passkey failure copy. |
| T-21-04-04 | Denial of Service | lost-device lockout | mitigate | `magic_link_recovery_available?/0` is mandatory in passkey-primary mode and login UI must keep `Email me a magic link` visible. |
| T-21-04-05 | Elevation of Privilege | session fixation | mitigate | Final login remains a plain POST into `UserAuth.log_in_user/3`; no LiveView event creates sessions. |
| T-21-04-06 | Repudiation | passkey login audit | mitigate | Completion routes call `Auth.authenticate_passkey/2`, preserving Phase 19 passkey authentication audit behavior. |
| T-21-04-07 | Elevation of Privilege | unconfirmed passkey-primary login | mitigate | `complete_passkey/2` must call `Auth.ensure_passkey_primary_user_eligible/1` and reject nil `confirmed_at` before authentication/session creation. |
</threat_model>
