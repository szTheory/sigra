<objective>
GATE-02's fix half, and the first link in D-24's locked chain: **GATE-02 fix -> GATE-04 fix ->
GATE-02 enable -> GATE-03 enforcement -> GATE-01 observation.** Nothing downstream may proceed until
the generated-host lane is green, because D-08 makes that a hard boundary — removing the stale
`head_ref` gate onto a lane that reds on ~38% of runs would train maintainers to ignore it, which is
the precise dishonest-signal failure this phase exists to remove.

The diagnosis is one instrumented run from certain and several hypotheses short of guessable. Five
candidate mechanisms are already falsified by live evidence: there is no webfont to race (no
`@font-face` anywhere in `sigra_auth.css`); the 15-character token `SigraAdminSmoke` is already
breaking into four fragments in the failure screenshot; the app name is hardcoded in
`admin-acceptance-smoke.sh`; the runner image is byte-identical (`ubuntu24/20260720.247`) between a
passing and a failing run; and so are the Chromium (`147.0.7727.15`) and WebKit (`26.4`) builds.
What the screenshot proves is that the overflow is REAL — the label `Email for sign-in lin` is
clipped mid-word at x=320, running off-canvas rather than wrapping.

The surviving primary hypothesis is structural: `<input>` elements carry an intrinsic `min-content`
width of roughly 20 characters, `.sigra-auth form` has `min-width: 0` but the inputs themselves do
not, and a grid item's automatic minimum size resolves to `min-content` regardless of `width: 100%`.
At a 32px root font that is well past 320px. If that is right, the ~62% of "passes" are racy
false-greens where `page.evaluate` reads a pre-viewport-change `innerWidth` of 1280.

So this plan instruments first and fixes second. It does not implement against the hypothesis.

Purpose: make the generated-host parity lane honestly green so D-06 can remove its stale gate.
Output: an instrumented diagnosis with run ids, a real WCAG 1.4.10 reflow fix in the shipped
template, and a confirming run.
</objective>
