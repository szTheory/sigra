green, or every remaining red lane is a filed, diagnosed defect with an

## 4. Standing post-merge backstops (same structurally-unobservable-pre-merge class)

These two items cannot be observed pre-merge for the same structural reason
as GATE-01 itself, and are not new gaps introduced by this phase:

- **D-18 — GitHub Pages source builds `main` root, not `gh-pages`.** The
  Pages publisher's two self-heal steps (`Publish to gh-pages branch`,
  `Point GitHub Pages at gh-pages (REST API)`) are both hard-gated on
  `github.ref == 'refs/heads/main'`. `workflow_dispatch` always resolves the
  workflow definition from the dispatched ref, so no single pre-merge
  dispatch can exercise both the fix (which requires dispatching from the
  phase branch) and the `ref == main` gate (which requires dispatching from
  `main`, which would run `main`'s pre-fix copy). Confirmed unchanged via
  `gh api repos/szTheory/sigra/pages` immediately after dispatch run
  `30529885885` (`source: {"branch": "main", "path": "/"}`). Filed at
  `.planning/todos/pending/2026-07-29-github-pages-source-builds-main-root-not-gh-pages.md`
  with both candidate root causes (insufficient `GITHUB_TOKEN` scope vs. a
  Settings-level block) left open rather than guessed at. Post-merge
  verification: `gh api repos/szTheory/sigra/pages --jq '.source'` after the
  first merge-triggered push, or the next scheduled run, and check whether
  `source.branch`/`source.path` now point at `gh-pages`.
- **DX-05's `gate-ci-green` ceiling half.** The `timeout-minutes: 75` /
  `wait-for-ci-gate.sh --max-attempts 120` fix (`release-please.yml`) is only
  exercised on a real `release_created == 'true'` release — it cannot be
  forced on a non-release PR. Its hermetic self-tests (11/11 passing) prove
  the polling logic in isolation; the ceiling itself is only provable
  end-to-end on the next real release.

## 5. The change most deserving human review before merge: the floor-rebase mechanism

`scripts/ci/quality-findings-monotonic.sh`'s floor-rebase declaration
mechanism (231-05, commits `8c49722b` (mechanism) / `af1b192c` (declaration
data), declaration schema at `guides/reference/floor-rebase-declarations.json`)
was authorized as an out-of-fence deviation during 231-05: the old
merge-blocking floor (33,642 open findings) had been measured on renders
that aborted early and so undercounted; the honest current value is 38,016.
The alternatives were a knowingly-false ledger or a permanently-red merge
gate — neither acceptable.

**The verifier independently exercised this mechanism against the real
pre/post-rebase git boundary** (not just read the code) and found it
genuinely bounded:

- Comparing at the actual pre-rebase→post-rebase boundary
  (`--base be970b50^`), the declaration validates and authorizes exactly the
  claimed 114 cells — matching both `prior_totals` (33,642, confirmed against
  `be970b50^`'s ledger) and `new_totals` (38,016, confirmed against the
  current ledger) exactly.
- Fail-closed by default: absent a declaration, behavior is today's exact
  strict behavior.
- Cannot be reused for a second, different increase: negative controls
  (Tests E, F, G, H) independently re-run and confirmed — absent declaration
  still fails (E), a mismatched declaration is rejected (F), drift beyond the
  declared floor still fails (H), and a base that already contains the
  rebase (`--base be970b50`) trivially passes with the declaration correctly
  reported as non-matching / inert, not reused.
- Both `prior_totals` and `new_totals` are verified against actual ledger
  content before authorizing anything — a declaration cannot launder an
  unrelated increase.

**Conclusion: reviewed and sound.** It is noted here — not as a defect, but
because it changes how this repo re-baselines a quality floor going forward,
and that class of change warrants an owner's eye before merge, independent
of whether the mechanism itself is correct.
