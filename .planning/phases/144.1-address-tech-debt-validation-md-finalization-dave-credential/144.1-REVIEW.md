### WR-01: `testInfo` parameter declared but unused in `assertDemoScreenshot`

**File:** `test/example/priv/playwright/tests/demo-showcase.spec.ts:49-59`
**Issue:** `assertDemoScreenshot` accepts `testInfo: TestInfo` as its second parameter but never references it inside the function body. In `admin-checkpoints.spec.ts`, the equivalent helper uses `testInfo.project.name` to derive dark/mobile variants — this is the purpose of the parameter. In `demo-showcase.spec.ts` the function only detects CI via `process.env.CI`, so `testInfo` is dead weight. This will trigger a TypeScript unused-parameter warning (`@typescript-eslint/no-unused-vars`) if strict linting is applied to test files, and misleads a future developer into thinking project-name logic is already wired.

**Fix:** Either remove the parameter and all four call-sites (passing `(page, testInfo, slug)` → `(page, slug)`), or add the project-name branch if dark/mobile tolerance differentiation is actually needed:

```typescript
// Option A — remove unused parameter
async function assertDemoScreenshot(page: Page, slug: string) {
  const ci = process.env.CI === 'true';
  await expect(page).toHaveScreenshot(`${slug}.png`, {
    fullPage: false,
    maxDiffPixels: ci ? 200_000 : 30_000,
    maxDiffPixelRatio: ci ? 0.22 : 0.06,
  });
}
// update call sites: assertDemoScreenshot(page, testInfo, 'demo-credentials')
//                → assertDemoScreenshot(page, 'demo-credentials')
```

If `testInfo` is retained intentionally for future activation, suppress the lint warning explicitly rather than leaving it silent:

```typescript
// Option B — explicit no-op suppression
async function assertDemoScreenshot(
  page: Page,
  _testInfo: TestInfo,  // reserved for future dark/mobile branching
  slug: string,
) { ... }
```

### WR-02: `DEMO_TOTP_B32` constant is unverified and cannot be independently checked

**File:** `test/example/priv/playwright/tests/demo-showcase.spec.ts:23`
**Issue:** `DEMO_TOTP_B32 = 'CSIL7ZDJ7RGXDGXRGIV3Q6CZIBOESTCW'` is described as "the correct base32 encoding of `Personas.demo_totp_secret/0`". `Personas.demo_totp_secret/0` is derived as `:crypto.hash(:sha256, "sigra-demo-admin-totp-v1") |> binary_part(0, 20)`. The constant is declared but never exercised at runtime in this spec (the comment explains why), so a mismatch would go undetected for the life of the spec. If a future developer activates the TOTP challenge path by adding `mfa.check_fn`, a silently wrong constant will cause an immediate test failure with a confusing root cause. The constant's correctness cannot be statically verified from the TypeScript side alone — it requires running the Elixir derivation.

**Fix:** Add an inline comment that documents exactly how to re-derive the value if the Elixir side changes, so the activation path is self-contained:

```typescript
// DEMO_TOTP_B32: NimbleTOTP.Base32.encode(Sigra.Test.Personas.demo_totp_secret())
// Re-derive: iex -S mix -e \
//   'IO.puts NimbleTOTP.Base32.encode(Example.Demo.Personas.demo_totp_secret())'
// Current derivation: :crypto.hash(:sha256, "sigra-demo-admin-totp-v1") |> binary_part(0, 20)
const DEMO_TOTP_B32 = 'CSIL7ZDJ7RGXDGXRGIV3Q6CZIBOESTCW';
```

This does not fix a current runtime bug (the constant is never called), but prevents silent staleness on activation.

### IN-02: `demo-showcase.md` guide references a credential page only available in dev mode without surfacing the constraint at the guide level

**File:** `guides/introduction/demo-showcase.md:17-18`
**Issue:** The guide embeds a screenshot of `/demo/credentials` and instructs readers to visit it, but the dev-mode-only constraint is only disclosed in the body text of the "Credentials Cheat-Sheet" section (`"The page is only available in development mode — it is not generated in production builds"`). The guide's introduction paragraph ("without writing any setup code yourself") could lead a reader who has cloned the example app in a non-dev environment to be confused when the route 404s. This is a documentation clarity issue, not a security issue — there is no production-access risk.

**Fix:** This is minor; the existing disclosure in the section body is adequate. If the guide is ever restructured, surfacing the constraint in the section heading (e.g., "Credentials Cheat-Sheet (dev mode only)") would make it immediately visible to skimmers.
