### Item 3: Dave credential language — misleading "wrong password" framing

**What is wrong:** Two files describe Dave's scenario in a way that may mislead evaluators:

**`test/example/README.md` (line 45):**
```
Try the wrong password to see the enumeration-resistant login response.
```

**`guides/introduction/demo-showcase.md` (line 47):**
```
Try logging in with the wrong password to see Sigra's enumeration-resistant
response — the error message does not reveal whether the account exists or why
the login failed.
```

**Why this is misleading:** The enumeration-resistant response applies to ALL failed login attempts on Dave's account — not just wrong-password attempts. Specifically:
- Using Dave's CORRECT password (`DaveDemoPass1!Locked`) also produces an enumeration-resistant error response, because the account is locked AND unconfirmed.
- An evaluator reading "try the wrong password" might try the correct password and see the same response, then be confused about whether the demo is working correctly.
- The interesting behavior is that Sigra does not distinguish between "wrong password", "locked", and "unconfirmed" in its public-facing response — that is the enumeration-resistance. The current language only illustrates one trigger.

**Dave's actual state** (from `test/example/lib/example/demo/personas.ex`):
- `confirmed: false`
- `locked: true`
- `password: "DaveDemoPass1!Locked"` (correct password that also produces error response)

**Recommended fix — README.md (line 45):**
Replace:
```
Try the wrong password to see the enumeration-resistant login response.
```
With:
```
Try logging in — with the correct password or a wrong one — to see Sigra's enumeration-resistant response. The error does not reveal whether the account exists, is locked, or is unconfirmed.
```

**Recommended fix — demo-showcase.md (line 47):**
Replace:
```
Try logging in with the wrong password to see Sigra's enumeration-resistant
response — the error message does not reveal whether the account exists or why
the login failed.
```
With:
```
Try logging in — with the correct password (`DaveDemoPass1!Locked`) or a wrong one — to see Sigra's enumeration-resistant response. The error message does not reveal whether the account exists, is locked, or is unconfirmed. This is by design: leaking the reason for a failed login enables account enumeration and targeted attacks.
```

The expanded explanation in the guide is intentional — the guide is the deeper reference, while the README is brief. Adjust length to taste.

**What is wrong:** `test/example/priv/playwright/tests/demo-showcase.spec.ts` line 119:
```typescript
// Step 2: Login as demo admin (TOTP challenge)
```

**Why this is wrong:** The `loginDemoAdmin` function's own JSDoc block (lines 62-84) explicitly states:

> "The example app's sigra_config() does not set mfa.check_fn, so the login flow creates a :standard session (not :mfa_pending), regardless of the user's TOTP enrollment state. The admin lands directly at "/" on successful login — no MFA challenge redirect."

There is no TOTP challenge at Step 2. The step label contradicts the function it calls. A future maintainer reading only the step header would be confused when they see no TOTP interaction in the actual step code.

**Fix:** Update the Step 2 comment to accurately describe what happens:
```typescript
// Step 2: Login as demo admin (no MFA challenge — example app uses step-up auth, not login challenge)
```

Or more concisely:
```typescript
// Step 2: Login as demo admin (standard session — no MFA challenge)
```

This is a comment-only change. No behavioral code is touched.

## Common Pitfalls

### Pitfall 1: Over-editing Dave's callout
**What goes wrong:** Rewriting the entire Dave section instead of just fixing the "wrong password" framing.
**Why it happens:** The clarification is small but the surrounding context tempts expansion.
**How to avoid:** Make the minimal change that removes the misleading implication. The key fix is removing "wrong password" as the only trigger and making clear both the correct and wrong passwords produce the same response.
**Warning signs:** If the README Dave callout grows beyond 3-4 sentences, it is over-scoped.

### Pitfall 2: Incorrect VALIDATION.md checkbox syntax
**What goes wrong:** Using wrong markdown checkbox syntax when updating task statuses.
**Why it happens:** The VALIDATION.md uses a non-standard status column format (`⬜ pending` / `✅ green`) rather than `[ ]`/`[x]`.
**How to avoid:** In the Per-Task Verification Map table, replace `⬜ pending` with `✅ green` in the Status column. The sign-off section at the bottom uses `- [ ]` / `- [x]` checkbox syntax.
