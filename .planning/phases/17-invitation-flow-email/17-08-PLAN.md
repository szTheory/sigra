<objective>
Sidecar plan (Wave 2, independent of Phase 17 main path) — fix the Phase 16
slug-alias migration's Postgres IMMUTABLE pitfall that STATE.md flags as
pending follow-up. Folded into Phase 17 per RESEARCH §Open Question Q4
RESOLVED (Option a from revision W4).

The existing migration at `priv/templates/sigra.install/organizations/migration.exs:75-78`
defines:

```elixir
create unique_index(:organization_slug_aliases, [:old_slug],
  where: "expires_at > now()",
  name: :organization_slug_aliases_old_slug_active_idx
)
```

Postgres rejects this because `now()` is `STABLE`, not `IMMUTABLE`, and
partial index predicates must be IMMUTABLE. Host apps running
`mix ecto.migrate` against Postgres will see:

```
ERROR:  functions in index predicate must be marked IMMUTABLE
```

Same bug class as Phase 17 D-03 (the invitation `pending_index` uses the
IMMUTABLE-safe `IS NULL` predicate precisely because of this pitfall).

**Runs in Wave 2 (independent of 17-01 and 17-02)** — touches a single
file not touched by any other Phase 17 plan. Safe to run in parallel
with 17-02 and 17-03 (zero `files_modified` overlap).

Purpose: Unblock the Phase 16 slug-alias migration so new installs and
existing hosts can run migrations cleanly. Scope is strictly limited —
this plan does NOT rewrite Phase 16's slug-alias behavior, only the
index definition.

Output:
- `priv/templates/sigra.install/organizations/migration.exs` — slug-alias
  index definition replaced with an IMMUTABLE-safe alternative
- Generator golden fixture updated if it contains the old predicate
</objective>

From `priv/templates/sigra.install/organizations/migration.exs:75-78` (the broken predicate):
```elixir
create unique_index(:organization_slug_aliases, [:old_slug],

```

**Two acceptable replacements — planner MUST choose one after reading the
Phase 16 slug-alias consumer code (`lib/sigra/plugs/load_organization_from_slug.ex`
or equivalent) to determine which preserves existing behavior:**

**Option A — full unique index, application-level expiry filter:**
```elixir
create unique_index(:organization_slug_aliases, [:old_slug],
  name: :organization_slug_aliases_old_slug_idx
)
```
The consumer query must already filter `where: as.expires_at > ^DateTime.utc_now()` (application-level). This is cleaner but means EXPIRED old-slug rows can no longer be reclaimed by a DIFFERENT org until the row is hard-deleted (by a cleanup worker). If Phase 16 relied on the partial index to auto-reclaim expired rows, this breaks.

**Option B — drop partial-uniqueness entirely, use plain non-unique index:**
```elixir
create index(:organization_slug_aliases, [:old_slug],
  name: :organization_slug_aliases_old_slug_idx
)
```
Slug-alias uniqueness becomes an application-level invariant enforced at
the insertion point. Expired rows and active rows coexist in the index
without constraint violation. Cleanup worker hard-deletes expired rows
opportunistically.

**Planner recommendation:** Option A. Reasoning: the consumer plug
already filters by `expires_at > now()` in its lookup query, so the
index-level partial predicate was structurally redundant. A full unique
index on `old_slug` enforces "at most one row per old_slug ever" which
is stricter but operationally acceptable if cleanup runs before another
org wants to reclaim the same slug. If Phase 16 tests pass with Option A,
go with it. If any Phase 16 test relies on slug-reclamation-via-expiry,
fall back to Option B and document in SUMMARY.md.

Read `lib/sigra/plugs/load_organization_from_slug.ex` (or the grep
equivalent) and any `test/sigra/plugs/load_organization_from_slug_test.exs`
before choosing.
