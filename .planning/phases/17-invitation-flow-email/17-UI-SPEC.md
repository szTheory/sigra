# Phase 17 — UI Design Contract

> Visual and interaction contract for the organization invitation surface:
> invite-member modal, pending-invitations lists (on `OrganizationMembersLive`
> + `OrganizationsLive.Index`), revoke-confirm modal, the single unscoped
> Accept LiveView with three render branches (signup / signed-in match /
> signed-in mismatch), and the transactional `organization_invitation_email`
> template. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> Phase 17 is **additive on top of Phase 16 UI-SPEC**. Every design token,
> component, and voice rule from `16-UI-SPEC.md` is inherited by reference.
> Only deltas and new surfaces are specified here. When Phase 17 and Phase 16
> contradict, Phase 16 wins (Phase 17 is a non-breaking extension).

**Stack baseline:** Phoenix 1.8 generated `core_components.ex` + daisyUI 5
+ Tailwind v4 + Heroicons. All new templates ship as **generator templates**
under `priv/templates/sigra.install/organizations/` (invite modal, pending
list partials, accept LV) and `priv/templates/sigra.install/core/`
(email template). Zero new library UI components — matches Phase 16 D-28/D-29
UI Ownership Rule.

## Copywriting Contract

### Voice

Inherits Phase 16 voice: authoritative, terse, reversible-state, clinical on
destructive actions, second person, no emoji, no exclamation marks except
success confirmations. `phx.gen.auth` 1.8 tone.

**Phase 17 additions to voice rules:**

- Mismatch branch uses **factual, non-accusatory** language. Never "You are
  not authorized" or "Access denied" — the invitee is not at fault, they are
  just signed in as someone else on a shared device. Copy: *"This invitation
  is for other@example.com. You are signed in as you@example.com."*
- Email subject line must **name both the inviter and the org** for phishing
  defense clarity (D-12 discretion note): *"Jane Doe invited you to join
  Acme on {product_name}"*.
- Never say "click the link" in the email — say "accept the invitation"
  (accessibility + screen-reader friendly).

### Primary CTAs (one per screen/surface)

| Screen / Surface | Primary CTA label | Button variant |
|------------------|-------------------|----------------|
| Invite-member modal (on `OrganizationMembersLive`) | `Send invitation` | `btn btn-primary` (submit); `phx-disable-with="Sending..."` |
| Revoke-confirm modal (simple confirm, not typed) | `Revoke invitation` | `btn btn-error` (submit); `phx-disable-with="Revoking..."` |
| Accept LV — signup branch | `Create account & join {org.name}` | `btn btn-primary btn-block`; `phx-disable-with="Creating account..."` |
| Accept LV — signed-in-match branch | `Accept & join {org.name}` | `btn btn-primary btn-block`; `phx-disable-with="Joining..."` |
| Accept LV — signed-in-mismatch branch | **none — zero accept control in DOM by construction (D-06)** | — |
| `OrganizationsLive.Index` pending-invite row | `Accept` (primary) + `Decline` (optional, `btn btn-ghost btn-xs`) | `btn btn-primary btn-sm` |
| `OrganizationMembersLive` header | `Invite member` (was disabled stub in Phase 16, **enabled in Phase 17**) | `btn btn-primary` |
| Email CTA button | `Accept invitation` | Single primary button in email body (inline CSS matching precedent `cta_button/2`) |

### Invite-Member Modal (new in Phase 17 — extends `OrganizationMembersLive`)

Native `<dialog id="invite-member-modal" class="modal">` triggered by the
previously-disabled "Invite member" header button. Matches Phase 16 modal
rhythm (native `<dialog>`, no custom component).

**Anatomy:**

```heex
<dialog id="invite-member-modal" class="modal">
  <div class="modal-box">
    <h3 class="text-lg font-semibold">Invite a member</h3>
    <p class="text-sm text-base-content/70 mt-2">
      Send an invitation to join {@active_organization.name}.
      They will receive an email with a secure accept link.
    </p>

    <.simple_form for={@invite_form} phx-submit="invite_member" class="mt-4">
      <.input
        field={@invite_form[:email]}
        type="email"
        label="Email address"
        placeholder="teammate@example.com"
        required
        autocomplete="off"
        phx-debounce="300" />

      <.input
        field={@invite_form[:role]}
        type="select"
        label="Role"
        options={[
          {"Member — can access the organization", "member"},
          {"Admin — can invite and manage members", "admin"},
          {"Owner — full control, including deletion", "owner"}
        ]}
        prompt="Choose a role" />

      <:actions>
        <button
          type="button"
          class="btn btn-ghost"
          phx-click={JS.dispatch("click", to: "#invite-member-modal .modal-backdrop button")}>
          Cancel
        </button>
        <.button variant="primary" phx-disable-with="Sending...">
          Send invitation
        </.button>
      </:actions>
    </.simple_form>
  </div>
  <form method="dialog" class="modal-backdrop"><button>close</button></form>
</dialog>
```

- Default role: `member` (lowest privilege — fail-safe default).
- Email field: `type="email"`, `autocomplete="off"` (prevents auto-fill of
  current user's email onto an invite-someone-else form), `phx-debounce="300"`
  for live validation.
- Form errors appear inline on the field via `<.input>`'s standard error slot.
- Rate-limit error does **not** render inline — it renders as a flash toast
  (see Error Flashes table below).
- Modal closes on success via `JS.dispatch("close", to: "#invite-member-modal")`
  after `{:ok, _invitation}` assign cycle.

### Revoke-Confirm Modal (new in Phase 17)

Simple confirm — **not typed-confirm** — per D-08. Matches Phase 16 D-19
"remove member" rhythm (one-click confirm for reversible destructive actions).

**Anatomy:**

```heex
<dialog id="revoke-invitation-modal" class="modal">
  <div class="modal-box">
    <h3 class="text-lg font-semibold">Revoke invitation?</h3>
    <p class="text-sm mt-2">
      Revoke the invitation for <strong>{@revoking_invitation.email}</strong>?
      They will no longer be able to join <strong>{@active_organization.name}</strong>
      with this link. You can re-invite them later.
    </p>

    <div class="modal-action">
      <button type="button" class="btn btn-ghost" phx-click="cancel_revoke">Cancel</button>
      <.button
        phx-click="confirm_revoke"
        phx-value-id={@revoking_invitation.id}
        class="btn btn-error"
        phx-disable-with="Revoking...">
        Revoke invitation
      </.button>
    </div>
  </div>
  <form method="dialog" class="modal-backdrop"><button>close</button></form>
</dialog>
```

Copy rules (locked):

- Title: **`Revoke invitation?`** (always this exact string)
- Body sentence 1: **`Revoke the invitation for {email}?`**
- Body sentence 2: **`They will no longer be able to join {org.name} with this link. You can re-invite them later.`**
- Primary button: **`Revoke invitation`** (not "Confirm", not "Yes, revoke")
- Cancel button: **`Cancel`**

**Layout:** centered card, `max-w-md mx-auto py-16 px-4`, single-column.

### Accept LV — Signed-In Mismatch Branch (hijack-defense)

**Structural invariant (D-06):** This render branch **MUST NOT contain any
button, form, or control that posts to an accept endpoint**. The hijack class
is closed by construction — not by server-side guard alone. The checker MUST
grep this template and fail if any `phx-click="accept"`, `phx-submit="accept"`,
or `<form action="...accept">` appears inside the `:mismatch` branch.

### Error States

| Scenario | User-facing copy | Surface | Recovery path |
|----------|------------------|---------|---------------|
| Invite modal — email invalid | `Enter a valid email address.` | Inline field error on `:email` | Modal stays open, user corrects |
| Invite modal — email already pending for this org | `{email} already has a pending invitation to this organization.` | Inline field error on `:email` | Modal stays open; helpful hint — re-inviting is still allowed (D-05 revoke+recreate) |
| Invite modal — email already a member | `{email} is already a member of this organization.` | Inline field error on `:email` | Modal stays open |
| Invite modal — rate-limited (user quota hit) | `You have invited too many people today. Try again tomorrow.` | Flash toast `<.flash kind={:error}>`, modal **closes** | Wait 24 hours |
| Invite modal — rate-limited (org quota hit) | `This organization has reached its daily invitation limit. Try again tomorrow.` | Flash toast `<.flash kind={:error}>`, modal **closes** | Wait 24 hours |
| Invite modal — last-owner guard (inviting as owner change) | N/A — owner creation never demotes existing owner | — | — |
| Accept LV — invalid token (HMAC verify fail) | `This invitation link is not valid.` | Full-page card (replaces all branches) | Link to `/` |
| Accept LV — expired | `This invitation has expired. Ask {inviter_email} to send a new one.` | Full-page card (replaces all branches); inviter email rendered so the invitee knows who to contact | Link to `/` |
| Accept LV — revoked | `This invitation is no longer valid.` | Full-page card | Link to `/` |
| Accept LV — already accepted (replay) | `This invitation has already been accepted.` + if user is signed in and a member: auto-redirect with flash `You're already a member of {org.name}.` | Flash or full-page | Navigate to `/organizations/{slug}` if member |
| Accept LV — email bound in HMAC does not equal DB row email (tamper detected) | `This invitation link is not valid.` | Full-page card (same as invalid token — **no information leak** about what differed) | Link to `/` |
| Accept LV — signup branch tries to post a different email (client disabled + server reject) | `This invitation is locked to {invitation.email}.` | Inline field error on `:email` — but **form should prevent** submission client-side via `disabled` attr | Locked input is visible |
| Accept LV — signup branch password invalid (too short, too common) | Standard `Sigra.Auth` changeset errors | Inline field errors | User corrects |
| Revoke modal — invitation already accepted between page-load and revoke click (race) | `This invitation has already been accepted and cannot be revoked.` | Flash toast `<.flash kind={:error}>`; modal closes; row removed from stream | None (terminal state) |
| Revoke modal — unauthorized (non-owner/admin) | `You do not have permission to revoke invitations.` | Flash toast; modal closes | None (should not happen — UI gates the button) |
| Email delivery failure (mailer exception) | **Invite row still commits** (D-12 discretion recommends after-commit send). Flash on admin side: `Invitation created, but the email could not be sent. You can re-send it from the list.` | Flash warning `<.flash kind={:error}>` on `OrganizationMembersLive` | Admin can revoke and re-invite (or, deferred: resend-same-token) |

**Locked email copy rules:**

- Subject MUST include both `inviter_display_name` AND `org.name` (phishing defense).
- Body paragraph MUST name `inviter`, `org`, `role`, and `product_name` (phishing defense — invitee can verify).
- CTA button label: **`Accept invitation`** (not "Click here", not "Join now" — verb + noun, terse, action-oriented).
- Fallback URL MUST be shown below the CTA button (copy-paste fallback for email clients that strip buttons or for screen readers).
- Fine print MUST include expiry date AND the "safely ignore" reassurance (phishing guidance — legitimate invites never demand action).
- Colors reference the `api_token_created_email` palette exactly: `#18181b` H1, `#3f3f46` body, `#71717a` meta, `#f4f4f5` card, `#ffffff` wrapper — meets WCAG AA on white.

### Destructive Action Confirmations

| Action | Token | Style | Title | Body | Submit | Undo-able? |
|--------|-------|-------|-------|------|--------|------------|

less destructive than member removal (Phase 16 also uses simple confirm for

## Structural Checker Invariants (Phase 17 specific)

These are **grep-targets** for `gsd-ui-checker` to verify by construction:

1. **Mismatch branch contains zero accept form.** In `invitation_accept_live.ex`,
   the `:mismatch` render branch MUST NOT contain any of:
   - `phx-click="accept"` / `phx-click="accept_invitation"` / `phx-click="accept_with_signup"`
   - `phx-submit="accept"` / `phx-submit="accept_invitation"` / `phx-submit="accept_with_signup"`
   - `<form ...action="...accept">` / `<.simple_form ...phx-submit="accept...">`

   **Rationale:** D-06 "by construction, not by convention" — the hijack class
   is closed by rendering nothing, not by a server guard alone.

2. **Signup branch email field is disabled + readonly.** In `invitation_accept_live.ex`,
   the `:signup` branch email `<.input>` MUST have both `disabled` and `readonly`
   attributes, AND the changeset server-side MUST reject mismatched emails.

3. **Invite modal default role is `member`.** Lowest privilege default
   (fail-safe). Grep target: form initial value or select `prompt`/default option.

4. **Email subject contains both inviter name and org name.** Grep target in
   `organization_invitation_email.ex`: `subject(..)` call MUST interpolate
   both `inviter_display_name` and `org.name`.

5. **Email body contains fallback URL.** Grep target: the signed accept URL
   must appear as plaintext below the CTA button (not just inside an `<a href>`).

6. **Pending-invitations list shows all five columns** (INV-10 literal):
   email, role, invited-by, expires-in, revoke. Grep target: `<:col>` count + labels
   in `organization_members_live.ex` pending section.

7. **Revoke modal uses simple confirm, not typed-confirm.** Grep target:
   revoke modal MUST NOT contain a text `<.input>` field requiring a typed
   token string (no `phx-change` confirmation matcher).
