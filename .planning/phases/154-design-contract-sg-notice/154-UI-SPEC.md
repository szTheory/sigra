## sg-notice Component Specification

This is the primary CSS deliverable for Phase 154 (~15 lines, inside
`@layer sg-components`, adjacent to `.sg-list-row[data-tone]` at lines 945–967).

### Visual contract

`sg-notice` is a behavior-preserving consolidation of the existing
`.sg-list-row[data-tone]` contextual-alert pattern. The rendered output must be
visually identical to the current `sg-list-row data-tone` treatment so Phase 156
can swap call sites to `<.notice>` without a Playwright baseline re-record.

**Structure:**
```
.sg-notice                        — block container
  .sg-notice__body                — prose content area (optional sub-element)
```

**Base rules (all `sg-notice` instances):**
- `border-radius: var(--sg-radius-sm)` — matches `sg-list-row`
- `background: var(--sg-color-panel-alt)` — neutral default (no tone)
- `box-shadow: var(--sg-elev-inset)` — 1px inset ring, neutral
- `padding: var(--sg-space-4)` — 16px all sides, matches `sg-list-row`
- `transition: var(--sg-transition-tone)` — color/bg/shadow 140ms ease

**Tone variants (`data-tone` attribute — four values):**

`[data-tone="ok"]`:
- `background: color-mix(in oklab, var(--sg-color-ok-soft) 62%, var(--sg-color-panel))`
- `box-shadow: inset 3px 0 0 0 var(--sg-color-ok), inset 0 0 0 1px color-mix(in oklab, var(--sg-color-ok) 18%, transparent)`

`[data-tone="warn"]`:
- `background: color-mix(in oklab, var(--sg-color-warn-soft) 62%, var(--sg-color-panel))`
- `box-shadow: inset 3px 0 0 0 var(--sg-color-warn), inset 0 0 0 1px color-mix(in oklab, var(--sg-color-warn) 20%, transparent)`

`[data-tone="risk"]`:
- `background: color-mix(in oklab, var(--sg-color-risk-soft) 62%, var(--sg-color-panel))`
- `box-shadow: inset 3px 0 0 0 var(--sg-color-risk), inset 0 0 0 1px color-mix(in oklab, var(--sg-color-risk) 20%, transparent)`

`[data-tone="info"]`:
- `background: color-mix(in oklab, var(--sg-color-info-soft) 62%, var(--sg-color-panel))`
- `box-shadow: inset 3px 0 0 0 var(--sg-color-info), inset 0 0 0 1px color-mix(in oklab, var(--sg-color-info) 20%, transparent)`

**Left-bar anatomy:** `inset 3px 0 0 0` — 3px wide, full-height, left edge only.
This is the semantic signal carrier; do not widen or change position.

### Motion contract

`sg-notice` uses `--sg-transition-tone` (color + background-color + box-shadow,
140ms `--sg-ease`). This is the same transition already on `sg-list-row`.

Motion is NOT animated on `sg-notice` for:
- Initial render / page load
- Keyboard navigation (focus moves to/from notice)
- Filter apply (a keyboard-frequent interaction per GATE-03)

`prefers-reduced-motion: reduce` is already handled globally at lines 1437–1447:
the universal rule strips `transform` and animation; color/bg/shadow transitions
are shortened to `--sg-motion-fast`. `sg-notice` inherits this automatically.
No additional reduced-motion rules needed.

Source: `app.css` lines 945–967, 1126–1131, 1437–1447; REQUIREMENTS.md GATE-03.

### ARIA contract

`sg-notice` is a live-region container for contextual status messages.

| Tone | ARIA role | ARIA live |
|------|-----------|-----------|
| `risk` | `role="alert"` | (implicit — `alert` is live assertive) |
| `warn` | `role="status"` | `aria-live="polite"` |
| `ok` | `role="status"` | `aria-live="polite"` |
| `info` | `role="status"` | `aria-live="polite"` |
| no tone | `role="region"` | — |

These are applied in the HEEx component markup (Phase 155), not via CSS.
Phase 154 only defines the CSS — ARIA contract is documented here so Phase 155
has a citable authority.

Source: REQUIREMENTS.md COMP-03 (ARIA requirement); WCAG 4.1.3 (Status Messages).

### When NOT to use `sg-notice`

- Do NOT use `sg-notice` for inline validation errors on form fields — use
  `sg-error` / Phoenix form error helpers (field-level, not block-level).
- Do NOT use `sg-notice` for persistent navigation context — use `sg-scope-ribbon`.
- Do NOT use `sg-notice` as a list row data item — use `sg-list-row[data-tone]`
  for tabular/list data rows that happen to have a semantic tone.
- Do NOT use `sg-notice` without a `data-tone` attribute unless the content is
  purely informational and tone-neutral.

## Admin Design Contract Document Specification

This specifies the content contract for `guides/reference/admin-design-contract.md`
(deliverable 1 of 2).

### Document structure

```
# Sigra Admin Design Contract
## Job → Component Mapping
  ### Canonical Component: <name>
    - Job
    - Winning markup/CSS
    - ARIA role(s)
    - Motion spec (including explicit "not animated" entries)
    - When NOT to use
## Page Archetypes
  ### Overview Archetype
  ### List Archetype
  ### Detail Archetype
```

### 10 canonical components — required coverage

| Component | Job | Note for doc |
|-----------|-----|--------------|
| `stat_link` | Numeric KPI with a navigation destination | Links to filtered view; always a real `<a>` with count and label |
| `stat` | Numeric KPI without navigation | Demoted posture metric; read-only; no `<a>` |
| `task_card` | Verb-first action prompt for admin | Opens to action view; above stat strip in Overview archetype |
| `summary_chip` | Compact boolean property badge | Non-interactive; communicates state, not action |
| `applied_chip` | Active filter indicator | Interactive — clear affordance; removes filter on click |
| `empty_state` | Slot content when a list has zero rows | Dashed border, centred, `sg-empty-state` CSS |
| `page_back` | Single navigation step back | Leaf screens only; consumes `return_to`; not a breadcrumb |
| `scope_ribbon` | Persistent in-body scope indicator | Present on every list + leaf screen; Global vs org name |
| `notice` | Contextual alert with semantic tone | Block-level; toned via `data-tone`; ARIA live region |
| `skeleton` | Loading placeholder matching content shape | Replaces async content during load; `sg-skeleton` CSS |

### 3 page archetypes — required compositions

**Overview archetype:** needs-review `notice` (loud when count > 0) → verb-first
`task_card` grid → `stat_link` strip → capability table (lowest priority).

**List archetype:** `sg-page-header` (open, not boxed) → `scope_ribbon` →
filter row with `applied_chip`s → table/mobile-card dual layout with
`sg-list-row` rows → `empty_state` when zero rows.

**Detail archetype:** `sg-page-header` (open) → `page_back` → `scope_ribbon` →
`notice` for summary alerts → `sg-detail-grid` with `sg-card` sections →
`skeleton` for async sections.

Source: CONTEXT.md D-03, D-07; REQUIREMENTS.md COMP-03; CONTEXT.md
`canonical_refs` (LiveView files).

## Copywriting Contract

This phase produces documentation artifacts, not UI copy. However, the
governance doc's prescribed copy patterns are part of the design contract
for downstream phases (155–160).

| Element | Prescribed copy |
|---------|----------------|
| `notice` tone="risk" heading | Use active-voice problem statement, e.g. "Action required" or "{N} users need review" |
| `notice` tone="warn" heading | Use informational present tense, e.g. "Invitation expires soon" |
| `notice` tone="ok" | Use confirmation past tense, e.g. "All users verified" |
| `notice` tone="info" | Use neutral present tense, e.g. "Showing results for {scope}" |
| `empty_state` heading | Noun phrase naming the absent content, e.g. "No users" or "No audit events" |
| `empty_state` body | Next step with a verb, e.g. "Invite a user to get started." |
| `stat_link` label | Noun + state phrase, e.g. "Needs review" or "High risk" |
| `task_card` label | Verb phrase (imperative), e.g. "Review flagged users" |
| Destructive confirmation | No destructive actions in Phase 154 — artifacts only |

Source: REQUIREMENTS.md LAND-01/02; CONTEXT.md specifics.
