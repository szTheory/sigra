<objective>
Tighten the enumeration-parity test so the roadmap criterion cannot silently shrink again, and settle the mfa-challenge counting question the verifier filed as the residual of WR-08.

Purpose: after Plans 259-14 and 259-15 the three genuine existing-versus-unknown account surfaces (sign-in, magic-link request, password-reset request) are parity rows, as are confirmation-resend (a payload-ignored probe) and mfa-challenge (a code-kind probe). The named-surface test still says each of the five may be parity OR not_proven and only three must be parity, and it counts mfa-challenge (a wrong authenticator code versus a wrong backup code) toward that floor. That tolerance is exactly how the original shortfall passed. It is removed, and mfa-challenge is kept as a real parity probe that is explicitly counted apart.
Output: a stricter named-surface rule with planted controls, a stronger positive-control assertion, an mfa note that says what it is, and the WR-08 residual closed in the todo.

Decision recorded (reversible, test-only): mfa-challenge is not removed from the named set and not reclassified as non-parity, because a wrong TOTP code versus a wrong backup code is a real pre-auth probe worth keeping green; it is only barred from standing in for account-existence evidence. Removing it would drop a working probe; letting it count would repeat the over-claim. The owner may revisit this classification (it is a test-only choice, reversible with a one-line edit); the todo bullet records that. The same reasoning applies to confirmation-resend, which gets its own class because its probe proves a payload email is ignored, not that an existing and an unknown address answer alike.
</objective>
