<objective>
Close the confirmation-resend half of the Phase 259 verification gap: make the example host's resend reachable and completable (the verifier showed it is uncompletable in both session states), add a deterministic parity probe, and flip the registry row from not_proven to parity.

Purpose: `confirmation-resend` was registered not_proven because confirmation_live.ex:158 reads `current_scope.user` (nil for an anonymous visitor) and router.ex:106 redirects signed-in visitors before mount. The generated LiveView flow no longer has this defect (Phase 246 moved it onto `:mount_current_scope` and renders `:sign_in_required` in place for an anonymous visitor), but the example host never received that repair: an anonymous visitor on its confirm page clicking "Didn't receive a code?" gets a crash and a signed-in one is bounced silently. The example's anonymous behaviour chosen here (error flash plus redirect to log in) is a deliberate example-host choice that differs from the generated in-place render; the row therefore proves the example host only and the registry note says so.
Output: a repaired example router and LiveView, a regression suite that asserts on `confirmed_at` (not response status), one probe, one flipped registry row, one re-stated register row.

Identity decision (judgment surfaced for the reviewer, reversible, test-only): the resend event in the example and the generated page takes NO email from the visitor (read in `priv/templates/sigra.install/core/confirmation_live.ex`: `with_confirmation_user/2` reads the session only); its target is the session user. A literal "existing versus unknown email" form does not exist and this plan does not invent one (that would be a new product surface). The enumeration-relevant question that does exist is whether a visitor who can choose the event payload can make the handler act on, or answer differently for, an account. The probe therefore sends an email in the event payload for an existing unconfirmed account versus an unknown address and requires identical outcomes and zero tokens created. The registry note and register row say exactly this, so the claim is not read as covering an email-keyed resend form. Because the probe proves only that a payload email is ignored (the handler never reads params), this row is NOT an account-existence probe in the sense of sign-in, magic-link and password-reset request; Plan 259-16 therefore gives it its own id class (payload-ignored) that cannot satisfy the account-existence requirement, guarded by phrases the note must keep (`payload` and `email-keyed resend form`).
</objective>
