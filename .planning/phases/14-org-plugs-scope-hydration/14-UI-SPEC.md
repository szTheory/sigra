# Phase 14 — UI Design Contract

> Visual and interaction contract for the generated user-facing surface of Phase 14 (Org Plugs + Scope Hydration). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

Phase 14 is primarily a library/plug phase (D-22: every new module is in the library). The entire user-visible surface consists of **two new `auth_error/3` clauses generated into the host app's `AuthErrorHandler`** (D-08, D-09) plus the `scope.membership` contract these clauses assume. No LiveViews, no controllers, no `.heex` templates are added in Phase 14.

Concretely, the UI contract for this phase covers:

1. **`:no_active_org` response** — flash + redirect to `~p"/organizations"` (the picker/landing page itself is built in **Phase 16**; Phase 14 only declares the redirect target and the flash copy).
2. **`:insufficient_role` response** — flash + render the host's `ErrorHTML :"403"` template (Phoenix default, already generated by `phx.new 1.8`; Phase 14 does not ship a custom 403 page).
3. **Stale-pointer silent recovery** — no flash, no redirect at the error-handler layer. The `LoadActiveOrganization` plug performs recovery inline (D-04 step 5) and the user continues to the originally requested page if recovery succeeds, or falls through to `:no_active_org` on a subsequent `RequireMembership` check if the reassign returned nil.

Generated-page work for the picker, create-first-org landing, and switcher UI is **Phase 16** and is explicitly out of scope here (CONTEXT.md §domain "Out of scope"). The orchestrator's "three screens" framing reflects where users *land*, not pages Phase 14 creates.

## Copywriting Contract

The copy below is **the canonical wording** Phase 14 generates into `auth_error_handler.ex`. Downstream phases (16) may override the redirect targets but MUST keep the tone (non-blaming, action-forward, second-person).

| Element | Copy |
|---------|------|
| `:no_active_org` flash kind | `:info` |
| `:no_active_org` flash message | `Pick or create an organization to continue.` |
| `:no_active_org` redirect target | `~p"/organizations"` (picker/landing from Phase 16) |
| `:insufficient_role` flash kind | `:error` |
| `:insufficient_role` flash message | `You don't have permission to access this page in the current organization.` |
| `:insufficient_role` HTTP status | `403 Forbidden` |
| `:insufficient_role` rendered view | host `ErrorHTML :"403"` (Phoenix default) |
| Stale-pointer silent recovery | NO flash, NO redirect, NO visible message — audit-only (`organization.active_auto_reassigned`) |
| Login-time `{:none, :zero_orgs}` | NO flash at login (login succeeds); user sees `:no_active_org` on the **next** `RequireMembership` hit |
| Login-time `{:multiple, orgs}` with no resume pointer | NO flash at login; user sees `:no_active_org` on the **next** `RequireMembership` hit |
| `auth_error_handler.ex` moduledoc addition | `Clauses for :no_active_org and :insufficient_role are generated by Sigra for organization-aware routes. Edit the redirect target or message to match your product's tone.` |

### Copy Rules (non-negotiable)

- **Non-blaming second person.** "You don't have permission to access this page in the current organization." — NOT "Access denied" or "You are unauthorized."
- **Action-forward.** "Pick or create an organization to continue." — tells the user what to DO next, not what went wrong.
- **No stale-pointer flash.** Silent recovery MUST NOT show a message. Rationale: a self-healing system that shouts about its self-healing creates anxiety and trains users to distrust the session. The audit log (D-14) is the sole record of the transition.
- **No technical vocabulary.** Never surface "membership", "scope", "pointer", "stale", "hydration", "org_id", "role filter" in user-visible copy. These are library internals.
- **Never name the required role in the 403 flash.** Do NOT write "This page requires the Owner role." Leaking role names in the error message is a minor enumeration leak and forces translation of role atoms. The 403 page itself is sufficient signal.

## Interaction Contract

### Flash Rendering

Flashes are rendered by the host app's existing `<.flash_group>` / `<.flash>` components in `core_components.ex` (Phoenix 1.8 default). Phase 14 asserts:

- Flashes dismiss via the user's click OR the next successful navigation (Phoenix 1.8 default behavior; do NOT add auto-dismiss timers).
- `:no_active_org` uses `kind={:info}` → DaisyUI `alert-info`.
- `:insufficient_role` uses `kind={:error}` → DaisyUI `alert-error`.
- ARIA: host `<.flash>` already emits `role="alert"` — Phase 14 relies on this, does not override.

### Redirect Semantics

- `:no_active_org` → `redirect(to: ~p"/organizations")`. 302 Found.
- `:insufficient_role` → render 403 inline (no redirect). Prevents URL-bar flicker and preserves the Referer for back-button UX.

### Loading / Pending States

None. Both error responses are server-rendered in a single request. No client-side JS, no LiveView patches, no spinners.

### Empty States

Not applicable to Phase 14 directly. The landing page at `/organizations` (Phase 16) is the empty-state host; Phase 14 only guarantees users arrive there with the correct flash.

### Error States

Covered above. The only error states Phase 14 introduces are the two new `auth_error/3` clauses.

### Accessibility Contract

- 403 response must set `Content-Type: text/html; charset=utf-8` and return a body — never empty.
- Flashes are announced via the host's existing `role="alert"` container. Phase 14 does not bypass the flash system.
- Redirects use `redirect/2` (302), not `redirect/2` with `:external` — screen readers and back buttons behave predictably.
- 403 page must not require JavaScript to render. Phoenix's default `ErrorHTML` template is a static HEEx render — this is already satisfied.
