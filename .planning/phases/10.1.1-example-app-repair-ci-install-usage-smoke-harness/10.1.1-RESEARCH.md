**Researched:** 2026-04-10

## Summary

Phase 10.1.1 is a pure integration/DX repair phase. Every "bug" below is a concrete defect already localized to a specific file/line by the UAT session; this research's job is not to rediscover the bugs but to confirm the fix shape, make sure the installer templates are patched in parallel with `test/example/` (the real DX bug), and lock in a CI harness design that would have caught these nine bugs automatically.

The biggest research finding: **the installer templates are demonstrably as broken as `test/example/`**. `priv/templates/sigra.install/user_auth.ex:59` still calls `generate_user_session_token` (the phx.gen.auth legacy path — B6). `priv/templates/sigra.install/session_controller.ex:13` uses the hyphen URL `/users/log-in/` (doc drift — D-02 must fix templates too, not just `test/example`). `priv/templates/sigra.install/migration.exs` only emits `binary_id` when an explicit flag is passed — bigint is the default (D-10 needs to flip this). The sudo template bug (B7) is a missing `value=` attr on a naked `<.input>` inside `sudo_html.ex` — confirmed by reading `core_components.ex` which declares `attr :value, :any` with no default. **Every fix in `test/example/` has a matching template fix, and the templates are the v1.0 artifact.**

The CI harness design is straightforward: extend the existing `.github/workflows/ci.yml` with three sibling jobs alongside the current `example_app_smoke`, all sharing the same Postgres service pattern and `erlef/setup-beam` SHA-pinned step that `library_tests` already uses. The expensive bit — `install_smoke` — can cache at two levels: the Sigra library deps (keyed on root `mix.lock`) and a Hex registry cache (`~/.hex/` via `actions/cache`) so the fresh `mix phx.new` job doesn't re-download the hex registry on every run. Playwright has a well-established Elixir pattern: put the harness under `test/example/priv/playwright/` with its own `package.json`, use `@playwright/test` and `otplib` (more popular + actively maintained) or `otpauth` (also fine — Claude's discretion), and drive `/dev/mailbox` via the Swoosh Plug.Swoosh.MailboxPreview HTML (there is no JSON endpoint; scrape the `<a>` with the confirmation URL).

**Primary recommendation:** Treat `test/example/` and `priv/templates/sigra.install/` as **synchronized siblings**. For every repair task in `test/example/`, add a paired task that patches the equivalent template. The CI `install_smoke` job is what locks this discipline in — once it's green, any template drift becomes a compile/compile-warning failure on PR.

## Architecture Patterns

### CI workflow extension shape

```
.github/workflows/ci.yml
├── library_tests            (existing — keep)
├── example_unit_smoke       (rename of existing example_app_smoke — mix test --include example_app)
├── example_http_smoke       (NEW — boot app, curl critical routes, assert non-500)
├── example_playwright_smoke (NEW — full browser lifecycle + MFA)
└── install_smoke            (NEW — mix phx.new + mix sigra.install + mix compile)
```

All four jobs share:
- Same `services: postgres` block (copy-paste from `library_tests`).
- Same SHA-pinned `erlef/setup-beam` / `actions/checkout` / `actions/cache` refs.
- `needs:` — none. They run in parallel (that is the entire point of D-13).
- PR gate: rely on GitHub's "require status checks to pass" branch protection, listing all four job names.

### Pattern 1: `install_smoke` job layout

**What:** Runs `mix phx.new tmp_app --no-dashboard --install` then `mix sigra.install` against the freshly-generated app, pointing the Sigra dep at the checked-out repo root via path dep, then compiles with warnings-as-errors.

**When to use:** PR-required smoke, every push to main. Caches two things: (1) the Sigra library's own `deps` + `_build` keyed on root `mix.lock` (shared with `library_tests`), and (2) `~/.hex` to avoid re-fetching the Hex registry on `tmp_app`'s fresh `mix deps.get`.

**Sketch:**
```yaml
install_smoke:
  name: Install smoke (fresh phx.new + sigra.install)
  runs-on: ubuntu-latest
  services:
    postgres:
      image: postgres:15
      env: { POSTGRES_PASSWORD: postgres }
      ports: ['5432:5432']
      options: >-
        --health-cmd pg_isready --health-interval 10s
        --health-timeout 5s --health-retries 5
  steps:
    - uses: actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5  # v4.3.1
    - uses: erlef/setup-beam@fc68ffb90438ef2936bbb3251622353b3dcb2f93  # v1.24.0
      with: { otp-version: '27.3', elixir-version: '1.18.4' }
    - name: Cache Hex registry
      uses: actions/cache@0057852bfaa89a56745cba8c7296529d2fc39830  # v4.3.0
      with:
        path: ~/.hex
        key: ${{ runner.os }}-hex-registry-${{ hashFiles('mix.lock') }}
        restore-keys: ${{ runner.os }}-hex-registry-
    - name: Install phx_new archive
      run: mix archive.install --force hex phx_new
    - name: Generate fresh Phoenix app
      run: |
        cd /tmp
        mix phx.new tmp_app --no-dashboard --no-gettext --install <<< "Y"
    - name: Point tmp_app at local Sigra
      run: |
        cd /tmp/tmp_app
        # prepend {:sigra, path: "$GITHUB_WORKSPACE"} to mix.exs deps list
        # (planner picks regex or elixir script to patch deps/0)
        mix deps.get
    - name: Run mix sigra.install
      working-directory: /tmp/tmp_app
      env: { PGUSER: postgres, PGPASSWORD: postgres, PGHOST: localhost }
      run: mix sigra.install --yes
    - name: Compile with warnings-as-errors
      working-directory: /tmp/tmp_app
      run: mix compile --warnings-as-errors
    - name: Run fresh app's migrations
      working-directory: /tmp/tmp_app
      env: { PGUSER: postgres, PGPASSWORD: postgres, PGHOST: localhost }
      run: mix ecto.create && mix ecto.migrate
```

Key decisions the planner must make:
1. **`--install` vs manual `mix deps.get`** — `mix phx.new --install` runs hex fetch inline. Need to decide whether to skip `--install` and do it manually AFTER patching `mix.exs` to add the path dep. Either works; the cleaner pattern is `mix phx.new --no-install`, then sed/Elixir-script the path dep in, then `mix deps.get`.
2. **How to patch `mix.exs` to add `{:sigra, path: "#{GITHUB_WORKSPACE}"}`** — cleanest is a short inline Elixir script using `File.read!/write!` with a known anchor line. Avoid sed fragility.
3. **Does `mix sigra.install` have a non-interactive `--yes` / `--force` mode today?** Verify against `lib/mix/tasks/sigra.install.ex`. If not, adding one is part of this phase (it's a real DX gap). [ASSUMED — not yet verified against task source]

### Pattern 2: `example_http_smoke` job — boot + curl

**What:** Boot `test/example` in `MIX_ENV=dev` against the services Postgres, with `mix phx.server` running in the background. Poll `http://localhost:4000/` until 200 OK, then run a bash loop of `curl -o /dev/null -w "%{http_code}" <url>` against the six routes in D-13 and fail on any 5xx.

**Why MIX_ENV=dev:** The Playwright and HTTP smoke jobs need `/dev/mailbox` (Swoosh dev mailbox) which is compile-gated on `Application.compile_env(:example, :dev_routes)` [VERIFIED: test/example/lib/example_web/router.ex:86]. Config enables `dev_routes: true` only in `dev`/`test`. Playwright and http_smoke both need dev mode so the dev_routes scope compiles in.

**Seed data:** The six routes in D-13 are mostly GETs that don't require a user — the critical non-500 check works against an empty DB. `/users/sudo` is the one route that requires auth (it's inside `:require_authenticated`); for the HTTP smoke test, hitting `/users/sudo` without auth should 302 to `/users/log_in`, not 500. That's still "non-500" so the assertion passes. [VERIFIED: test/example/lib/example_web/router.ex:66-80]

**Sketch:**
```yaml
example_http_smoke:
  name: Example HTTP smoke (boot + curl routes)
  steps:
    - ... checkout / setup-beam / cache ...
    - name: Setup example DB
      working-directory: test/example
      env: { MIX_ENV: dev, PGUSER: postgres, PGPASSWORD: postgres, PGHOST: localhost }
      run: mix ecto.create && mix ecto.migrate
    - name: Boot example app in background
      working-directory: test/example
      env: { MIX_ENV: dev, PGUSER: postgres, PGPASSWORD: postgres, PGHOST: localhost }
      run: mix phx.server &
    - name: Wait for app to respond
      run: |
        for i in {1..30}; do
          curl -sf http://localhost:4000/ && break
          sleep 1
        done
    - name: Curl critical routes
      run: |
        set -e
        for path in / /users/register /users/log_in /users/sudo /dev/mailbox /users/sessions; do
          code=$(curl -s -o /dev/null -w "%{http_code}" -L --max-redirs 5 "http://localhost:4000${path}")
          if [[ "$code" -ge 500 ]]; then
            echo "FAIL: ${path} returned ${code}"; exit 1
          fi
          echo "OK:   ${path} → ${code}"
        done
```

### Pattern 3: `example_playwright_smoke` job — full lifecycle

**What:** Same boot-in-background shape as HTTP smoke, then `npx playwright test` runs the golden-path spec under `test/example/priv/playwright/` that drives register → confirm-via-mailbox → login → sudo → session list → MFA enroll (TOTP) → MFA challenge → logout.

**Harness layout (recommended):**
```
test/example/priv/playwright/
├── package.json          # @playwright/test + otplib (or otpauth)
├── playwright.config.ts  # baseURL http://localhost:4000, 1 worker, 1 retry, trace on-first-retry
├── fixtures/
│   └── mailbox.ts        # helper: scrape /dev/mailbox for most-recent email to a given address
└── tests/
    └── golden-path.spec.ts
```

**Confirmation link extraction:** Swoosh's `Plug.Swoosh.MailboxPreview` serves HTML at `/dev/mailbox` listing emails with clickable entries. There is no first-party JSON API in the current Swoosh version, so scraping is the standard pattern:
1. `page.goto('/dev/mailbox')`
2. Click the most-recent email for the registered address.
3. `page.frameLocator('iframe').locator('a[href*="/users/confirm/"]').first().getAttribute('href')`
4. `page.goto(extractedHref)` — lands on the confirmation LiveView and auto-confirms via the URL token.

[CITED: Plug.Swoosh.MailboxPreview — the preview plug is mounted in `test/example/lib/example_web/router.ex:89` and is the standard Swoosh dev pattern]

**TOTP flow:** MFA enrollment renders a QR code and the raw secret as plaintext fallback text (this is standard — see `mfa_settings_live.ex`). The harness reads the secret from the DOM (e.g., `[data-testid="mfa-secret"]` or an element the planner adds) rather than OCR'ing the QR. Then `otplib.authenticator.generate(secret)` returns the 6-digit code, which the harness posts to the enrollment confirm form, then to the challenge form on next login.

**If no `data-testid` hook exists:** Adding one to `mfa_settings_live.ex` is a tiny repair task and belongs in this phase, not a follow-up. The planner should include it.

**Retries and flakiness:** Playwright Test supports `retries: 1` in config. D-15 forbids `continue-on-error` but does not forbid per-test retries. Retries are fine for network/timing flake (app-boot race); they are not fine for masking real bugs. The planner should set `retries: 1` and add a NOTE that any test failing twice is a real bug to fix at the root.

### Pattern 4: Hybrid LiveView + controller login (D-12)

This is the canonical Phoenix 1.8 `phx.gen.auth` shape. The LoginLive renders the form; the form POSTs to `SessionController.create/2` which is a plain controller. The controller calls `Auth.get_user_by_email_and_password/2` + `UserAuth.log_in_user/2`.

**Current state:**
- Router already has `post "/log_in", SessionController, :create` [VERIFIED: test/example/lib/example_web/router.ex:61]
- Template already sets `action={~p"/users/log_in"}` [VERIFIED: test/example/lib/example_web/live/login_live.ex:45]
- Template has `phx-update="ignore"` which is correct phx.gen.auth pattern — the LiveView does NOT handle form submit, the browser does a full HTTP POST. [VERIFIED: test/example/lib/example_web/live/login_live.ex:45]
- **BUT** the form is missing `phx-submit` explicitly set to nothing, and/or is inside a LiveView container that swallows submits. The UAT report B9 says "both `page.click()` and `form.submit()` are swallowed — no HTTP POST leaves the browser."

**Root cause hypothesis:** The `<.form>` component renders `<form phx-submit>` unless you pass `phx-submit={nil}` or omit it. With `:let={f}` + no `phx-submit`, the LiveView intercepts. The fix is either:
1. Add `phx-submit={nil}` to the `.form` component call, OR
2. Use a raw `<form>` element inside the LiveView (bypasses all phx-* attrs), OR
3. (Cleanest per phx.gen.auth) — render the login form outside a LiveView entirely: make the login page a plain controller + HEEx template (`SessionController.new/2`), not a LiveView.

Option 3 is what `phx.gen.auth` actually does: the login page is `Auth/login_html.ex` + `Auth.SessionController.new/2`, NOT a LiveView. The library has a `priv/templates/sigra.install/login_html.ex` file already. [VERIFIED: priv/templates/sigra.install/login_html.ex exists]

**Recommended fix:** Option 3 — rip `LoginLive` out and replace with `SessionHTML.new/1` + `SessionController.new/2`. Magic-link flow is already a plain controller (`SessionController.create` with `_action: "magic_link"` param dispatch [VERIFIED: priv/templates/sigra.install/session_controller.ex:12]). This realigns the example app and the templates to the phx.gen.auth canonical shape in one move.

**Template sync (D-07):** Update `priv/templates/sigra.install/` to not emit `login_live.ex` at all (or emit it as an optional extra), and wire the installer to generate `login_html.ex` + `session_controller.ex` as the default. The `login_html.ex` template already exists — the installer just needs to stop emitting `login_live.ex` as the primary login page.

### Anti-Patterns to Avoid

- **Dual write to two session tables (B6 root cause).** If both `user_tokens` and `user_sessions` exist post-repair, the wrong one will be queried somewhere. Drop `user_tokens` + `user_token.ex` + `generate_user_session_token` entirely from `test/example` AND from `priv/templates/sigra.install/`. The Sigra canonical store is `user_sessions`.
- **Curl-only smoke without browser coverage.** HTTP 200 from `curl /users/log_in` does not prove JS works, LiveSocket connects, or form submit reaches the controller. B1–B4 were all invisible to curl. Keep both `example_http_smoke` (fast signal) AND `example_playwright_smoke` (real integration signal).
- **Masking flakes with `continue-on-error`.** D-15 forbids this. Flake = fix the root cause.
- **Parallel migrations for `users.id` type change.** Changing a PK type from bigint to uuid in an existing DB requires a full migration cascade (new column, data copy, FK redirect, swap). For `test/example/` the right move is to DROP the migration files and rewrite them with `primary_key: false` + `:binary_id` from the start — there is no "beta user migration" concern for the example app itself. For the library template (D-10), the installer is only run on fresh projects, so the same "emit uuid from the start" approach works. No data migration needed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TOTP code generation in Playwright | Custom SHA-1 HMAC loop | `otplib` or `otpauth` npm package | RFC 6238 has subtle time-window + drift handling. Both packages are audited and handle `generate(secret, { timestamp })`. |
| `/dev/mailbox` email scraping via regex on raw HTML | Roll own Plug responder | `page.frameLocator('iframe').locator('a[href*="/users/confirm/"]')` in Playwright | Swoosh's MailboxPreview renders emails in an iframe. Playwright's frame locator handles this directly. |
| Fresh Phoenix app generation in CI | Hand-write a minimal Phoenix scaffold | `mix phx.new tmp_app --no-dashboard --no-install` | `phx.new` is the canonical scaffold. Anything less doesn't prove the generator works against a real Phoenix app. |
| Background process management for `mix phx.server` in CI | systemd/supervisor tricks | `mix phx.server &` + curl poll loop (30 × 1s) | GitHub Actions runners are ephemeral; the simplest pattern is job-scoped background. |
| Test-containers / docker-in-docker for Postgres | Anything | GitHub Actions `services: postgres` block | Already used by `library_tests` and `example_app_smoke`. Reuse. |
| Patching `tmp_app/mix.exs` to add `{:sigra, path: ...}` dep | Complex AST rewrite | Short inline Elixir script that `String.replace/3` on a known anchor line | `mix phx.new` output is stable. A single anchor replacement is enough and is cheap to re-verify if Phoenix ever changes the anchor. |

**Key insight:** The whole phase is "wire existing pieces together correctly." Zero new library surface area. Every fix has a canonical answer from either `phx.gen.auth` (login form shape, sudo pattern) or the Sigra library (`Sigra.Auth.create_session`, `Sigra.Auth.request_confirmation`, `Sigra.Audit` schema).

## Common Pitfalls

### Pitfall 1: Template drift is the real DX bug
**What goes wrong:** Repairing `test/example/` without repairing `priv/templates/sigra.install/*` leaves the installer output broken for every new user, while masking the problem for Sigra's own CI.
**Why it happens:** `test/example/` looks like "the app" but it IS the generator's output snapshot. They must be kept in lockstep.
**How to avoid:** For every repair task, pair it with a template-sync task. Rely on `install_smoke` as the forward-looking guard.
**Warning signs:** Repair tasks that touch only `test/example/` and not `priv/templates/sigra.install/*` for a symmetric file should be flagged in plan-check.

### Pitfall 2: LiveView form submit swallowing (B9)
**What goes wrong:** `<.form action={...}>` inside a LiveView still registers `phx-submit` unless explicitly nulled. The browser form submit becomes a LiveView event, no HTTP POST leaves the browser, and the controller never runs.
**Why it happens:** `Phoenix.Component.form/1` sets `phx-submit` automatically when inside a LiveView unless told not to.
**How to avoid:** Either (a) make the login page a plain controller/HEEx (not a LiveView) — the `phx.gen.auth` canonical shape — or (b) use a raw `<form action=...>` element bypassing `.form`. Option (a) is strongly preferred and matches `priv/templates/sigra.install/login_html.ex` which already exists.
**Warning signs:** Any LiveView containing a `<.form action=...>` with no `phx-submit={nil}`.

### Pitfall 3: Naked `<.input>` without `:field` or `:value` (B7)
**What goes wrong:** `core_components.ex` declares `attr :value, :any` with no default. Calling `<.input name="sudo[password]" type="password">` without passing `:value` or `:field` raises `KeyError: key :value not found` at render time.
**Why it happens:** Phoenix's `core_components.ex` requires either `:field` (Phoenix.HTML.FormField) or `:value`. `sudo_html.ex` uses a naked form (`for={%{}}`) without a form field wrapper.
**How to avoid:** Either pass `value={nil}` on the `<.input>`, or wrap the form with `for={to_form(%{"password" => ""}, as: "sudo")}` and use `field={f[:password]}`. Wrapping is cleaner and matches the rest of the codebase style.
**Warning signs:** Any `<.input>` without `:field=` and without `:value=`.

### Pitfall 4: ex_doc `formatters:` list clobbering the default
**What goes wrong:** Setting `formatters: ["html"]` in mix.exs docs config explicitly disables the markdown formatter, and with it `llms.txt` generation.
**Why it happens:** Providing the option replaces the default; it does not extend it.
**How to avoid:** Either set `formatters: ["html", "markdown"]` explicitly, or remove the `formatters:` key entirely so the default (html + markdown) applies.
**Warning signs:** `mix docs` runs cleanly but `doc/llms.txt` is absent.

### Pitfall 5: `install_smoke` wall-clock spiraling
**What goes wrong:** Fresh `mix phx.new` + `mix deps.get` + `mix sigra.install` on every PR downloads the entire hex registry + every dep, potentially 3-5 minutes per run.
**Why it happens:** No cache on `~/.hex` means full re-download every run.
**How to avoid:** Cache `~/.hex` keyed on `mix.lock`. The Sigra library deps are cached separately (shared with `library_tests`). `tmp_app` builds its own `_build`, which is ephemeral — do NOT cache `tmp_app` itself because the whole point is to prove fresh-install works.
**Warning signs:** Job duration over 5 minutes or download logs showing full registry fetch.

### Pitfall 6: Bigint→uuid PK flip in already-existing rows
**What goes wrong:** In a long-lived DB, changing `users.id` from bigint to uuid requires a multi-step zero-downtime migration (add new column, backfill, swap FKs, drop old). For `test/example/` and fresh installer output this is overkill.
**Why it happens:** Trying to write a migration that preserves existing rows.
**How to avoid:** `test/example/` has no production data. Drop the existing migrations and rewrite them from scratch to emit uuid from the start. For library users who already installed Sigra in bigint mode before this flip, the D-10 guidance is documentation-only: "if you already ran `mix sigra.install` with bigint, here is the manual migration template" — NOT an automated path.
**Warning signs:** A migration task attempting to `ALTER COLUMN ... TYPE uuid`.
