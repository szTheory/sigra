<objective>
Rename the existing `example_app_smoke` CI job to `example_unit_smoke` to match the naming of the three new smoke jobs (install_smoke, example_http_smoke, example_playwright_smoke), and document the branch protection update so a maintainer remembers to add the five required checks in the GitHub settings UI.

Purpose: After plans 06 and 07 land, CI has four smoke jobs. The existing job's name does not match the new pattern. Renaming clarifies the signal layers:
- example_unit_smoke — ExUnit ConnTest suite (fast, what this job is)
- example_http_smoke — curl the routes
- example_playwright_smoke — browser lifecycle
- install_smoke — fresh install

But renaming a required status check DROPS the existing required check on the old name — a subtle way to accidentally lower the bar. This plan pairs the rename with an explicit human checkpoint so a maintainer updates branch protection in the same PR (or immediately after).

This plan runs in WAVE 3 after plans 06 and 07 because the other smoke jobs must exist before the rename makes naming sense.
Output: Job renamed in ci.yml, RUNBOOK updated with the branch-protection update instruction, and a human-verify checkpoint confirming the maintainer applied the settings.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repo maintainer → GitHub branch protection settings | Manual configuration outside workflow YAML; protected by GitHub permissions |
| CI workflow → required-check coupling | Job name is the coupling; rename breaks existing required-check |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10.1.1-08-01 | Tampering | Silent drop of required check via rename | mitigate | This plan's entire reason for existence is to pair the rename with the branch-protection update. The human-verify checkpoint (Task 3) is the blocking gate — without it, the rename silently removes the example_app_smoke required check from any branch protection rule that still lists it. |
| T-10.1.1-08-02 | Denial of service | Maintainer forgets to update branch protection | mitigate | Three layers of reminder: (a) the checkpoint Task 3 blocks plan completion, (b) the RUNBOOK entry from Task 2 is a permanent reference, (c) the acceptance criterion requires the operator to paste the final required-checks list in the resume signal. |
| T-10.1.1-08-03 | Elevation of privilege | PR merged without all checks passing because of stale config | mitigate | By requiring explicit human confirmation of the new set of five required checks, the window where a PR could merge with an outdated required-check list is closed. The operator must confirm the rename is reflected in settings. |
| T-10.1.1-08-04 | Tampering | Maintainer adds continue-on-error later | accept | Out of band of this plan. D-15 is documented in the RUNBOOK as the policy; enforcement is by code review discipline. A future lint rule could forbid continue-on-error in ci.yml — deferred. |
</threat_model>
