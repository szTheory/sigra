## Decisions Made

- **Wire audit at both example and installer template level** — The original plan assumed B8 was purely a type-mismatch bug. Investigation revealed the deeper root cause: `sigra_config/0` never wired `:audit.audit_schema` in either the example app or the installer template, so `Sigra.Audit.log_safe/2` was a silent no-op regardless of types. Fixed at both layers so the install_smoke CI job (plan 06) will forward-verify the fix on fresh `mix phx.new + mix sigra.install` apps.
- **Query through AuditEvent schema in the test** — Ecto.UUID cast on raw `"audit_events"` fragment queries returns 16-byte binary tuples, not `"xxxxxxxx-xxxx-..."` strings. Using the `AuditEvent` schema module gives proper uuid cast and allows direct `==` comparison to `user.id`.
- **Align sigra.gen.oauth with sigra.install** — The plan only required sigra.install to flip. Applied the same flip (and corresponding template EEx branches) to sigra.gen.oauth so host apps don't get a mismatched schema if they run both installers.
- **No `--primary-key` flag (D-11 respected)** — Plan forbade the flag. Manual migration path documented in guides instead.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing Critical Functionality] Wire `:audit.audit_schema` into example_app sigra_config/0**
- **Found during:** Task 1 RED gate (test fails at `audit_count() > before_count` because no row is ever inserted)
- **Issue:** The plan assumed B8 was solely a type mismatch, but `Example.Accounts.sigra_config/0` never wired `:audit.audit_schema`, so `Sigra.Audit.log_safe/2` was a silent no-op. Even with types aligned the test would still fail.
- **Fix:** Added `audit: [audit_schema: Example.Accounts.AuditEvent]` to the config struct.
- **Files modified:** `test/example/lib/example/accounts.ex`
- **Verification:** After this fix, `Sigra.Auth.create_session/4` produces inserts that surfaced the next bug (#2 below).
- **Committed in:** `949f182` (Task 2 commit)

**2. [Rule 2 — Missing Critical Functionality] AuditEvent schema missing binary_id primary key override**
- **Found during:** Task 2 verification run (first post-fix run surfaced `not_null_violation` on `audit_events.id`)
- **Issue:** After wiring audit, every insert failed because the AuditEvent schema had default integer auto-generation, but the DB column was `binary_id` — Ecto did not autogenerate an id, and the column rejected NULL.
- **Fix:** Added `@primary_key {:id, :binary_id, autogenerate: true}` + `@foreign_key_type :binary_id` to `Example.Accounts.AuditEvent`. The installer template already had this under a `<%= if binary_id do %>` conditional, but the host-app copy had drifted.
- **Files modified:** `test/example/lib/example/accounts/audit_event.ex`
- **Verification:** Full example_app suite (46 tests) GREEN after fix.
- **Committed in:** `949f182` (Task 2 commit)

**3. [Rule 2 — Missing Critical Functionality] Installer template auth.ex also did not wire audit**
- **Found during:** Task 3 (while reviewing the installer template for the default flip)
- **Issue:** `priv/templates/sigra.install/auth.ex` `sigra_config/0` omitted the `:audit` keyword entirely, meaning fresh `mix sigra.install` host apps would hit exactly the same B8 silent-no-op bug. Flipping the binary_id default alone would not resolve it for fresh installs.
- **Fix:** Added `audit: [audit_schema: <%= context_module %>.AuditEvent]` to the template's sigra_config/0.
- **Files modified:** `priv/templates/sigra.install/auth.ex`
- **Verification:** Installer test suite (19 tests) + installer_drift_test suite GREEN; plan 06 install_smoke will forward-verify on a fresh host app.
- **Committed in:** `d1d2c40` (Task 3 commit)

**4. [Rule 2 — Missing Critical Functionality] sigra.gen.oauth did not honor binary_id**
- **Found during:** Task 3 (plan Step 2 called for checking sigra.gen.oauth binary_id handling)
- **Issue:** `sigra.gen.oauth` had no binary_id switch and its templates (`oauth_migration.exs`, `user_identity.ex`) had no EEx branches for binary_id, so after flipping sigra.install's default the two generators would emit mismatched schemas (user is uuid, user_identity FK is bigint) — cascading type mismatch back into the user_identities table.
- **Fix:** Added `binary_id: :boolean` switch + `binary_id: true` default to `@default_opts`, threaded into binding, and added EEx conditionals to the two templates matching the sigra.install pattern.
- **Files modified:** `lib/mix/tasks/sigra.gen.oauth.ex`, `priv/templates/sigra.gen.oauth/oauth_migration.exs`, `priv/templates/sigra.gen.oauth/user_identity.ex`
- **Verification:** Library suite GREEN after updating `test/sigra/install/oauth_generator_test.exs` for the new template shape.
- **Committed in:** `d1d2c40` (Task 3 commit)

**5. [Rule 1 — Bug] oauth_generator_test assertion too strict**
- **Found during:** Library test run after Task 3 template edits
- **Issue:** `String.contains?(content, "create table(:user_identities)")` asserted the exact legacy string, which no longer exists after adding the EEx conditional (`:user_identities<%= if binary_id do %>, primary_key: false<% end %>`). Test was validating the raw template file, not an EEx-evaluated result.
- **Fix:** Loosened the assertion to a prefix match `create table(:user_identities` and added a new test covering the binary_id branches in the template.
- **Files modified:** `test/sigra/install/oauth_generator_test.exs`
- **Verification:** 24 tests in the oauth_generator_test file GREEN (previously 23 + 1 failure).
- **Committed in:** `d1d2c40` (Task 3 commit)
