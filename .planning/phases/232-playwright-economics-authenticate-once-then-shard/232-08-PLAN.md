<objective>
Convert the seventh and last prelude call site — the GitHub Pages publisher — and rewrite the guard
that stands in the way, preserving its intent rather than its implementation.

Purpose: `p15-pages-publisher-seeds-before-boot.test.mjs` is the hardest constraint in PW-03. Its
`stepList()` splits the publish job on `^ {6}- ` and labels each step by its `^ {6}- name:`, then
`seedsOrderingIssue()` requires a step literally named `Setup example dev DB`, a step whose name starts
`Boot example app`, exactly one step whose raw text matches a `seeds.exs` invocation, that seeds step
strictly between the other two, and no `if:` on it. Replacing those steps with a single `uses:` makes
all three lookups fail and the guard returns its "the parse broke, this is not a pass" sentinel — a
hard red on the *intended* refactor. That makes the rewrite a deliverable with recorded justification,
not incidental collateral (D-30, RESEARCH § The three remediations).
Output: a `uses:`-aware `p15` that still fails on every original violation, and the publisher converted.
</objective>

Rewrite `p15` so it evaluates the publish job's *effective* step sequence rather than its literal one,
and land the rewrite before the workflow changes — the new guard must accept both the current literal
shape and the post-conversion `uses:` shape, so neither commit in this plan is ever red.

Add a resolver beside `stepList()`: given a parsed step whose label is
`uses:./.github/actions/boot-example-app`, read the composite through `readRepoFile()`, strip its YAML
comments with the same helper, extract its `runs.steps` list with a splitter written for the
composite's own indentation (composite steps sit under `runs:` -> `steps:` at a shallower indent than a
workflow job's), and return those steps in the same `{ name, hasCondition, text }` shape `stepList()`
produces. If the composite path does not resolve, or its step list is empty, return the "the parse
broke, this is not a pass" sentinel — a missing composite is a broken run, never an absent violation.

Then flatten: walk the publish job's step list and, wherever a composite `uses:` step appears, splice
that composite's resolved steps into its position. Run the existing `seedsOrderingIssue()` unchanged
over the flattened list. Every original assertion then holds on its original terms — one seeds step,
strictly between `Setup example dev DB` and the step whose name begins `Boot example app`.

The one place the original check needs a deliberate reinterpretation is the no-`if:` rule. The
composite's seeds step legitimately carries `if: inputs.seeds == 'true'`, and the original rule existed
because a condition referencing a `changes` job this workflow does not have evaluates empty and never
runs. Preserve the *intent* by making the rule stronger rather than weaker: when the seeds step comes
from a composite, its condition may reference only the composite's own inputs, and the guard must
additionally assert that the caller's `uses:` step passes an explicit `seeds:` value equal to the
string `true`. Assert both halves — either alone is satisfiable while the app boots unseeded. When the
seeds step comes from a literal caller step, the original no-condition rule applies unchanged.

Extend the negative-control fixtures so each new failure mode is proven to red, using the existing
fixture idiom (a synthetic workflow string plus, now, a synthetic composite string, both driven through
the same pure functions): a composite with no seeds step; a composite whose seeds step sits after the
boot step; a composite whose seeds step is gated on something other than its own inputs; a caller that
omits the `seeds:` input entirely; a caller that passes `seeds: 'false'`; and an unresolvable composite
path. Keep both original fixtures.

Rewrite the header's four parts. The prohibition sentence and the "what silently breaks" paragraph
stand as-is in substance. Correct the factual errors RESEARCH C-5 found: the four `ci.yml` seeds line
numbers cited (`:1288`, `:1950`, `:2258`, `:2506`) are all stale, and the claim that all four
example-booting `ci.yml` jobs seed is wrong — `example_http_smoke` boots without seeding and does so
deliberately. Replace the line citations with job-id references. Add a paragraph recording that Phase
232 rewrote this guard to follow the `uses:` indirection, why (the composite made the literal step-name
walk unresolvable), and what was strengthened rather than relaxed (the caller's input value is now
asserted, which the original could not check because there was no input).
