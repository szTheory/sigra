<objective>
Make the two claims that PW-02 cannot prove by reading YAML *provable on demand*, and pin the topology
they depend on with a contract that runs on every PR.

Purpose: D-22 says a job whose `needs` dependency failed is skipped and a skipped required check
reports success. That is an assertion about GitHub's behaviour, not about this repository, and the only
honest way to show the aggregator reds is to make a leg red and read the aggregator's conclusion —
which is exactly why Phase 231's GATE-03 became credible. This plan builds the mechanism that lets plan
232-13 capture that observation, and pins every structural property SC-2 and SC-3 rest on so a later
phase cannot quietly undo the split.
Output: a dispatch-only `force_shard_fail_probe` input and its one-leg probe step, plus
`test/sigra/planning/phase_232_playwright_shard_topology_test.exs`.
</objective>

The input is `force_shard_fail_probe`: `required: false`, `type: boolean`, `default: false`, with a
`description` in the same voice as its two siblings — that it intentionally fails a single Playwright
shard leg so the fail direction of the `Example Playwright smoke (full lifecycle)` aggregator is
provable on demand, and that it is for probing only.

The probe step goes inside `example_playwright_shard` as its **first** step, named
`Forced-failure probe (shard aggregator self-test)`. Its `if:` is the conjunction of
`inputs.force_shard_fail_probe` and `matrix.seam == '<the first value in the matrix list>'` — one leg,
not all of them, so the same run demonstrates two things at once: `fail-fast: false` lets the sibling
legs run to completion, and `needs.<matrix-job>.result` is `failure` when any single leg failed. Its
body echoes a banner naming the input, the leg, and what the run is proving, then exits 1. Because it
is the first step, the probe leg fails in seconds rather than after a full boot — the point is the
aggregator's conclusion, not the leg's work.

Two properties matter more than the mechanics. First, `inputs.*` is null on `push`, `pull_request` and
`schedule`, so this step cannot fire on any event but a dispatch that explicitly sets the flag; state
that in a comment rather than relying on a reader knowing it. Second, when the flag is absent the step
is a total no-op — no banner, no side effect, no change to any other step's behaviour. Do not implement
the probe as a `continue-on-error` step, an env var production code reads, or a conditional that alters
a real run's arguments.

Add a short comment above the step recording why the probe exists: a job whose `needs` dependency
failed is *skipped*, GitHub reports a skipped required check as *success*, and the only honest proof
that `if: always()` closes that hole is to make a leg red and read the aggregator's conclusion — the
same argument Phase 231's GATE-03 settled by observation rather than by reasoning.
