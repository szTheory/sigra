Extracting a composite consumed by seven jobs across two workflows is a one-way change in practice:
after plans 232-07 and 232-08 land, the prelude has exactly one definition, three guards

The planner's recommended answers, with their reasoning, are below. Approving them ratifies them.

**(1) Scope — all seven call sites, including `example_unit_smoke`.**
RESEARCH Open Question 3 recommends excluding `example_unit_smoke` because SC-4's wording is "the jobs
that boot the app" and that job does not boot. The recommendation here is the opposite: include it,
with `boot: 'false'`, `node: 'false'`, `seeds: 'false'`, `browsers: 'none'`, `mix-env: 'test'`. The
`boot`, `node`, `seeds` and `browsers` inputs are needed regardless (`example_http_smoke` already needs
`boot: 'true'` with `node: 'false'` and `seeds: 'false'`), so including the seventh site costs exactly
one additional axis — `mix-env` — which the deps-cache key needs anyway. Excluding it would leave a
verbatim duplicate of the prelude standing while the phase claims "defined once", which is a scope
reduction dressed as a reading of SC-4.

**(2) Cache split — deps cache inside, browser cache outside.**
CONTEXT D-27 states the composite "must not unconditionally include an `actions/cache` step" because
`admin_eval_render` declares none as a deliberate structural guarantee. RESEARCH correction C-4 shows
that statement is factually wrong: `admin_eval_render` *does* declare one (`ci.yml:2581-2591`, id
`admin_eval_render_deps_cache`). What it declares no cache for is `~/.cache/ms-playwright`. D-27's
intent — do not re-open the Phase 231 GATE-04 bug — stands and is served by keeping the **browser**
cache caller-owned. Its stated fact does not, and following the stated fact would leave the largest
duplicated block unfactored and SC-4 unmet. Keeping the browser-cache key literal in `ci.yml` also
means `scripts/ci/playwright-cache-key-guard.sh:56-62` needs no change at all, which is one fewer guard
to rewrite.

**(3) Gating stays at the caller.** The `if: needs.changes.outputs.docs_only != 'true'` conditions move
onto the single `- uses:` step, never inside the action, so `p10` and `honest-skip-verdict.sh` can still
resolve them from `ci.yml`.

**(4) `seeds` defaults to `'false'`.** `example_http_smoke` is the only app-booting job with no seeds
step (RESEARCH C-5, which also shows `p15`'s own header comment is wrong about this). A true default
would silently seed it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Third-party action -> runner | Four `uses:` steps execute untrusted code on a runner with repo checkout access |
| GitHub Actions cache -> job filesystem | A restored cache entry becomes trusted build input for seven jobs |
| Composite -> caller environment | `$GITHUB_ENV` writes inside a composite leak outward into the caller's later steps |
