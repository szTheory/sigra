## Summary

The continuation data model has sound one-time-claim and fresh-session-binding mechanics, but the browser handoff leaks the PKCE verifier through a GET URL. The proof runner also overstates exact-input evidence when ignored runtime files affect a run, and terminal audit recording silently drops database failures.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: PKCE verifier is exposed in the browser URL

**Classification:** BLOCKER

**File:** `/Users/jon/projects/sigra/test/example/lib/example_web/controllers/crosswake_controller.ex:10-19`

**Issue:** `start/2` serializes `values.pkce_verifier` into the `Location` of a `303` GET request. The verifier is therefore retained in browser history and can be captured by reverse-proxy/access logs, browser extensions, endpoint security tools, or any other URL telemetry before the return response applies `Referrer-Policy`. `config.exs` only filters Phoenix parameters; it cannot protect upstream logs or client history. Possession of this value together with the continuation/state URL material defeats the intended confidentiality of the PKCE correlation secret.

**Fix:** Keep the verifier out of the URL. Store it in a server-side, continuation-bound record (or an HttpOnly host session keyed by the opaque handle), and accept only the opaque continuation plus state on the fixed return route. For example, persist a verifier digest plus a server-only encrypted verifier/transport reference, then remove `"pkce_verifier" => values.pkce_verifier` from the redirect query and resolve it after the continuation is atomically claimed. Add an integration test asserting the redirect URL, browser history, and subsequent request URL never contain the verifier.

## Warnings

### WR-01: Terminal outcome persistence failures are discarded

**Classification:** WARNING

**File:** `/Users/jon/projects/sigra/test/example/lib/example/accounts/crosswake_continuations.ex:48-52`

**Issue:** `record_outcome/2` returns `Repo.update/1`, but `complete/5` ignores that value and returns the evaluator decision. A transient database error after the atomic claim leaves a consumed row with no outcome/reason, while callers receive an allow or deny result. This breaks the stated outcome/audit record contract and makes security investigations unable to distinguish an allowed return from a failed write.

**Fix:** Make outcome recording part of the operation result. Handle `{:error, changeset}` explicitly (with a durable retry/outbox if the authorization result must remain available), and add tests that force `Repo.update/1` failure and assert the selected failure policy rather than a silently incomplete continuation record.

### WR-02: Exact-SHA receipt guard ignores untracked ignored runtime inputs

**Classification:** WARNING

**File:** `/Users/jon/projects/sigra/scripts/ci/lib/exact-sha-worktree.sh:28-35`

**Issue:** `git ls-files --others --exclude-standard` intentionally omits ignored files. The proof runner compiles, migrates, seeds, and starts the host using runtime configuration, so an ignored configuration or source-adjacent runtime input can change the exercised behavior without being reflected in the clean-worktree check or receipt. The resulting receipt claims an exact committed SHA although not all effective test inputs were verified.

**Fix:** Either fail when relevant ignored inputs exist (with an explicit allowlist for build artifacts and the receipt), or record a redacted fingerprint of every allowed runtime input such as `tmp/db.env` and host configuration. Add a helper test that creates an ignored relevant input and verifies the guard rejects it or includes it in the evidence.
