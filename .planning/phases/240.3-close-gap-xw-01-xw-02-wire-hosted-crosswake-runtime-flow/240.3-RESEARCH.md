## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Wire the runtime flow in `test/example` as a host-owned reference integration. Keep `crosswake_sigra`, the raw cookie/session seam, host schemas, routes, navigation, and Crosswake policy outside Sigra core and canonical generated B2C templates.
- **D-02:** Use thin Phoenix controller endpoints over explicit Accounts-context operations. Do not make the flow LiveView-only or hide the start/return workflow in a broad evaluator Plug. Shared pipelines may fetch and protect normal browser-session state, but the controller owns HTTP orchestration and response mapping.
- **D-03:** Use an authenticated, CSRF-protected `POST` start route under the normal browser/authentication pipeline. Put the return route under the normal browser/session-fetching pipeline without an automatic authentication redirect, so missing or changed session state is handled as an explicit fail-closed return.
- **D-04:** At departure, freshly resolve the canonical backend SIGRA session and user, derive the opaque expected `session_ref`, `subject_ref`, and exact session version, then persist them in a short-lived, database-backed, one-time continuation record.
- **D-05:** Address each continuation with a random 256-bit opaque handle and store only its digest. The record contains the expected opaque binding, an immutable internal `route_id`, timestamps, expiry, consumption state, and optional redacted outcome metadata. It never contains a raw session token/cookie, token hash, user/database session ID, OAuth/provider credential, Crosswake authority payload, or arbitrary URL.
- **D-06:** On return, atomically claim an unused/unexpired continuation; validate approved return evidence and applicable transaction state/PKCE; freshly resolve and validate the current backend session/user; compare session ref, subject ref, and exact version; then construct facts and invoke the evaluator. Any terminal allow or deny consumes/invalidates the continuation. Binding/session/evidence failures deny before evaluator invocation.
- **D-07:** Return/callback data is evidence and correlation only. It cannot supply or replace the expected binding, SIGRA session, subject, organization, Crosswake route, grant decision, or navigation destination. Recomputing a new expected binding solely from the return-time session is forbidden because it would erase account/session-switch detection.
- **D-08:** Use a fixed host-owned Crosswake route and fixed safe local destination for this phase. If multiple outcomes later become necessary, departure may select a closed server-side `route_id` allowlist stored in the continuation; callback-selected paths, URLs, policy routes, and open redirects remain forbidden.
- **D-09:** Complete successful browser returns with redirect-after-processing semantics, preferably `303 See Other`, leaving no handle, code, binding, or evidence in the final URL or rendered DOM. Do not introduce a Crosswake success interstitial.
- **D-10:** Collapse user-visible denials to safe recovery guidance: either the sign-in session is no longer available and the user should sign in again, or the return could not be completed and should be restarted. Keep forensic distinctions internal as stable redacted reason codes such as `invalid_or_expired_handle`, `already_used`, `invalid_return_evidence`, `oauth_state_or_pkce_failure`, `session_unavailable`, `binding_mismatch`, and `route_denied`.
- **D-11:** Structured logs/telemetry may include an opaque correlation reference and stable outcome/reason class, but never raw query parameters, cookies/tokens, continuation handles, binding values, database identifiers, provider payloads, or return evidence bodies.
- **D-12:** Preserve the Phase 239 database-backed adapter matrix as the authority layer, and add focused continuation-store tests for digest-only lookup, expiry, atomic single use, replay denial, concurrent-flow isolation, and sensitive-field exclusion.
- **D-13:** Add `ConnCase` request-level integration proof through the real router and Plug session for authenticated start, same-session allow, missing/revoked/expired denial, different-account and same-account/different-session denial, replay, smuggled authority/route/destination rejection, safe redirects, generic failure copy, evaluator non-invocation, and telemetry redaction.
- **D-14:** Add one focused deterministic Playwright happy-path journey in `test/example` to prove real cookie-jar departure/return navigation and absence of sensitive material from the final URL/DOM. Keep the negative-security matrix in Elixir tests; use role/label selectors, stable readiness signals, no sleeps, and no retries as evidence substitution.
- **D-15:** Extend the bounded hosted-session proof and machine-readable exact-SHA receipt to run the adapter, continuation, request-level, focused browser, and documentation/contract guards. CI may claim an in-process host reference runtime flow only—not real Google, email, deployment, Crosswake network service, or physical-device success.
- **D-16:** Update the B2C alpha recipe with a copyable host-owned integration outline, explicit dependency placement, start/return flow, fixed-route and continuation rules, recovery behavior, and truthful proof/non-claim boundary. Keep implementation vocabulary out of end-user copy.
- **D-17:** Defer an opt-in Crosswake generator or Sigra public integration abstraction. Promote one only after this reference implementation demonstrates a stable contract across real host needs; do not commit generated migrations, router mutation, configuration, or companion compatibility prematurely.

## Summary

The milestone audit identifies one precise defect: `Example.Accounts.CrosswakeSessionAdapter` has complete database-backed authority tests, but it has no production-style caller; only its own test module invokes `expected_binding/2`, `evaluate/5`, or `evaluate_return/5`. Thus the missing handoff is `request/session -> adapter -> Crosswake evaluator -> evidence/navigation response`. [VERIFIED: `.planning/v1.48-MILESTONE-AUDIT.md`]

Implement the closure entirely in `test/example`: a host-owned Accounts continuation context persists the departure binding under a random handle digest, a thin controller starts and returns the browser transaction, and the existing adapter remains the only place that derives Crosswake facts from a freshly resolved SIGRA session. The return controller must atomically consume the continuation before it delegates to `evaluate_return/5`; all failure categories map to generic recovery and must not invoke the evaluator. [VERIFIED: `240.3-CONTEXT.md`; VERIFIED: `test/example/lib/example/accounts/crosswake_session_adapter.ex`]

No new dependency is needed. `test/example` already pins `crosswake_sigra ~> 0.1.3` and resolves `crosswake 0.2.0`; the Phase 239 release receipt records the package, release SHA, and checksum. This phase adds a runtime consumer and proof only, not a Crosswake network service or generated-host integration. [VERIFIED: `test/example/mix.exs`; VERIFIED: `test/example/mix.lock`; VERIFIED: `239-CROSSWAKE-RELEASE.json`]

**Primary recommendation:** Create an explicit, database-backed one-time continuation context and controller pair in `test/example`; claim by digest with one conditional database update, then run the existing adapter with only server-record binding, fixed route, fresh browser session token, and validated evidence.

### Pattern 1: Server-owned departure binding and digest-only continuation

**What:** On authenticated departure, extract the canonical raw session token from the Plug session, call `CrosswakeSessionAdapter.expected_binding/2`, generate a 32-byte opaque handle, and store only its SHA-256 digest with the adapter’s opaque refs, exact version, fixed route ID, expiry, and unconsumed state. [VERIFIED: `240.3-CONTEXT.md`; VERIFIED: `crosswake_session_adapter.ex`]

**When to use:** Every start request; never reconstruct this data from return parameters or the return-time session. [VERIFIED: `240.3-CONTEXT.md`]

**Example:**

```elixir
# Host-only context sketch; record must never receive raw_token or raw_handle.
with {:ok, binding} <- CrosswakeSessionAdapter.expected_binding(raw_token, now),
     handle <- :crypto.strong_rand_bytes(32) |> Base.url_encode64(padding: false),
     {:ok, _continuation} <- CrosswakeContinuations.issue(handle, binding, "fixed-route", now) do
  {:ok, handle}
end
```

### Pattern 2: Conditional database update is the single-use claim

**What:** Claim the continuation with one query constrained by handle digest, `consumed_at IS NULL`, and `expires_at > now`; only an affected row may progress. Use `Repo.transaction/1` when claim plus outcome update must be one logical unit. [CITED: https://ecto.hexdocs.pm/Ecto.Repo.html]

**When to use:** The first operation on every return, including invalid evidence; this closes parallel replay races. [VERIFIED: `240.3-CONTEXT.md`]

**Example:**

```elixir
from(c in CrosswakeContinuation,
  where: c.handle_digest == ^digest and is_nil(c.consumed_at) and c.expires_at > ^now,
  update: [set: [consumed_at: ^now]],
  select: c
)
|> Repo.update_all([], returning: true)
```

### Pattern 3: Controller maps fixed host outcomes; adapter owns authority projection

**What:** The controller reads only the host session token and claimed record, passes return input as evidence to `evaluate_return/5`, and maps `{:allow, _}` to a local `303` redirect. It maps all terminal denial classes to two generic recovery messages, while recording only redacted reason class internally. [VERIFIED: `240.3-CONTEXT.md`; CITED: https://phoenix.hexdocs.pm/Phoenix.Controller.html]

**When to use:** All browser start/return behavior. Do not move adapter comparisons, route construction, or safe-destination selection into callback parameters. [VERIFIED: `240.3-CONTEXT.md`]

### Anti-Patterns to Avoid

- **Rebinding at return:** Calling `expected_binding/2` solely at return and using that result as expected authority turns an account switch into an allow. Preserve the departure record. [VERIFIED: `240.3-CONTEXT.md`]
- **Read-then-write consumption:** A separate `get` followed by `update` permits two concurrent returns to evaluate. Claim through a single conditional update. [CITED: https://ecto.hexdocs.pm/Ecto.Repo.html]
- **Continuation record as a session cache:** Never store raw token, hash, session/user ID, provider credential, Crosswake payload, URL, or raw evidence. [VERIFIED: `240.3-CONTEXT.md`]
- **Evaluator Plug / LiveView-only ceremony:** Violates D-02 and makes start/return HTTP ownership opaque. [VERIFIED: `240.3-CONTEXT.md`]
- **Callback-directed navigation:** Evidence may be validated but must not select route/destination/authority. [VERIFIED: `240.3-CONTEXT.md`]

## Common Pitfalls

### Pitfall 1: Marking consumption after evaluator execution

**What goes wrong:** Two concurrent callbacks can both see an unused record and reach Crosswake. [ASSUMED]

**Why it happens:** A non-atomic read/validate/update sequence has no single claimant. [CITED: https://ecto.hexdocs.pm/Ecto.Repo.html]

**How to avoid:** Conditional database claim before evidence/session/evaluator work, then test two concurrent attempts produce exactly one eligible claim. [VERIFIED: `240.3-CONTEXT.md`]

**Warning signs:** Replay test checks only a sequential second request, or claim code has `Repo.get` before a later unconditional update. [ASSUMED]

### Pitfall 2: Testing adapter denials without router/session integration

**What goes wrong:** Tests pass while cookie extraction, route pipeline, response status, and final URL remain unwired—the exact audit finding. [VERIFIED: `.planning/v1.48-MILESTONE-AUDIT.md`]

**How to avoid:** Add `ConnCase` endpoint tests that authenticate with the real Plug session and invoke actual start/return routes, then one Playwright cookie-jar path. [VERIFIED: `240.3-CONTEXT.md`; CITED: https://hexdocs.pm/phoenix/Phoenix.ConnTest.html]

### Pitfall 3: Leaking sensitive return material through response or telemetry

**What goes wrong:** A raw handle/code/token appears in a final redirect, flash, rendered page, log event, or evidence receipt. [VERIFIED: `240.3-CONTEXT.md`]

**How to avoid:** Put a `303` before successful final navigation; use generic flash text; test final URL/DOM and captured telemetry metadata for forbidden strings. [VERIFIED: `240.3-CONTEXT.md`; CITED: https://phoenix.hexdocs.pm/Phoenix.Controller.html]

### Pitfall 4: Wrong return pipeline

**What goes wrong:** An authentication plug redirects before the controller can classify a missing/revoked return as fail-closed restart guidance. [VERIFIED: `240.3-CONTEXT.md`]

**How to avoid:** Start route uses `[:browser, :require_authenticated]`; return uses only `[:browser]` and does explicit session result mapping in controller. [VERIFIED: `240.3-CONTEXT.md`; VERIFIED: `router.ex`]

### RESOLVED deterministic local return protocol

The browser path is a local host reference, not a provider simulation. `POST /crosswake/start` freshly resolves the SIGRA session, generates the continuation handle, a separate 256-bit state value, a separate 256-bit PKCE verifier, and an opaque `return_ref`; it persists the SHA-256 handle digest, SHA-256 state digest, and S256 PKCE challenge digest derived from the verifier plus the server-owned `return_ref`, binding, fixed route IDs, issue/expiry timestamps, and redacted correlation/outcome fields. The POST responds `303` to its own `GET /crosswake/return?continuation=...&state=...&pkce_verifier=...` URL. All three query values are transported by the real browser cookie jar, filtered by exact parameter names from Phoenix logs, and are never authority. [VERIFIED: D-03–D-07/D-11]
