**Pattern for a Multi-integrated operation (register example):**

```elixir
# Before
multi =
  Ecto.Multi.new()
  |> Ecto.Multi.insert(:user, user_changeset)
  |> maybe_insert_confirmation_token(...)

case repo.transaction(multi) do
  {:ok, %{user: user}} -> ...
end

# After
audit_opts = [
  audit_schema: audit_schema(config),
  actor_resolver: fn %{user: u} -> u.id end,
  actor_type: "user",
  ip_address: Keyword.get(opts, :ip_address),
  user_agent: Keyword.get(opts, :user_agent),
  metadata: %{method: "password"}
]

multi =
  Ecto.Multi.new()
  |> Ecto.Multi.insert(:user, user_changeset)
  |> maybe_insert_confirmation_token(...)
  |> Sigra.Audit.__log_internal__("auth.register.success", audit_opts)

case repo.transaction(multi) do
  {:ok, %{user: user} = changes} ->
    Sigra.Audit.emit_telemetry_from_changes(changes)
    # existing post-commit logic
    ...
  {:error, :audit, changeset, _} ->
    # new branch — audit changeset failure shouldn't happen for internal callers,
    # but handle it gracefully (log and return a generic error)
    Logger.error("Sigra.Audit internal write failed: #{inspect(changeset.errors)}")
    {:error, :internal_audit_failure}
  {:error, step, reason, _} ->
    # existing error branches unchanged
    ...
end
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Plug.Conn → Auth subsystems | IP and UA captured from conn cross here and flow into audit rows |
| user input → Account/MFA/OAuth subsystems | Business op and audit row share same transaction |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-9-03 | Information Disclosure | Audit metadata in Auth/Session/MFA/OAuth/API/Account integration | mitigate | Every integration site builds metadata from allowlisted fields (user ID, provider name, scopes, outcome reason, method name) and NEVER includes tokens, passwords, or hashes. Enforced by Plan 02 changeset at insert time and by Plan 05 sensitive-data regression test that drives every D-26 operation and asserts forbidden keys are absent. |
| T-9-05 | Repudiation | Audit missing on partial failure | mitigate | `__log_internal__/3` appends to the SAME Multi as the business op. If business insert rolls back, audit row rolls back. If audit changeset fails (shouldn't happen for internal callers since allow_reserved: true), whole transaction fails — operation is rejected, not silently un-audited. |
| T-9-07 | Tampering | D-27 exception for api.token_verify success could be abused to hide a compromised key | accept | Successes are covered by telemetry; SIEM forwarding on telemetry provides observability. Audit trail captures failures (attack signal). Trade-off documented in D-27. |
</threat_model>
