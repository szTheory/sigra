<objective>
Take the two single-line topology wins: stop charging every PR 17m33s of runner time for a job that
gates nothing, and stop letting superseded PR runs run to completion.

`admin_eval_render` is not in `ci-gate.needs` and is not a ruleset context, so demoting it breaks no
gate. It concluded `failure` on the pre-change PR run while `continue-on-error: true` kept that
failure invisible — which is exactly why it must be demoted here and fixed in Phase 231, not both at
once: removing `continue-on-error` now would turn every push to main red and contaminate the "after"
half of the pair this phase is judged on.

The concurrency grouping is chosen so release integrity is structural rather than
expression-dependent: PR runs key on the PR number and supersede each other, while every other event
keys on its own unique run id and therefore sits in a group of one.

Purpose: remove 17m33s from the PR lane and stop paying for superseded runs.
Output: one job-level `if:` and one workflow-level `concurrency:` block.
</objective>

## Flagged Assumptions

One probe-surfaced edge for FAST-04 came back **unclassified** and is carried forward unresolved
rather than silently dropped or auto-backstopped:

- **FAST-04 / unclassified** — the probe could not assign an edge category to
  "superseded PR runs cancelled; main and scheduled runs never cancelled". The residual uncertainty
  is whether a `cancelled` conclusion on a superseded SHA can ever strand a ruleset-required context.
  D-14 records the reasoning that it cannot here (no same-SHA `push`+`pull_request` overlap, so a
  `cancelled` conclusion only ever lands on a SHA that is no longer the PR head), and RESEARCH
  verified the trigger block directly. This is recorded as an assumption, not as a proven truth:
  the AFTER-CANCEL probe in plan 09 observes the superseded run's conclusion but does not prove the
  general case. If a required context is ever observed stranded on a cancelled run, this assumption
  is falsified and FAST-04 must be revisited.

A second assumption worth naming (RESEARCH A2): that `github.run_id` is available in the
workflow-level `concurrency:` context is an established idiom that was not re-verified against the
GitHub docs this session. It is falsified directly and cheaply by the first real push run — if it
were wrong, non-PR runs would share a group and the AFTER-PUSH run would be observed queued or
cancelled.
