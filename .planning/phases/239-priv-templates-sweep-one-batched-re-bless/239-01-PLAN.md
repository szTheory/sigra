<objective>
Build the SC-3 instrument before anything is edited, and freeze the baseline it needs.

Purpose: SC-3 as written in the ROADMAP ("the re-bless diff contains only comment lines") is
structurally wrong at HEAD. Only 80 of the 158 token-bearing lines under `priv/templates/` are
`#`/`//`/`/*` comments; 57 are `@moduledoc`/`@doc` heredoc prose, 4 are single-line `@doc "…"`
strings, and 17 are EEx-escaped HEEx tags. A classifier matching `^[+-]\s*#` would flag 78
legitimate lines as stop-the-line events. This plan replaces that syntactic test with the
**expected-removed-set containment check** (RESEARCH §5.1 option 1), which sidesteps the
definitional argument and is strictly more precise. It also re-runs the RESEARCH §2 union
measurement as the phase's first action, so a moved HEAD is caught before 46 files are edited.

The expected set is the **±1-line neighbourhood** of the union-token lines, not the bare union grep,
because plan 239-02's ledger mandates two block merges that legitimately remove an adjacent non-token
line; and the non-vacuity floor is on `removed_lines` (exactly 139, known pre-sweep) rather than on
`changed_lines`, because 127 of the 158 template lines are pure deletions and the diff's addition
count is not knowable in advance. Both choices exist so the instrument is satisfiable by the correct
diff while staying falsifiable against an incorrect one.

Output: a phase-local, falsifiable classifier; a frozen, deterministically-generated pre-sweep
expected-set snapshot; three committed fixture diffs; and the opening ledger of `239-EVIDENCE.md`.

**Step B — freeze the expected set, as a ±1 neighbourhood rather than the bare union grep.**

The bare union grep is **not** a sufficient expected set, and this is the defect this step exists to
avoid. Plan 239-02's rewrite ledger mandates two *block merges* that join a token line to a
physically adjacent non-token line — `organizations/live/organization_settings_live.ex` (merge `:21`
into `:20`) and `organizations/live/invitation_accept_live.ex` (the wrapped `:19-20` sentence). Both
files are in the golden tree, so a **correct** re-bless diff removes those adjacent non-token lines
too. An expected set built from the union grep alone would score them `nonconforming_removed >= 1`
and trip the stop-the-line rule in plan 239-04 on the success path.

So `239-golden-expected.txt` is the **±1-line neighbourhood** of the union-token lines: for every
union-token hit at `path:N`, emit records for `path:N-1`, `path:N` and `path:N+1` (clamped to the
file's bounds), tagged so the two classes stay distinguishable:

- `T:path:line:text` — a union-token line. Exactly **139** of these, across 35 distinct paths.
- `N:path:line:text` — an adjacent context line admitted only because a documented block merge may
  consume it. Deduplicated; a line that is itself a token line is emitted as `T:`, never `N:`.

`±1` is the right radius by construction, not by taste: every documented merge in the ledger joins a
token line to an *immediately* adjacent line, so `±1` is a superset of the ledger's touched-line set,
and nothing wider is admitted. A merge that needed a radius of 2 does not exist in the ledger; if
plan 239-02 discovers one, that is a **stop-the-line** event to be reported, not a reason to widen
this file after the fact.

Generate it with a single deterministic command — never by hand, and never edited afterwards — and
put that command verbatim on the first line of the file as a `# ` comment, so the contents are
reproducible rather than asserted (the convention `237-docs-attribute-scan.py:1-6` establishes). A
working shape, to be adapted rather than copied blind:

`grep -nE "$U" $(git ls-files test/fixtures/install_golden/tree) | awk -F: '{print $1":"$2}' | while read -r h; do f=${h%%:*}; n=${h##*:}; awk -v f="$f" -v n="$n" 'NR>=n-1 && NR<=n+1 {print (NR==n?"T:":"N:") f ":" NR ":" $0}' "$f"; done | sort -u -t: -k2,2 -k3,3n`

with the `T:`/`N:` collision resolved in favour of `T:`. Whatever mechanism is used, the acceptance
test is the one in `<verify>`: re-running the recorded command at the frozen sha must reproduce the
committed file exactly.

This snapshot is taken **before** plan 239-02 edits any template; a post-sweep snapshot would make
the containment check tautological.

**Step C — write the classifier.** Create
`239-comment-only-diff-check.sh`, executable (`chmod +x`), modelled section-by-section on
`237-security-comment-diff-check.sh` per `239-PATTERNS.md`:

- Header block: filename, the literal phrase `phase artifact, not repository tooling`, the anchor
  `(D-04)`, a rationale paragraph explaining why a syntactic `^[+-]\s*#` rule is wrong here (80 of
  158 lines are comments; 57 are `@moduledoc`/`@doc` heredoc prose; 17 are EEx-escaped HEEx tags),
  a `Usage:` block, a per-exit-code contract documented before any code, and an explicit sentence
  that it is NOT wired into any workflow or prohibitions glob.
- `set -euo pipefail` immediately after the header.
- Argv contract: exactly two positional arguments — `<diff-file>|-` and `<expected-set-file>`.
  Wrong arity → `exit 2`. Unreadable file → `FAIL: cannot read input file: …` on stderr → `exit 1`.
  `-` reads the diff from stdin.
- Fail-closed-on-empty guard, stronger than 237's (`:47-50`): empty diff content → exit 1 with
  `FAIL: empty diff input — refusing to report success on no input (fail-closed guard)`. Then two
  non-vacuity floors, both printed and both failing closed, **both derived from quantities known
  exactly before the sweep runs**:
  1. `removed_lines` must be `>= ` the number of `T:` records in the expected-set file (139). The
     floor is computed from that file at runtime, never hardcoded. Every one of the 139 golden
     token lines must change, and every changed line appears as a `^-` removal, so 139 is an exact
     lower bound on removals — unlike the diff's *addition* count, which is unknowable in advance
     because plan 239-02 partitions 127 of the 158 template lines as pure deletions with no
     replacement line at all. **Do not floor on `changed_lines`**: a correct diff is roughly 139
     removals plus only ~30 rewrite additions, so a `changed_lines >= 200` gate would fail on the
     success path.
  2. `files` must be `>= 30` (expected 35).

  Below either floor → exit 1 with a message naming the observed and required number.
  `changed_lines` is still computed and printed on every path; it is a reported measurement, not a
  gate.
- The containment body, three independent violation classes summed into `nonconforming`:
  1. `nonconforming_removed` — count of removed lines (`^-`, excluding `^--- `) whose
     `(path, whitespace-trimmed leading-`-`-stripped text)` pair does not appear among the
     expected-set records, where `path` is the enclosing hunk's `^+++ b/` path with the `b/` prefix
     stripped. Compare **path plus trimmed text, never line numbers**: the EEx header offsets
     template line numbers by 2 relative to the golden tree, so line-number mapping is structurally
     wrong (RESEARCH §5.5). Pairing on the path rather than on text alone is what keeps the `N:`
     neighbour records from widening the check across files — a removed code line only ever matches
     a neighbour record admitted for its own file.
  2. `nonconforming_files` — count of `^+++ b/` paths in the diff that are not among the paths in
     the expected-set file.
  3. `nonconforming_addonly_hunks` — count of hunks (`^@@`) containing at least one `^+` line and
     zero `^-` lines. This is the pure-addition drift path that a removals-only containment check
     would miss.
- Follow the 237 pipeline idiom exactly: every `grep` in a pipeline carries `|| true` under
  `set -e`, results are held in shell variables, and emptiness is tested with `[ -n … ]` rather than
  relying on grep exit status. `awk` is acceptable for the hunk walk.
- Verdict block: on violation, `FAIL: …` plus the offending lines to **stderr**; on both paths print
  `changed_lines=<N>`, `removed_lines=<N>`, `files=<N>`, `nonconforming=<N>`, plus the three
  sub-counters and the `removed_lines` floor that was applied, to **stdout**;
  explicit `exit 0` on clean, `exit 1` on violation.
