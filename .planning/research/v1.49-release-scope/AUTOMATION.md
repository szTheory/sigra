## Automation recommendation

Keep GitHub Actions + Release Please manifest mode + the existing `ci-gate` + `mix hex.publish` path for 1.5.1. It already fits the one-package Elixir project, is reviewable through a Release PR, and keeps the Hex key out of CI and PR jobs. Do not add a new release platform or make a manual approval the normal publish path.

Before using it for 1.5.1, make the release workflow non-cancelling while it is in progress; verify the tag resolves to Release Please's output SHA before testing/publishing; scope workflow permissions per job; and make success and failure evidence durable and machine-readable. Treat the existing manual recovery workflow as a documented recovery route. Keep any credential or artifact-provenance expansion limited to this release lane.

## Risks and bounded recommendations

### 1. Do not cancel an active release lane (critical)

`.github/workflows/release-please.yml` groups every main-branch run together and sets `cancel-in-progress: true`. Since `gate-ci-green` can wait up to 75 minutes and publication follows it, a later push to `main` may cancel the whole release workflow during the gate or publish. That can interrupt a non-idempotent remote publish after the request was accepted and can suppress `notify-release-failure` because concurrency cancels the run itself. Configure release serialization so an active release run is allowed to finish (`cancel-in-progress: false`); leave superseding cancellation to PR CI. GitHub documents that concurrency groups cancel a prior running job when configured to cancel and otherwise retain only one pending run by default, so a later event can replace an older pending event. The Release Please run is repeatable on the newest `main` commit, but validate that the merge-triggered release run is not lost under a rapid-push scenario. [GitHub Actions concurrency](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)

CI already deliberately keys non-PR events on unique run IDs and only supersedes PR runs. Preserve that constraint; do not replace it with a shared `main` queue or a quoted boolean. The detailed explanation in the current `ci.yml` is consistent with GitHub's documented single-pending-run behavior.

### 2. Tie release ref, tested SHA and published source together

The gate correctly queries `gh run list --commit "$SHA"` and checks the `ci-gate` conclusion. The publish job, however, checks out the mutable tag name. Before package work, explicitly resolve the tag to a commit and assert it equals Release Please's output SHA; publish/test that immutable SHA and separately assert the required `v1.5.1` tag resolves to it. Keep the existing tag/version/manifest/source_ref truth checks. This closes the gap where an exact-SHA gate passes but a moved or mistyped tag supplies different publish source. Release Please exposes `sha`, `tag_name`, and `version` specifically for downstream release jobs. [Release Please Action outputs](https://github.com/googleapis/release-please-action#outputs)

The CI wait script returns only SHA, run URL, attempts and verdict in JSON mode; current workflow uses human-readable table output and does not upload a gate receipt. Emit and retain one compact JSON receipt with tag, SHA, workflow/run ID, `ci-gate` conclusion, run URL, attempts and timestamp. Extend the post-publish receipt with source SHA and workflow run URL/ID, and ensure a publish failure before the visibility script still produces an artifact; today the `always()` upload step ignores a missing file, so early failures may leave no evidence artifact. Keep the 90-day artifact and commit a concise final receipt with milestone evidence; current post-publish JSON does not carry source commit or run identity. [Workflow artifacts and retention](https://docs.github.com/en/actions/tutorials/store-and-share-data)

### 3. Reduce write scope and secret exposure

The workflow-wide permissions grant `actions: write`, `contents: write`, `issues: write`, and `pull-requests: write`; `release-please` and `notify-release-failure` inherit them, while the gate and Hex publish jobs declare narrower job-level permissions. Set a read-only workflow default, then grant each job only the write scopes it needs: Release Please its required release/PR/issue scopes, the CI dispatcher `actions: write` plus `contents: read`, the Hex job `contents: read`, and the issue reporter `issues: write` plus checkout read access. Full-SHA pinning is already in use across the inspected workflows and should stay. [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use)

Hex's `--dry-run` performs local build/check work without publishing, so it does not need `HEX_API_KEY`. The current workflow exposes that key to both dry-run and publish steps; remove it from dry-run and pass it only to final publish. Use an expiring, API-write-only key and keep it unavailable to pull-request runs. Hex's CI docs specify API write permission and `HEX_API_KEY`; they also caution that automation may hide useful warnings. [Hex CI publishing guidance](https://hex.pm/docs/publish), [Hex `mix hex.publish`](https://hex.hexdocs.pm/Mix.Tasks.Hex.Publish.html)

The repo's `prompts/elixir-oss-lib-ci-cd-best-practices-deep-research.md` endorses Release Please, `mix hex.publish --dry-run`, tight secret scope, least-privilege tokens and SHA-pinned actions. Its broad generic proposals (add Dependency Review, actionlint, more static-analysis jobs, wide OS/version matrices, or adopt reusable workflows) are not requirements for 1.5.1 and should not expand this release scope. Its PAT advice applies only if downstream checks must be triggered by Release Please-created push/PR events: GitHub documents that `GITHUB_TOKEN` generally does not trigger new workflow runs, while the current lane uses an explicit `workflow_dispatch` fallback for tag-ref CI. [GitHub GITHUB_TOKEN behavior](https://docs.github.com/en/actions/concepts/security/github_token)

### 4. Keep retries state-aware and bounded

The current gate polls every 30 seconds for at most 60 minutes and dispatches tag CI once per invocation after three empty polls. The Hex visibility verifier polls up to 36 times at 10 seconds. These bounded waits are reasonable for a single release, and the gate's empty-run result fails closed. The polling load is modest for one release (about 120 run-list requests maximum), but do not add fast loops or parallel watchers. On ambiguous publish timeout, query Hex for the exact version before retrying; never infer failure from a lost client response or blindly publish a replacement. The current “version exists, skip publish” check should be followed by the same visibility/docs evidence and should not be treated as proof of package identity. Hex documents a 24-hour correction/revert window for a first package release and one hour for later releases; use the runbook's precise 1.5.1 recovery instructions and do not expand to `--replace`/`--revert` without verifying the current remote release. [Hex publish recovery rules](https://hex.hexdocs.pm/Mix.Tasks.Hex.Publish.html)

GitHub asks API clients to pace and back off when rate-limited; the current single-run polling cadence stays below that concern. Honor `403`/`429` and server retry guidance rather than adding immediate retries. [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

### 5. Do not make attestations a release blocker yet

The post-publish JSON artifact is useful operational evidence, not cryptographic provenance. GitHub artifact attestations can prove where/how a workflow-built artifact was made and require additional `id-token`/`attestations` permissions. Hex package publishing already creates the authoritative package tarball from the tagged source. For 1.5.1, record the exact source SHA and workflow receipt; defer signed tarball provenance until the project defines how the attested tarball is the exact package bytes uploaded to Hex. [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)

## Version-parameterized release path

1. Merge the reviewed Release Please PR only after normal protected-main requirements pass; confirm its tag/version outputs (`v$VERSION`) and one immutable SHA.
2. Verify `v$VERSION` resolves to that SHA, dispatch/observe tag-ref CI, and require `ci-gate=success` on the exact SHA. A green main-branch run is not a substitute for release-ref evidence.
3. At that same SHA, check version/manifest/source_ref, compile with warnings as errors, run library tests and docs, inspect `mix hex.build --unpack`, and pass `mix hex.publish --dry-run --yes`.
4. Publish once with the narrowly scoped Hex key; then verify package API visibility and HexDocs source links resolve to `v1.5.1`. Preserve machine-readable gate and post-publish evidence for 90 days, including source SHA and run identity. If the publish step has an ambiguous outcome, inspect Hex first and use the documented recovery route.
