# Release Delivery Ecosystem Research: Sigra v1.49 Candidate

**Scope:** Elixir OSS release conventions for a patch release after published `1.5.0`. This report informs release-delivery scope only; it does not recommend product or authentication features.

## Decision

Keep Sigra's existing reviewed Release Please release-PR flow and its release-SHA CI gate, package inspection, Hex dry run, publication, and post-publish evidence. The live PR #224 proposes `1.6.0` from protected-main SHA `5a00b90d`, is merge-clean, and has passing checks including `ci-gate`; its review decision is still blank. The user initially selected `1.5.1`, so changing the target to `1.6.0` requires explicit confirmation. Recommendation: use the already-generated `1.6.0` candidate rather than constructing a backport, curate its maintainer-facing “Features” entries into accurate adopter notes, and align installation examples to `~> 1.6.0`. If the target remains 1.5.1, scope a separate patch-only source selection and do not merge #224 as that release.

Do not create a new release mechanism or infer that v1.48's unfinished 1.5.1 outcome is already completed. Its safety closeout required a separately scoped phase and fresh explicit authorization. The user's `1.5.1` selection supplies that authorization only for a scope that still targets 1.5.1; the material switch to 1.6.0 needs confirmation. Once the final target and scope are confirmed, do not ask again for the same publication authorization absent another material change.

## What successful projects demonstrate

- **Ecto:** The changelog groups changes by component and impact, separates enhancements from bug fixes, labels deprecations, and explicitly states minimum Elixir versions or potential incompatibilities where needed. The CI workflow checks multiple Elixir/OTP combinations, runs warning-as-error compilation and tests, and exercises integration builds. Emulate the clarity and compatibility disclosures; do not infer that every Ecto CI dimension is necessary for this one patch release. [Ecto changelog](https://github.com/elixir-ecto/ecto/blob/master/CHANGELOG.md), [Ecto CI](https://github.com/elixir-ecto/ecto/blob/master/.github/workflows/ci.yml).
- **Plug:** The changelog keeps a concise section for every patch and clearly separates security fixes from ordinary bug fixes; its history includes repeated patches against older supported minor lines. Its CI explicitly tests earliest- and latest-supported Elixir/OTP pairs and gates formatting/lock hygiene on the lint lane. Emulate precise patch notes and security labeling; branch backports are relevant only if Sigra has a maintained older branch. [Plug changelog](https://github.com/elixir-plug/plug/blob/main/CHANGELOG.md), [Plug CI](https://github.com/elixir-plug/plug/blob/main/.github/workflows/ci.yml).
- **Phoenix:** Phoenix keeps the active major/minor changelog visible and points users to the `v1.8` branch for its supported line's detailed changelog. Its release notes include rolling-deploy sequencing advice where mixed-version nodes could behave differently. Emulate release-specific compatibility/operations advice when it is needed; avoid adding generic upgrade prose when no consumer action exists. [Phoenix changelog](https://github.com/phoenixframework/phoenix/blob/v1.8/CHANGELOG.md), [current changelog index](https://github.com/phoenixframework/phoenix/blob/main/CHANGELOG.md).

## Sigra evidence and implications

**Repository evidence:** At research time, `mix.exs` declares `@version "1.5.0"`; `.release-please-manifest.json` also says `1.5.0`; and the latest changelog release is `1.5.0`. `release-please-config.json` uses `release-type: elixir`, root manifest mode, and a `v` prefix. `.github/workflows/release-please.yml` already creates the reviewed release PR, waits for CI green on the release SHA, verifies version/tag/manifest/docs-source alignment, tests/builds docs, inspects the unpacked Hex artifact, dry-runs and publishes Hex, and records public registry/HexDocs evidence.

The live Release Please PR #224 is based on protected `main` SHA `5a00b90d`, proposes `1.6.0`, and has green checks including `ci-gate`. The generated release notes contain three internal tooling/remediation “Features.” The package diff since 1.5.0 touches 77 code, generated-template, and documentation files; this is not a trivial patch-only content set. The PR is open with no recorded review decision, and the user's prior scope explicitly selected 1.5.1.

**Repository footgun:** `CHANGELOG.md` says Release Please inserts the generated section below the maintainer warning beneath `## Unreleased`; the file is included in the package (`mix.exs` package file list). A missed manual fold therefore publishes a visible `Unreleased` heading/warning to consumers. The generated PR diff is the right place to assert that notes appear under the selected release heading—currently `[1.6.0]`—and that `Unreleased` stays empty.

**Prior-state constraint:** v1.48 Phase 242's safety closeout says no 1.5.1 release receipt exists and future publication must start in a separately scoped phase with fresh explicit authorization. The user's initial `1.5.1` selection authorizes a 1.5.x backport; moving to 1.6.0 is a separate version decision. Phase 242 delivered a bounded `~> 1.5.0` install-doc safeguard only; do not report that as proof a new release was made or resolver behavior repaired. [Phase 242 safety closeout](../../milestones/v1.48-phases/242-hex-retire-docs-revert-pinned-install-adr-cut-1-5-1/242-SAFETY-CLOSEOUT.md).

## Facts vs. inference

- **Source-backed facts:** Hex requires SemVer, publishes docs alongside a package by default, recommends local docs builds, documents dry-run/unpack commands, and warns that CI automation can hide publish warnings. SemVer classifies patch versions as backward-compatible bug fixes. Release Please's action documents a review PR; merge updates the changelog, tags the commit, and creates a GitHub Release. (Sources below.)
- **Sigra-specific facts:** Release automation and post-publish checks described above are present in the checked-in manifest/config/workflow. Phase 242 explicitly recorded unsuccessful bounded remediation attempts and no release receipt.
- **Inference/recommendation:** Given the existing automation and 1.5.0 published baseline, the lowest-risk ecosystem fit is to retain the current workflow and spend review effort on the actual generated patch contents and public artifact. This follows from Hex's package immutability window and the project’s prior closeout, not from a claim that all mature projects use Release Please.
