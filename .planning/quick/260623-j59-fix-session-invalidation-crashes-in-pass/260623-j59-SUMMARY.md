# Fix: session invalidation crashes in password-change and account-deletion flows

## Bug (reproducible, shipped, sibling of 260622-nft)
`password_change.ex` and `deletion.ex` invalidate sessions via the real
`Sigra.SessionStores.Ecto` store but never threaded the opts that store requires,
so the public `Sigra.Auth` path **crashed** the moment it ran. Only mock-based
unit tests exercised these flows, so — exactly like the email-change bug
(260622-nft) — the crashes shipped.

## Root cause — THREE chained defects (the plan found the first; integration testing found all)
1. **Missing `session_store_opts`** (planned). `delete_all_for_user/2` was called
   with only `except_token` / `[]`; the Ecto store does `Keyword.fetch!(opts, :repo)`
   + reads `:session_schema` → `ArgumentError`.
2. **`Sigra.Config` struct is not Access-compatible** (found via integration test).
   `password_change.ex` / `deletion.ex` did `get_in(config, [...])`, but on the
   public path `config` is a `%Sigra.Config{}` struct → `UndefinedFunctionError
   (Sigra.Config.fetch/2)`. This actually fires *before* defect 1.
3. **`schedule_deletion` never passed `:token_query_fn`** (found via integration
   test). `Sigra.Account.Deletion` does `Keyword.fetch!(opts, :token_query_fn)`,
   and the wiring also used struct-unsafe `get_in(config, [:audit|:session, ...])`.

All three are the same family: the public `Sigra.Auth` entrypoints were never
integration-tested against the real config struct + real Ecto store.

## Fix (3 commits)
- **`880fe5fe`** — thread `session_store_opts` via `session_store_and_opts/2` in
  `auth.ex` (`change_password` + `schedule_deletion`); forward
  `Keyword.get(opts, :session_store_opts, [])` (+ `except_token` for password
  change) to `delete_all_for_user` in `password_change.ex` / `deletion.ex`.
  Exact mirror of email-change commit `c2ab16f1`.
- **`9a157a9f`** — `access_config/1` helper (maps a `Sigra.Config` struct before
  `get_in/2`; maps/keyword lists pass through) in both account modules;
  `schedule_deletion` now threads `token_query_fn` (identical lambda to the
  confirm/reset/email-change paths) and reads `config.audit` / `config.session`
  directly.
- **`5a25f665`** — integration tests + `oban_jobs` migration for the example.

`email_change.ex` untouched (the correct reference). **Library-only** — these
flows have NO `priv/templates` or golden-fixture mirror (unlike `user_token.ex`
in 260622-nft), so nothing to byte-sync.

## Verification
- New `test/example/test/example/accounts/session_invalidation_test.exs` (real
  `Sigra.SessionStores.Ecto`):
  - change_password sign-out-other-sessions → other sessions deleted, current
    preserved via `except_token`, password actually changed.
  - schedule_deletion → ALL of the user's sessions revoked.
- **Regression guard proven:** reverting the lib fix to its pre-task state
  (f1e6dec6) makes both new tests fail (2 failures — `Sigra.Config` Access crash,
  with the `Keyword.fetch!(:repo)` crash behind it); restoring the fix → 0
  failures.
- Library unit tests (mock-based) still pass: `password_change_test` +
  `deletion_test` → **28 tests, 0 failures**.
- Full example suite: **225 tests, 0 failures** (223 baseline + 2 new).
- `mix compile --warnings-as-errors` clean.

## Follow-up noted (out of scope, not filed unless wanted)
The `oban_jobs` migration is the pragmatic example-app fix. The deeper question:
`schedule_deletion` enqueues an Oban job whenever Oban is *compiled*
(`Code.ensure_loaded?(Oban)`), even if the host neither supervises Oban nor has
the `oban_jobs` table — which would raise `42P01` in such a host. Worth a library
robustness pass (respect `dispatch: :sync` / guard the enqueue) but separate from
this session-invalidation fix.
